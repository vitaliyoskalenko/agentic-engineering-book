Після уроку ви зможете

  • увійти в незнайомий репозиторій за маршрутом «карта → гарячі точки → шви → характеризаційні тести → зміна» і перевірити карту агента скриптом;

01

Дві різні проблемиЧужий код і зміна, більша за рев'ю

Legacy-код і великі зміни ламають роботу з агентом з протилежних боків. У чужому коді агент не має моделі системи: правка компілюється, тести зелені, але друге місце, яке теж треба було змінити, лишилося незачепленим (8.4, «змінили одне з двох місць»). У великій зміні модель є, але diff більший за увагу рецензента: 38 файлів і +1600/−649 рядків одним комітом ніхто не прочитає уважно.

Ціна великої зміни — не токени (фан-аут на 9 файлів коштував $0,06), а година рецензента на кожен непомічений побічний ефект. Тому бюджет іде в гейти й нарізку, а не в сильнішу модель.

02

Вхід у legacyМаршрут із п'яти кроків

Для мене legacy-код — це просто код без тестів.

“To me, legacy code is simply code without tests.”

Michael Feathers, «Working Effectively with Legacy Code», передмова, 2004

У Фезерса алгоритм зміни legacy-коду: знайти точки зміни → знайти точки для тестів → розірвати залежності → написати тести → змінити й відрефакторити. З агентом до нього додається крок нуль — карта, бо агент, на відміну від вас, не пам'ятає вчорашньої розвідки.

Шов у Фезерса — «місце, де можна змінити поведінку програми, не редагуючи її в цьому місці»; у кожного шва є точка ввімкнення, де обирають, яку поведінку використати. У Python це параметр (parse(timestr, parserinfo=…) у dateutil), підклас, атрибут модуля, який читають під час виклику (tz.tz.TZPATHS), або об'єкт-файл замість шляху (tzfile(fileobj)). Шви агент знаходить добре — усі 19 адрес швів у трьох картах нижче існують у коді, — але який із них безпечний для тесту, вирішує людина: monkeypatch глобального TZPATHS зачіпає кожен тест у процесі.

“A seam is a place where you can alter behavior in your program without editing in that place.” “Every seam has an enabling point, a place where you can make the decision to use one behavior or another.” — Feathers, розд. 4

Що просити від карти

Не «опиши архітектуру», а JSON з адресами: файл + символ для кожного входу, шва й ризику; файл + модуль для кожної залежності; файл тестів для кожного модуля. Адресу перевіряє AST за мілісекунди; прозу — лише людина.

Три способи змінити багато кодуМеханічний, судження, гібрид

Перше питання до великої зміни — чи вміщається правило в код. Якщо так, агент пише інструмент, а не правки: інструмент детермінований, повторний запуск нічого не змінює, і рецензент читає 20 рядків правила замість 600 рядків diff.

Codemod — програма, що переписує код за правилом. LibCST для цього парсить Python у конкретне синтаксичне дерево, яке «зберігає всі деталі форматування (коментарі, пробіли, дужки тощо)», тож незачеплені рядки лишаються байт у байт. Механічну частину B40 закриває один клас:

class InitReturnsNone(VisitorBasedCodemodCommand):
    DESCRIPTION = "Add '-> None' to every __init__ that has no return annotation."

    def leave_FunctionDef(self, original_node, updated_node):
        if updated_node.name.value == "__init__" and updated_node.returns is None:
            return updated_node.with_changes(returns=cst.Annotation(cst.Name("None")))
        return updated_node

05

Нарізка великої зміниExpand → migrate → contract і правила зупинки

Паралельна зміна, або expand and contract, — патерн для безпечного впровадження зворотно несумісних змін інтерфейсу: зміну ділять на три окремі фази — розширення, міграцію і скорочення.

“Parallel change, also known as expand and contract, is a pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract.”

Danilo Sato, martinfowler.com, 13.05.2014

B21 з беклогу Lectern — наскрізний рефакторинг: схеми трьох інструментів жили двічі — рукописний SCHEMAS для агентів на Agent SDK і Messages API та type hints MCP-сервера. Ось як він ліг у коміти, кожен із зеленим scripts/check.sh:

  1. Expand (f3d8323): @tool("…") на методах Session, QuizItem як TypedDict, генератор tool_schemas(). Ніхто його ще не споживає; тест: tool_schemas(Session) == SCHEMAS байт у байт.
  2. Migrate + contract (86876be): SCHEMAS = tool_schemas(Session), рукописний літерал видалено й заморожено в тесті-знімку; Pydantic-модель MCP будується з того самого TypedDict. mcp_contract.py check — «contract unchanged (0.3.0)».
  3. Docs (698c054): CLAUDE.kit і карта модулів — як тепер додають інструмент.

Оракул «поведінка не змінилася» тут — не лише тести. Знайшлися два приховані споживачі схеми:

  • Кеш. PROMPT_VERSION — хеш системного промпту, задачі і схем; він входить у ключ кешу результатів. Додати опис до поля answer означало б нову версію й холодний кеш. Тому p-861a085610 до і після — частина приймання.
  • Два рендери одного факту. Агент на Messages API працює зі strict: true, а strict-режим не підтримує minimum/maximum, лише enum. MCP-модель Pydantic пише ge=0, le=3. Одне джерело — Annotated[int, Choice(0, 3, "index of the correct option")], два рендери: enum [0, 1, 2, 3] для агентів, minimum/maximum + опис для MCP.

Старий тест порівнював лише імена полів. Мутація на каноні — le=3 → le=4 у MCP-моделі — його проходить; новий тест порівнює типи й діапазони і падає на quote: str → list[str]. Тайпчекер теж окупився: list[QuizItem] там, де тіло чекає list[dict] (4 нові помилки mypy), і клас із create_model, якого mypy не бачить (ще 4) — cast в одному місці й псевдонім під TYPE_CHECKING.

Коли потрібен feature flag

Expand-contract усередині одного релізу обходиться без прапорця: проміжні коміти не змінюють поведінки. Прапорець (feature toggle — «змінити поведінку системи, не змінюючи коду», Pete Hodgson) потрібен, коли нова й стара поведінка мають жити в продакшні одночасно: міграція даних, новий конвеєр генерації, поступове ввімкнення для частини авторів.

  1. Обсяг: змінено рівно цей файл (git diff --name-only + невідстежувані).
  2. Повнота: ruff check --select ANN на файлі чистий.
  3. Лише анотації: scripts/annotations_only.py порівнює AST до і після, викинувши анотації, — cast(), нове значення за замовчуванням чи перейменування не пройдуть.
  4. Типи узгоджені: жодної помилки mypy, якої не було в базі (помилки бази — 23 на тому знімку — порівнюються як множина без номерів рядків).
  5. Поведінка: увесь pytest.

  • Фан-аут claude -p у циклі з --allowedTools (урок 4.4). Порада документації — «Test on a few files, then run on all of them»: доведіть промпт на перших 2–3 файлах. Наш пілот це підтвердив.
  • Великий код (сторінка «monorepo or large codebase»): CLAUDE.md по теках вантажиться на вимогу, claudeMdExcludes відсікає чужі й legacy-пакети, Read-deny — згенерований і vendored-код, плагіни code intelligence дають визначення й посилання через language server замість grep-сканування, worktree.sparsePaths — sparse checkout для worktree.

  • Хмарні задачі: у кожної свій робочий простір, працює, поки ваш комп'ютер спить; результат — коміт або pull request.

  • Cloud Agents (колишні Background Agents): ізольовані VM, клонують репозиторій і працюють в окремій гілці; паралельно — скільки завгодно.

Квіз10 ситуацій

10 питань
1. Агент повернув карту legacy-репозиторію: 62 твердження, перевіряльник підтвердив усі адреси файлів і символів. Що це гарантує?
Так. AST перевіряє адреси, а «найбільше churn» Sonnet написав усупереч власному git log, який показав по 2 коміти на файл. Поле «доказ» робить таке судження перевірюваним.
Адреси — це структура; судження («гаряча точка», «ризик») AST не перевіряє. А назви символів популярної бібліотеки модель може знати з навчання: перший Sonnet не викликав Read жодного разу.
2. git log --name-only -- src | uniq -c у 20-річній бібліотеці дає по 1–2 коміти на кожен файл. Що робити?
Так. Після переходу dateutil на src/ наївний підрахунок дав 1 коміт для _parser.py, а --follow — 189.
1–2 коміти на 20 років — ознака переїзду, а не стабільності. Історія лишилася під старими шляхами; --follow іде крізь перейменування й повертає реальні 189/141/112.
3. Треба додати -> None до всіх __init__ без анотації у 300 файлах. Що обрати?
Так. Правило вміщається в код — агент має написати інструмент, а не 300 правок. У прогоні LibCST закрив 5 таких місць, другий запуск нічого не додав.
Агенти тут лише додають недетермінізм і рев'ю 300 diff. Однакове для всіх місць правило — механічна зміна: codemod плюс перевірка ідемпотентності.
4. Чому в B21 рукописний SCHEMAS не видалили першим же комітом, а спершу додали генератор поруч?
Так. Це фаза expand: нове існує поруч зі старим і перевірене тестом на рівність байт у байт; migrate і contract — наступним комітом.
API не розрізняє, хто написав схему, а MCP-контракт лишився 0.3.0. Сенс першого коміту — довести рівність, поки нічого не переключено (expand).
5. Ви додали опис до поля answer у схемі для агентів Lectern. Що зміниться, крім тексту схеми?
Так. prompt_version() хешує системний промпт, задачу й схеми; тому знімок схем у B21 — окреме рішення, а p-861a085610 до і після — частина приймання.
Схема агентів не входить у MCP-контракт, а описи полів модель бачить. Прихований споживач — кеш: хеш схем є в PROMPT_VERSION, тож будь-яка зміна холодить кеш.
6. Один факт «answer — ціле від 0 до 3» у схемі для агентів записано як enum, а в MCP — як minimum/maximum. Чому не однаково?
Так. Одне джерело (Choice(0, 3)), два рендери під можливості споживачів; тест паритету порівнює саме діапазон.
Обмеження в споживачі з боку агентів: structured outputs у strict-режимі не підтримують числові обмеження. Тому джерело одне, а рендер — під кожного споживача.
7. У пілоті фан-ауту на двох шардах жоден агент так і не запустив гейт. Що робити?
Так. Пілот для того й існує: агенти склеювали команди, складену команду dontAsk відхиляв. Одне речення в промпті — і в раунді 2 відмов 0.
Агент без зворотного зв'язку від гейта не може виправитися сам, а широкий Bash знімає рамки. Правило зупинки: більшість пілоту впала — стоп і виправлення причини.
8. Три шарди проходять гейт лише тоді, коли агент переносить if TYPE_CHECKING: у кінець файлу. Висновок?
Так. Мітки за позицією робили новий імпорт угорі «зміною коду». Після виправлення раунд 2 дав 8/9 з першої спроби.
Зелений гейт не означає доброго коду, якщо агент оптимізує під його дефект. Агент навіть написав це в коментарі; правильна реакція — виправити гейт і перезапустити все.
9. Зміна «лише типи» пройшла AST-гейт, mypy і весь pytest, але GET /openapi.json віддає 500. Чому гейти не допомогли?
Так. AST-гейт виходить з того, що анотації не виконуються; для FastAPI, Pydantic і dataclasses це не так. Потрібен поведінковий оракул — тест сторінки, знімок OpenAPI.
Тести сервісу проходили, mypy перевіряв файл. Проблема в припущенні гейта: тип, імпортований лише під TYPE_CHECKING, FastAPI не зміг розв'язати під час генерації схеми.
10. Після переформату з .git-blame-ignore-revs колега і в GitHub, і локально бачить у blame автора форматера. Lectern лежить підтекою монорепозиторію. Що не так?
Так. GitHub шукає файл у корені репозиторію, а локальний git читає його лише через blame.ignoreRevsFile або --ignore-revs-file.
Документація git вимагає саме повні хеші. Переписувати історію не треба — для цього файл і існує; проблема в розташуванні й локальному налаштуванні.

1. Вхід у чужий репозиторій із перевірюваною картою
