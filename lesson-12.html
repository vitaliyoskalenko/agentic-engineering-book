01

Augmented LLMБудівельний блок і п'ять способів його скласти

Одиниця всіх патернів — augmented LLM: модель, якій дали пошук (retrieval), інструменти (tools) і пам'ять (memory). Сучасні моделі користуються ними самі: формують пошукові запити, обирають інструмент, вирішують, що зберегти. Anthropic радить дві речі: підганяти ці можливості під свою задачу і давати моделі простий, задокументований інтерфейс до них.

Усі приклади уроку стоять на одній функції. API-ключа тут немає, тож виклик моделі — це процес claude -p з порожнім набором інструментів і власним системним промптом. Модель за замовчуванням — Haiku: патерни не залежать від моделі, а вимірювати дешевше.

"""One LLM call = one `claude -p` process. Logs model, seconds and cost of every call."""
import json, subprocess, time

SYSTEM = "Ти — генератор навчальних матеріалів Lectern. Пиши українською, лише за наданим текстом."
LEDGER: list[dict] = []          # one row per call: model, seconds, usd (client estimate)


def llm(prompt: str, schema: dict | None = None, model: str = "haiku", system: str = SYSTEM):
    cmd = ["claude", "-p", prompt, "--model", model, "--output-format", "json", "--tools", "",
           "--strict-mcp-config", "--no-session-persistence", "--system-prompt", system]
    if schema:
        cmd += ["--json-schema", json.dumps(schema, ensure_ascii=False)]
    t = time.perf_counter()
    run = subprocess.run(cmd, capture_output=True, text=True, stdin=subprocess.DEVNULL)
    out = json.loads(run.stdout)
    LEDGER.append({"model": model, "s": round(time.perf_counter() - t, 2), "usd": out["total_cost_usd"]})
    if out.get("is_error"):
        raise RuntimeError(out.get("result"))
    return out["structured_output"] if schema else out["result"]


def xml(tag: str, text) -> str:
    """Wraps a piece of data in a tag, on its own lines, so the prompt separates data from orders."""
    return f"""
<{tag}>
{text}
</{tag}>"""

Тривіальний виклик зі схемою: 3,1 с від запуску процесу, з них 1,8 с — запити до API (duration_api_ms). Решта — старт CLI, тож у прямому API кожен патерн буде швидшим на ~1–2 с на виклик. Зі --json-schema CLI робить два ходи (num_turns: 2): відповідь приходить окремим кроком структурованого виводу. Ціни нижче — total_cost_usd, оцінка клієнта за прайсом, а не рахунок. Усі прогони, показані в уроці, — 99 викликів і 3 агентні сесії — коштували разом $0,24.

Усі п'ять патернів Anthropic відносить до workflows: етапи і їхній порядок тримає код. Найближче до агента orchestrator-workers — там модель уже вирішує, які підзадачі будуть, але не те, що станеться після них. Агент тримає цикл сам.

02

Prompt chainingЛанцюжок із gate між кроками

Задача розкладається на фіксовані кроки, кожен виклик обробляє вихід попереднього. Між кроками стоїть gate — програмна перевірка, що процес не з'їхав. За Anthropic, ланцюжок міняє затримку на точність: кожен виклик розв'язує простішу задачу. Доречний, коли задача чисто ділиться на кроки, які відомі заздалегідь.

"""1. Prompt chaining with a gate: lecture -> outline -> gate (code) -> quiz."""
from llm import llm, obj, xml
S, A = {"type": "string"}, lambda item: {"type": "array", "items": item}
OUTLINE = obj(sections=A(obj(title=S, points=A(S), quote=S)))
QUIZ = obj(questions=A(obj(q=S, options=A(S), answer={"type": "integer"}, quote=S)))


def gate(outline: dict, lecture: str) -> list[str]:
    """Code, not a model: returns the list of problems (empty = pass)."""
    secs = outline["sections"]
    errs = [] if 3 <= len(secs) <= 6 else [f"{len(secs)} розділів, треба 3–6"]
    errs += [f"«{s['title']}»: цитати немає в лекції" for s in secs if s["quote"] not in lecture]
    return errs + [f"«{s['title']}»: < 2 тез" for s in secs if len(s["points"]) < 2]


def chain(lecture: str) -> dict:
    outline = llm("Склади план лекції: 3–6 розділів, у кожному 2–4 тези і одна ДОСЛІВНА "
                  "цитата-речення з тексту." + xml("lecture", lecture), OUTLINE)
    if errs := gate(outline, lecture):
        raise ValueError(f"gate: {errs}")            # stop before paying for the quiz
    return llm("За планом склади по одному питанню з 3 варіантами на розділ. Питання — на "
               "застосування, а не на пригадування; answer — індекс правильного варіанта; "
               "quote — цитата розділу." + xml("outline", outline), QUIZ)

Той самий квіз ми зробили й одним викликом (план і gate не потрібні) — по три прогони кожного варіанта, Haiku, лекція «Класичне означення ймовірності» на 577 слів:

ВаріантВикликівЧас, сЦіна, $Цитати дослівні
Один виклик110,2–14,40,0015–0,002012 з 12
Chain + gate224,0–24,40,0036–0,003816 з 16; gate пройдено 3 з 3
Що показав вимір

На короткій лекції ланцюжок подвоїв ціну й час і нічого не додав: один виклик уже дав усі цитати дослівно, gate не спрацював жодного разу (разом із пробними прогонами — 7 з 7). Ланцюжок окуповується, коли gate справді щось ловить (довгий PDF, слабша модель) або коли проміжний результат читає людина: у Lectern автор затверджує план до генерації. Документація Claude формулює так само: явний ланцюжок корисний, коли треба бачити проміжні виходи або гарантувати структуру конвеєра.

Збій: gate перевіряє форму, а не зміст. У пробному прогоні питання про підмножини простору подій отримало дослівну цитату про те, що елементарні події взаємно виключні: підрядок знайдено, gate пропустив. Друга пастка — втрата контексту: крок 2 бачить лише план, тож усього, що план не зберіг, для квізу не існує.

03

RoutingКласифікувати й розвести по гілках

Routing класифікує вхід і передає його спеціалізованому продовженню: окремий промпт, інструменти або модель. Без нього оптимізація під один тип запитів псує інші. Працює, коли категорії справді різні і класифікувати їх можна точно — моделлю або звичайним класифікатором.

"""2. Routing: classify a learner's question, then send it to a different model / prompt."""
from llm import llm, obj, xml
KIND = obj(kind={"type": "string", "enum": ["factual", "conceptual", "off_topic"]})
ROUTES = {  # route -> (model, prompt); off_topic never reaches a model
    "factual": ("haiku", "Відповідай одним-двома реченнями лише за лекцією."),
    "conceptual": ("sonnet", "Поясни ідею за лекцією: інтуїція, приклад, типова помилка. "
                             "До 120 слів."),
}


def route(question: str, lecture: str) -> tuple[str, str]:
    kind = llm("Класифікуй питання студента до лекції. factual — відповідь є в тексті "
               "прямо; conceptual — треба пояснити «чому» або застосувати; off_topic — "
               "не про лекцію." + xml("question", question), KIND)["kind"]
    if kind == "off_topic":
        return kind, "Це питання поза темою лекції — поставте його викладачеві."
    model, prompt = ROUTES[kind]
    return kind, llm(prompt + xml("lecture", lecture) + xml("question", question), model=model)

П'ять питань до лекції, порівняння з варіантом без router — усе одразу на Sonnet з «пояснювальним» промптом:

ПитанняКлас → модельЧас, сЦіна, $
Як позначають простір елементарних подій?factual → Haiku8,10,0015
Чому для двох монет 1/2, а не 1/3?conceptual → Sonnet8,80,0154
Скільки коштує сертифікат?off_topic → шаблон5,90,0008
Чому m/n не працює для точки на відрізку?conceptual → Sonnet10,10,0155
Чому дорівнює ймовірність неможливої події?factual → Haiku11,70,0012
Разом з routing9 викликів44,60,0344
Усе на Sonnet5 викликів25,10,0587

Routing зекономив 41% грошей і коштував +78% часу: класифікатор — окремий виклик на кожне питання (3,7–8,4 с). Без нього Sonnet на питання «як позначають Ω?» відповів за шаблоном «інтуїція → приклад → типова помилка» — 101 слово там, де Haiku дав одне речення. Routing вибирає не лише модель, а й промпт під тип запиту.

Збій: помилка класифікатора мовчазна — складне питання тихо отримує дешеву модель і поверхову відповідь, і ніхто цього не бачить. Логуйте клас кожного запиту і ганяйте класифікатор на розміченому наборі (модуль 12). Затримку знімає дешевший класифікатор: регулярний вираз для очевидного off_topic, невелика модель або кеш класів. Про кеш промптів: у кожної моделі він свій (урок 1.5).

04

ParallelizationSectioning і voting

Кілька викликів працюють одночасно, а результати зводить код. Два різновиди: sectioning — незалежні частини задачі паралельно; voting — та сама задача кілька разів, щоб отримати різні відповіді й обрати за правилом. Anthropic додає: у задачі з кількома аспектами модель працює краще, коли кожен аспект — окремий виклик.

"""3. Parallelization: sectioning (code splits the input) and voting (same check, 3 graders)."""
import re
from concurrent.futures import ThreadPoolExecutor
from llm import llm, obj, xml
S = {"type": "string"}
CARDS = obj(cards={"type": "array", "items": obj(front=S, back=S)})
VOTE = obj(correct={"type": "boolean"}, reason=S)
GRADERS = ["Розв'яжи задачу сам і порівняй з позначеною відповіддю.",
           "Знайди в лекції правило, яке перевіряє це питання, і застосуй його.",
           "Спробуй довести, що позначена відповідь хибна; якщо не вдається — вона правильна."]


def sectioning(lecture: str) -> list[dict]:
    parts = re.split(r"(?m)^(?=\d+\. )", lecture)[1:]       # split by headings — in code
    with ThreadPoolExecutor(len(parts)) as ex:
        return list(ex.map(lambda p: llm("Дві картки (термін → визначення) за цим "
                                         "фрагментом." + xml("fragment", p), CARDS), parts))


def vote(item: str, lecture: str, parallel: bool = True) -> tuple[bool, list[dict]]:
    ask = lambda g: llm(g + xml("lecture", lecture) + xml("quiz_item", item), VOTE)
    with ThreadPoolExecutor(3 if parallel else 1) as ex:
        votes = list(ex.map(ask, GRADERS))
    return sum(v["correct"] for v in votes) >= 2, votes          # majority of 3

Sectioning: лекцію розрізав регулярний вираз за заголовками, чотири виклики по 4,8–5,1 с пішли одночасно — 5,1 с замість 19,6 с послідовно, 8 карток за $0,0031. Voting: три судді з різними промптами перевіряють ключ питання. Ті самі три виклики послідовно і паралельно:

ПитанняГолосиПідряд, сПаралельно, с
Ключ хибний (дві монети, позначено 1/3)0 з 3 «правильно» → ключ відхилено15,16,7
Ключ правильний (C(25,3) = 2300)3 з 3 → ключ прийнято17,37,6

У шести парах прогонів паралельний варіант був швидшим у 2,3–3,2 раза при тій самій кількості викликів. Різниця в ціні між парами — кеш промптів, не паралельність.

Судді проголосували за дефектне питання

Питання «ймовірність числа, більшого за 4» з варіантами A) 1/3, B) 2/6, C) 1/2 і ключем A має дві правильні відповіді. Три прогони голосування: 8 з 9 голосів «ключ правильний», більшість щоразу «так». Найцікавіше — у першому прогоні всі три судді написали в поясненні, що 2/6 = 1/3, але двоє поставили correct: true: ключ A справді правильний, а про те, чи він єдиний, їх не питали. Вузьке питання «які з варіантів правильні?» дало ["A", "B"] у 3 з 3 прогонів.

Збій: voting гасить випадкові помилки, але не систематичні. Судді з тієї самої моделі помиляються разом, а більшість ховає єдиний правильний голос меншості. Тому питайте вузько, по критерію на виклик, і обирайте поріг під ціну помилки: для квізу, який побачать тисячі студентів, — «будь-яке «ні» → людина». Sectioning ламається інакше: частини не бачать одна одну, тож дві картки можуть визначити одне поняття по-різному.

05

Orchestrator-workersМодель сама ділить задачу

Центральна модель (orchestrator) динамічно розбиває задачу, роздає частини моделям-виконавцям (workers) і зводить результат. Зовні схоже на sectioning, але підзадачі не задані наперед — їх визначає orchestrator для конкретного входу. Канонічний приклад Anthropic — зміни в коді, де кількість файлів і характер правок залежать від задачі. Зведення робить synthesizer: окремий виклик, що об'єднує результати workers.

"""4. Orchestrator-workers: the model decides the subtasks; workers run them; a synthesizer merges."""
from concurrent.futures import ThreadPoolExecutor
from llm import llm, obj, xml
S, I = {"type": "string"}, {"type": "integer"}
PLAN = obj(subtasks={"type": "array", "items": obj(topic=S, start=S, n_cards=I, focus=S)})
CARDS = obj(cards={"type": "array", "items": obj(front=S, back=S)})


def orchestrate(lecture: str, max_parts: int | None = 6) -> tuple[dict, list, dict]:
    cap = f"не більше {max_parts} " if max_parts else ""
    plan = llm(f"Розбий лекцію на {cap}смислові частини для карток. Для кожної: topic; start — "
               "перші 5–8 слів частини ДОСЛІВНО; n_cards 1–4 за щільністю; focus — що "
               "перевірити." + xml("lecture", lecture), PLAN)
    starts = [lecture.find(t["start"]) for t in plan["subtasks"]]     # -1 = not verbatim
    def work(i: int) -> dict:                                  # a worker sees only its slice
        t, a = plan["subtasks"][i], starts[i]
        part = lecture[a:min([s for s in starts if s > a], default=None)] if a >= 0 else lecture
        return llm(f"{t['n_cards']} карток про «{t['topic']}». Фокус: {t['focus']}."
                   + xml("part", part), CARDS)
    with ThreadPoolExecutor(8) as ex:
        drafts = list(ex.map(work, range(len(plan["subtasks"]))))
    deck = llm("Ти — synthesizer. Об'єднай картки в одну колоду: прибери дублікати й "
               "перекриття, вирівняй стиль, збережи порядок тем." + xml("drafts", drafts), CARDS)
    return plan, drafts, deck

Задача та сама, що в sectioning, — картки з лекції, — але межі частин тепер обирає модель. Перевірка в коді: start має бути дослівним початком частини, інакше worker отримує всю лекцію.

ПрогінЧастинВикликівЧас, сЦіна, $Карток: workers → колода
Sectioning (межі — код)445,10,00318
Без обмеження, прогін 1151770,00,023025 → 21
Без обмеження, прогін 291155,20,015521 → 18
Без обмеження, прогін 3101285,50,019422 → 21
max_parts=66839,00,009911 → 11

Той самий вхід дав 9, 10 і 15 частин: orchestrator дробить 577 слів аж до окремих «запитань для самоперевірки». З обмеженням у промпті — рівно 6 частин в обох прогонах. Synthesizer виявився найповільнішим кроком: 17,5 с і 46,0 с — близько половини часу прогону і третина ціни, — а прибрав 0–1 картку. Дублікати карток дешевше знімати кодом (нормалізувати front), а synthesizer лишити для конфліктів, які код не бачить.

Архітектура

Правило вибору: якщо межі частин можна обчислити кодом (заголовки, файли, сторінки), беріть sectioning — у нашому вимірі він у 3–7 разів дешевший і в 8–17 разів швидший. Orchestrator-workers потрібен, коли розбиття залежить від змісту і його неможливо передбачити. У продакшн-системі Research з Anthropic (червень 2025) orchestrator — Opus 4, workers — Sonnet 4; вона випередила одиночного агента Opus 4 на 90,2% на внутрішньому eval, але мультиагентні системи витрачають приблизно у 15 разів більше токенів, ніж чат. Команди агентів детально — у модулі 14.

06

Evaluator-optimizerГенерувати, оцінити, переробити

Один виклик генерує, інший оцінює й дає зворотний зв'язок, і так по колу. Anthropic називає дві ознаки, що патерн доречний: відповідь помітно кращає, коли людина формулює зауваження, і модель здатна сформулювати такі зауваження сама. Без чітких критеріїв цикл перетворюється на дороге перефразування.

Це генератор квізів Lectern v0. Він пройшов три версії, і кожна виправляла збій, виміряний на попередній:

from llm import llm, obj, xml
S, B = {"type": "string"}, {"type": "boolean"}
ITEM = obj(q=S, options={"type": "array", "items": S, "minItems": 3, "maxItems": 3},
           answer={"type": "integer", "minimum": 0, "maximum": 2}, quote=S)
VERDICT = obj(c1=B, c2=B, c3=B, c4=B, issues={"type": "array", "items": S})  # one bool per criterion
CRITERIA = """1) рівно один правильний варіант — перевір КОЖЕН окремо;
2) дистрактори — типові помилки студентів, а не випадкові значення;
3) питання на застосування в новій ситуації, а не на пригадування тексту;
4) quote — дослівне речення лекції, яке обґрунтовує відповідь."""

def generate_quiz_item(topic: str, lecture: str, max_rounds: int = 3) -> tuple[dict | None, list]:
    history, feedback = [], ""
    for rnd in range(1, max_rounds + 1):
        item = llm(f"Одне питання квізу на тему «{topic}» за критеріями:" + xml("criteria", CRITERIA)
                   + xml("lecture", lecture) + feedback, ITEM)
        v = llm("Ти — суворий рецензент, не виправляй сам. c1–c4: true, лише якщо критерій виконано "
                "ПОВНІСТЮ; issues — тільки недоліки." + xml("criteria", CRITERIA)
                + xml("lecture", lecture) + xml("quiz_item", item), VERDICT)
        v["c4"] = v["c4"] and item["quote"] in lecture              # code check beats a model's word
        unchanged = bool(history) and item == history[-1]["item"]   # a re-roll of the judge is not a fix
        passed = all(v[c] for c in ("c1", "c2", "c3", "c4")) and not unchanged
        history.append(dict(v, round=rnd, item=item, passed=passed, unchanged=unchanged))
        if passed: return item, history
        feedback = xml("previous_attempt", item) + xml("reviewer_issues", v["issues"])
    return None, history                        # 3 rounds failed: to a human, never to students
  1. Один boolean passed від рецензента. 2 з 2 тем пройшли в першому раунді, хоча в тих самих відповідях рецензент написав «критерій 4 виконано частково» і «індексація відповіді неоднозначна». Цілісна оцінка поблажлива: модель знаходить недолік і все одно ставить «так».
  2. Boolean на кожен критерій, вердикт рахує код. 2 з 3 тем пішли на другий раунд, але в одній генератор повернув те саме питання байт у байт, і рецензент цього разу його пропустив. Цикл «зійшовся» на шумі судді, а не на виправленні. Ще один прохід прийняв питання з 4 варіантами, хоча просили 3.
  3. v0: повтор без змін не зараховується, кількість варіантів і діапазон answer задає схема, дослівність цитати перевіряє код.

З восьми прийнятих питань чотири мають дефект поза критеріями. У трьох варіанти несуть пояснення міркування, а в одному прямо написано «1 — правильно: усі шість елементарних подій сприятливі» поруч із «1/6 — помилка: …». У двох випадках рецензент сам назвав підказки в issues, але поставив c1–c4 true: такого критерію не було. У четвертому генератор на темі «статистичне і геометричне означення» після зауваження до цитати змінив тему на кубик — і пройшов. Optimizer задовольняє критерії будь-яким шляхом, зокрема підміною задачі. Що не записано в критеріях і не перевірено кодом, того рецензент не гарантує.

У прикладі з cookbook Anthropic цикл — while True до PASS, без межі раундів; для демонстрації це нормально, у продукті — ні. Збої патерну: поблажливий або шумний рецензент; генератор обходить критерії; рецензент і генератор з однієї моделі мають спільні сліпі плями (як судді у voting); ціна росте лінійно з кількістю раундів.

Правило вибору

Блок-схему можна намалювати до запуску → workflow. Lectern: «лекція → план → квіз», «питання → клас → відповідь». Наступний крок залежить від знайденого, і кроків може бути 2 або 20 → агент. Lectern: цитата не знайшлася дослівно — треба шукати сторінку, інше видання, слід OCR. Start simple: почніть з одного виклику з retrieval і прикладами, міряйте на eval-наборі й додавайте крок лише тоді, коли він доведено покращує результат. На нашій лекції один виклик уже виконав критерій якості, а chain і агент коштували у 2–3 рази більше.

Патерни всередині інструментівClaude Code, Codex, Cursor

Ті самі п'ять патернів вбудовані в coding-асистентів. Знаючи, який саме працює, ви передбачаєте його ціну.

  • Subagents → orchestrator-workers. Кожен субагент працює у власному контекстному вікні, «досліджує свою ділянку незалежно, потім Claude синтезує результати». Orchestrator і synthesizer тут — сама сесія, і вирішує вона хід за ходом. Типово до 20 субагентів одночасно і до трьох рівнів вкладеності.
  • Поле model субагента → routing. Дешеву роботу можна віддати haiku, складну — opus.
  • Hooks → gate й evaluator. PreToolUse з кодом виходу 2 блокує виклик інструмента — це gate. Stop з "decision": "block" і reason не дає Claude зупинитися, і він продовжує з цим зворотним зв'язком — evaluator-optimizer, де рецензент — ваш скрипт. Hook типу prompt — одноразова оцінка моделлю, що повертає рішення в JSON.
  • Dynamic workflows → workflow у прямому сенсі. Claude пише JavaScript-скрипт, який оркеструє десятки субагентів; документація формулює різницю так само, як цей урок: у субагентів наступний крок вирішує Claude, у workflow — скрипт. Вбудований /deep-research розсилає пошук за кількома напрямками, звіряє джерела, голосує за кожне твердження і синтезує звіт — sectioning, voting і synthesizer разом.
  • Subagent workflows → orchestrator-workers за вашою вказівкою. Codex запускає субагентів, лише коли ви прямо попросите (або цього вимагають AGENTS.md чи skill), і збирає їхні результати в одну відповідь. Приклад з документації — sectioning за аспектами з синтезом: «один субагент на ризики безпеки, один на прогалини в тестах, один на підтримуваність; дочекайся всіх трьох і підсумуй».
  • Модель на агента → routing. Субагент успадковує модель і reasoning effort батька, якщо їх не задати в [agents] у config.toml або у файлі власного агента.
  • Документація попереджає про ціну: кожен субагент робить власну роботу з моделлю й інструментами, тож витрачає більше токенів, ніж один агент. /subagents показує потоки агентів під час роботи.
  • Subagents → orchestrator-workers. Агент Cursor делегує задачі субагентам, кожен з власним контекстним вікном. Вбудований Explore за замовчуванням працює на швидшій моделі — це routing. Власні субагенти — markdown з YAML у .cursor/agents/, поле model типово inherit.
  • /best-of-n → parallelization: voting. Та сама задача на кількох моделях одночасно, кожна у своєму git worktree. Порівнює і обирає переможця людина: команда сама нічого не зливає.

11 питань
1. Lectern має зробити короткий підсумок кожного з 30 уроків курсу; кожен урок — окремий файл. Який патерн?
Так. Межі відомі заздалегідь, тож розбиття моделлю — зайвий виклик і розкид. У нашому вимірі orchestrator був у 3–7 разів дорожчим і у 8–17 разів повільнішим за sectioning.
Orchestrator-workers потрібен, коли розбиття залежить від змісту і непередбачуване, а агент — коли невідома кількість кроків. Тут межі — файли, їх перелічує код, отже sectioning.
2. Три судді на Haiku відповідають на питання «чи правильна позначена відповідь?» і пропускають питання з двома правильними варіантами. Що допоможе найбільше?
Так. Судді бачили проблему (усі троє написали, що 2/6 = 1/3), але відповідали на інше питання. Вузьке питання дало ["A", "B"] у 3 з 3 прогонів.
Судді з однієї моделі помиляються корельовано: голосували за правильну відповідь на неправильне питання. Ще два такі голоси нічого не додадуть, а одностайність спіймала б дефект лише в одному прогоні з трьох — там, де один суддя сказав «ні».
3. Рецензент повертає passed: true, а в його ж issues написано «критерій 4 виконано частково». Що змінити?
Так. Цілісна оцінка поблажлива; окремий boolean на критерій з вимогою «true лише якщо повністю» і all() у коді робить вердикт перевірюваним.
Проблема в тому, що один boolean змішує всі критерії, і модель ставить «так» попри знайдені недоліки. Вердикт має рахувати код з окремих критеріїв.
4. Routing зекономив 41% грошей, але додав 78% затримки. Фіча — живий чат із жорстким SLA на відповідь. Що робити?
Так. Затримку додає окремий виклик класифікатора на кожен запит, а Anthropic прямо допускає звичайний класифікатор замість LLM.
Економія справжня, проблема — у ціні класифікатора за часом. Більша модель генерує повільніше, а другий класифікатор додав би ще один послідовний виклик.
5. На короткій лекції один виклик дав усі цитати дослівно, а gate ланцюжка не спрацював у 7 прогонах з 7. Що каже правило «start simple»?
Так. Складність додають, коли вона доведено покращує результат. Тут ланцюжок подвоїв ціну і час без виміряного виграшу.
Ланцюжок коштував ×2,1 ціни і ×2,0 часу, а його gate нічого не зловив; агент — ще дорожчий і менш передбачуваний. Без виміряної користі це зайва складність.
6. Orchestrator розбив лекцію на 577 слів на 15 частин. Що з цього випливає?
Так. 15 частин — це 17 викликів і 70 с проти 8 викликів і 39 с з max_parts=6; розкид 9–15 частин на тому самому вході теж ризик.
Кожна частина — окремий виклик worker, а synthesizer отримує більше чернеток, тож ціна і час ростуть. Розбиття обмежують явно: з max_parts=6 — рівно 6 частин, 8 викликів і 39 с.
7. У циклі evaluator-optimizer другий раунд повернув питання, ідентичне першому, і цього разу воно пройшло. Що сталося?
Так. Цикл «зійшовся» на випадковості судді. У v0 рядок unchanged відкидає такий pass.
Питання було те саме байт у байт — виправлення не було. Змінився лише вердикт, отже це шум рецензента.
8. Що з цього — workflow за визначенням Anthropic?
Так. Workflow — шляхи задані в коді. Документація Claude Code так і розрізняє: у субагентів вирішує Claude, у workflow — скрипт.
У двох інших варіантах наступний крок обирає модель — це агентна поведінка. У workflow шлях тримає код.
9. Після зауваження до цитати генератор замінив питання про геометричну ймовірність питанням про кубик — і пройшов. Як це закрити?
Так. Optimizer задовольняє лише записані критерії, будь-яким шляхом, зокрема підміною задачі. Тема має стати критерієм.
Більше раундів дадуть генератору більше спроб обійти критерії. Закривати треба сам критерій.
10. Цитату не знайдено в PDF дослівно: треба перевірити сусідні сторінки, інше видання, сліди OCR — заздалегідь невідомо, скільки кроків. Що будувати?
Так. Кількість кроків залежить від знайденого — класичний випадок для агента. Межі циклу і критерії зупинки — урок 2.2.
Фіксований ланцюжок не знає, скільки сторінок перебрати, а голосування без доступу до джерела лише вгадує.
11. Synthesizer займає близько половини часу orchestrator-workers і прибирає 0–1 картку. Що зробити?
Так. Нормалізація front і порівняння рядків коштують нуль викликів; синтез моделлю виправданий там, де потрібне судження.
Synthesizer за визначенням чекає на всіх workers, тож паралельно його не запустити. А «обов'язковий» він лише тоді, коли робить те, чого не зробить код.

Домашнє завданняДві задачі з AI-перевіркою

1. Розкладіть AI-фічу на патерни

Візьміть фічу зі своєї роботи (або підтримку магазину чи рев'ю PR), розбийте на 3–6 етапів, оберіть для кожного патерн за властивістю задачі, порахуйте виклики й множники ціни за вимірами уроку і назвіть два найімовірніші збої з кодовими контрзаходами.

2. Зламайте evaluator-optimizer

Напишіть три питання квізу з одиничними дефектами (два рівнозначні правильні варіанти, відповідь поза лекцією, дослівна, але не та цитата), проженіть їх через рецензента v0 по 3 рази, запишіть вердикти і запропонуйте для кожного пропуску перевірку кодом, вузьким питанням або людиною.
