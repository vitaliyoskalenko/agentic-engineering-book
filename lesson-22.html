Паралельна робота: git worktrees, фонові задачі, headless-режим

Паралельність скорочує час до результату, але не вартість і не рев'ю. Розбираємо механіку Claude Code: worktree, які він створює сам, фонові команди й сесії, що переживають закриття терміналу, і headless-запуски як цеглини скриптів — з реальними замірами на Lectern.

Після уроку ви зможете

  • обирати між worktree, фоновою роботою в сесії, фоновою сесією і fan-out headless-запусків за тим, що саме треба розпаралелити;
  • запускати агентів у worktree, які створює Claude Code (-w), готувати в них середовище через .worktreeinclude і хук WorktreeCreate, зливати результат і прибирати за собою;
  • передбачати, що з фонової роботи переживе закриття терміналу, а що ні;
  • писати скрипти над claude -p: ліміт паралельності, розбір JSON через jq, ланцюжки --resume, коди виходу, ліміт витрат;
  • заздалегідь бачити, де паралельні агенти впруться в ліміти, порти, базу даних або конфлікт злиття.
01

Чотири механізмиЩо саме ми розпаралелюємо

Заміри цього уроку на Lectern: дві незалежні задачі агентам Haiku — 40,4 с послідовно і 21,2 с паралельно; квізи для трьох лекцій — 88,1 с в один потік і 30,8 с у три. Витрати при цьому не впали: ~$0,004 за задачу в обох режимах. Паралельність купує час до результату, а не токени, і не скорочує ваше рев'ю (урок 3.5).

МеханізмЩо розпаралелюєІзоляція файлівПісля закриття терміналу
git worktree (claude -w)сесії, що редагують кодсвої файли й гілка, спільний .gitкаталог лишається; сесія — ні, якщо її не відправили у фон
фонова команда, монітор, фоновий субагентроботу всередині однієї сесіїнемає: той самий checkoutзупиняються разом із сесією
фонова сесія (claude --bg, /bg, agent view)цілі розмовивласний worktree перед першою правкоюпрацює під supervisor; зупиняється з вимкненням машини
fan-out claude -p зі скриптаоднотипні задачілише та, яку забезпечите ви: окремі вихідні файли або -wзвичайні процеси вашого скрипта
Правило вибору

Три питання по черзі. Задачі редагують ті самі файли? Потрібні окремі worktree або послідовність. Задачі потрібна розмова з вами по ходу? Це фонова сесія. Задачі однотипні й перевіряються кодом? Тоді fan-out headless-запусків, без розмови і часто без worktree.

02

Worktree у Claude Code-w, ізоляція і спільний .git

claude -w feature-auth (довга форма --worktree) створює .claude/worktrees/feature-auth/ у корені репозиторію на новій гілці worktree-feature-auth і запускає сесію там. Без імені Claude Code згенерує його сам, наприклад bright-running-fox. Додайте .claude/worktrees/ у .gitignore, інакше головний checkout бачитиме їх як untracked.

ПоведінкаЯк працюєНаслідок
База гілкиworktree.baseRef: "fresh" (типово) — гілка за замовчуванням з origin; якщо fetch був понад 24 год тому, Claude Code робить його, максимум 5 с. Без remote — локальний HEAD. "head" — ваш поточний HEADз "fresh" агент не бачить ваших незапушених комітів; конкретну гілку задати не можна — тоді git worktree add вручну
PR як базаclaude -w "#1234" або URL PR/MR → .claude/worktrees/pr-1234рев'ю чужого PR не чіпає ваш checkout; лапки обов'язкові, бо # у shell — коментар
Повторне ім'явідкриває наявний worktree; чистий і без власних комітів з "fresh" скидається на гілку за замовчуваннямім'я — ключ задачі: однакове ім'я для двох задач = одна папка
Субагентиisolation: worktree у frontmatter; тимчасовий worktree видаляється, якщо змін немаєбаза — та сама, що для -w, тобто не поточний стан батьківської сесії

Ізоляцію Claude Code примушує сам: блокує Edit/Write у шляхи головного checkout, Bash-команди з робочим каталогом там, перенаправлення git (git -C, GIT_DIR, cd перед git) і команди, з тексту яких не видно, куди піде git. Але ці перевірки читають текст команди, а не відстежують записи: cp або > у головний checkout вони не зупинять. Тому це захист від помилки агента, а не sandbox — для sandbox є урок 3.4.

Що worktree ділять з головним checkout, важливіше за те, що вони ізолюють:

  • .git: коміт агента одразу видно з головного checkout, а одну гілку не можна мати відкритою у двох worktree одночасно;
  • дозволи: «Yes, and don't ask again» у worktree записується в .claude/settings.local.json головного checkout і діє в усіх worktree репозиторію (з v2.1.211);
  • плагіни project scope і gitignored .claude/skills, agents, commands підтягуються з головного checkout;
  • хуки: ${CLAUDE_PROJECT_DIR} лишається коренем головного checkout, шлях worktree хук отримує в полі cwd вхідного JSON.

Середовище в кожному worktree

Worktree — свіжий checkout лише відстежуваних файлів: немає .env, .venv, node_modules, кешів збірки. Окремий venv для Lectern з закешованими wheel-ами — 11,1 с на кожен worktree.

Ми зробили оточення спільним, але без пастки: один venv лише з залежностями (anthropic, claude-agent-sdk, pytest, ruff), сам Lectern у ньому не встановлено, а pythonpath = ["src"] у pyproject.toml змушує pytest імпортувати код саме того worktree, у якому він запущений.

Хук WorktreeCreate повністю замінює git-логіку створення: він сам робить checkout, а останній непорожній рядок його stdout — шлях, у якому стартує сесія; усе інше — у stderr. З хуком .worktreeinclude не обробляється, а гілку, яку створив хук, Claude Code ніколи не видаляє: це робота парного хука WorktreeRemove. Наш хук дає кожному worktree власний порт:

# .claude/hooks/worktree-create.sh — у .claude/settings.json як хук WorktreeCreate
name=$(jq -r .name)
root=$(git rev-parse --show-toplevel)
dir="$root/.claude/worktrees/$name"
git -C "$root" worktree add -q -b "worktree-$name" "$dir" HEAD >&2
cp "$root/.env" "$dir/.env"               # .worktreeinclude з хуком не працює
n=$(git -C "$root" worktree list | wc -l | tr -d ' ')
sed -i '' "s/^LECTERN_PORT=.*/LECTERN_PORT=$((8400 + n))/" "$dir/.env"
echo "$dir"                              # останній рядок stdout = шлях

03

Справжній прогінДва агенти, два worktree, одне злиття

Lectern у стані після модуля 3, scratch-репозиторій без remote. Дві задачі з різною власністю файлів: T1 — lectern --version (cli.py, test_smoke.py), T2 — квіз відхиляє порожнє питання (tools.py, test_tools.py). Worktree створює сам Claude Code; агент працює, комітить і звітує.

# dispatch.sh NAME SPEC — один агент, один worktree
cd $root/lectern
export LECTERN_PY=$root/deps/bin/python      # спільні залежності, без самого lectern
claude -p -w $name --model haiku \
  --setting-sources project --strict-mcp-config \
  --tools "Read,Edit,Write,Glob,Grep,Bash" \
  --allowedTools "Read" "Edit" "Write" "Glob" "Grep" \
     "Bash(scripts/test.sh*)" "Bash(git add *)" "Bash(git commit *)" \
  --permission-mode dontAsk --max-turns 25 --max-budget-usd 0.30 \
  --output-format json "…промпт зі списком дозволених команд… $(cat $root/specs/$spec.md)" \
  > $root/runs/$name.json < /dev/null

-p пропускає діалог довіри до каталогу, тому -w працює і в щойно створеному репозиторії.

Фонова роботаКоманди, монітори, субагенти, фонові сесії

Усередині сесії

ЩоЯк запуститиМежі
фонова Bash-командапопросити «у фоні» (Claude ставить run_in_background: true) або Ctrl+B на команді, що вже йде (у tmux — двічі); список і зупинка — /tasksвивід пишеться у файл, Claude читає його через Read; команда, що не вклалась у таймаут (типово 2 хв), сама йде у фон, якщо не починається з sleep; понад 5 ГБ виводу — примусова зупинка

фоновий субагентв інтерактивній сесії типово увімкнено fork mode, і субагенти йдуть у фон самі; background: true у frontmatter тримає субагента у фоні завждименший набір інструментів, ніж у foreground; його запити дозволів з'являються у вашій сесії з ім'ям субагента

Час життя фонових команд залежить від того, чи є людина поруч. У локальній сесії в терміналі, desktop чи VS Code ліміту немає. У сесії без нагляду — -p, Agent SDK, CI, хмара — 30 хв типово і до 2 год, якщо Claude передасть timeout. У -p з текстовим промптом обидва значення — 10 хв. Команда, яку запустив foreground-субагент, зупиняється разом з ним; команда головної розмови переживає її фінальну відповідь.

Останнє правило змінює поведінку скрипта. claude -p не завершується, доки не закінчиться фонова команда головної розмови, і після неї робить ще один хід. Перевіримо на збірці, що йде 12 с:

Два result в одному потоці

Парсер, який читає stream-json до першого result, тут отримає «Збірку запущено.» і пропустить справжню відповідь. Беріть останній: jq -s 'map(select(.type=="result")) | last'. З --output-format json друкується результат останнього ходу. Скільки скрипт чекатиме: на фонову команду головної розмови — до її ліміту часу (тут 10 хв); на іншу фонову роботу — до 10 хв простою, після чого Claude Code зупиняє її й відкидає частковий результат. Стелю змінює CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS, а --max-budget-usd при досягненні ліміту зупиняє фонову роботу замість очікування.

Що переживає закриття терміналу

Звичайна сесія claude прив'язана до терміналу: при виході фонові команди прибираються. Якщо щось ще працює (субагенти, команди, монітори), замість виходу з'явиться діалог Background work is running з варіантом Move to background and exit. Він робить те саме, що /bg (або ← на порожньому промпті): сесія стає фоновою і переходить під supervisor — окремий процес, який тримає фонові сесії без терміналу. Нову фонову сесію запускає claude --bg "задача", а дивитися на всі одразу можна в agent view (claude agents, research preview).

Ліміти й конкуренціяДе паралельність перестає працювати

Підписка. Pro і Max мають п'ятигодинний ліміт сесії і тижневий ліміт, спільні для Claude і Claude Code, включно з IDE. Кожна фонова сесія витрачає квоту окремо: документація agent view прямо каже, що десять агентів вичерпують її приблизно вдесятеро швидше за одного.

API. Ліміти рахуються за запитами (RPM), вхідними (ITPM) і вихідними токенами (OTPM) окремо для кожного класу моделей і поповнюються безперервно (token bucket). Тому 60 RPM можуть застосовуватися як 1 запит на секунду, і десять агентів, стартованих в одну мить, — це сплеск. Різке зростання навантаження впирається ще й в acceleration limits: нарощуйте поступово. Перевищення дає 429, часто з retry-after. Claude Code повторює сам і в stream-json повідомляє про це подією system/api_retry з error: "rate_limit" — за нею видно, що паралельність уже впирається в стелю.

Паралельте, коли

  • задачі не ділять файлів, портів і даних;
  • кожну перевіряє команда, яку агент чи скрипт запускає сам;
  • задачі однотипні: N лекцій, N модулів, N репозиторіїв;
  • wall time важливіший за квоту: демо, реліз, нічний прогін.

Не паралельте, коли

  • друга задача залежить від результату першої;
  • обидві чіпають ту саму міграцію, схему чи pyproject.toml;
  • перевірка ручна і рев'ю вже вузьке місце;
  • квота підписки на межі, а задачі не термінові.

Новий scripts/batch_generate.sh запускає по одному headless-агенту на лекцію з лімітом паралельності, приймає квіз лише після lectern check --json, при відмові дає одну спробу виправлення в тій самій сесії і друкує підсумок вартості. Кожен агент пише тільки свої файли в out/batch/, тому worktree тут не потрібні.

one() {  # одна лекція → out/<stem>.{run1,run2,quiz,check,row}.json
  ask "$prompt" > "$OUT/$stem.run1.json"; rc=$?
  while :; do
    jq '.structured_output // {items: []}' "$run" > "$OUT/$stem.quiz.json"
    lectern check "$lec" "$OUT/$stem.quiz.json" --json > "$OUT/$stem.check.json"; ok=$?
    sid=$(jq -r '.session_id // empty' "$run")
    [ $ok -eq 0 ] || [ $attempt -ge 2 ] || [ -z "$sid" ] && break
    attempt=2   # модель уже прочитала лекцію — виправляємо в тій самій сесії
    ask "lectern check rejected the quiz: $(jq -r '.errors | join("; ")' …). Fix only these items…" \
      --resume "$sid" > "$OUT/$stem.run2.json"; rc=$?
  done
  # після --resume total_cost_usd уже містить перший запуск — не підсумовуйте їх
}
printf '%s\0' "$@" | xargs -0 -n 1 -P "$JOBS" bash -c 'one "$1"' _
jq -s -e 'all(.ok)' "${rows[@]}" > /dev/null   # код виходу скрипта: 0 лише якщо всі квізи пройшли

11

Квіз11 питань

11 питань
1. Дві задачі: перша додає таблицю й міграцію, друга змінює запит до тієї ж таблиці. Обидві — в окремих worktree. Що з цього вийде?
Так. Worktree ізолює лише файли репозиторію. БД, порти й Docker спільні, а друга задача ще й залежить від першої: краще послідовно або окрема БД на worktree.
Worktree дає окремі файли й гілку, але не окрему базу даних, тож тести заважатимуть один одному ще до злиття. Залежні задачі зі спільною БД ведуть послідовно або дають кожному worktree власну БД через хук.
2. Нічний скрипт запускає claude -p -w task-$N. Через тиждень git worktree remove падає з «cannot remove a locked working tree». Чому?
Так. Lock ставиться при створенні, щоб паралельне прибирання не знесло робочий каталог, і в -p лишається після завершення процесу — до stale-lock sweep наступної сесії.
Процес давно завершився — у причині lock видно його pid. Незлита гілка видаленню worktree не заважає; заважає lock. Claude Code не прибирає worktree неінтерактивних запусків: unlock → remove → git branch -d у самому скрипті.
3. Ви закомітили фікс локально і запустили claude -w review. Агент каже, що фіксу в коді немає. Найімовірніша причина?
Так. Допоможе worktree.baseRef: "head" або push перед запуском. У Cursor типова база навпаки поточний HEAD — пастка при зміні інструмента.
Коміт у спільному .git видно одразу, а 24 години стосуються лише того, коли Claude Code сам робить fetch. Типово база — гілка за замовчуванням з origin, тому локальних комітів агент не бачить.
4. Скрипт читає stream-json і зупиняється на першому result. Агент запустив збірку у фоні. Що отримає скрипт?
Так, саме це показав прогін уроку: два result в одному потоці. Беріть останній.
-p дозволяє фонові команди і чекає на команду головної розмови, але перший result друкує одразу, а після збірки робить ще один хід з окремим result.
5. Паралельний fan-out при невдалій перевірці робить claude -p "виправ" --continue. Чим це загрожує?
Так. Зберігайте session_id з JSON кожного запуску і передавайте --resume "$sid". У Codex exec resume --last має ту саму пастку.
Саме спільний каталог і створює проблему: «найсвіжіша» сесія залежить від того, хто фінішував останнім, а не від процесу. Сесії -p пропускає лише інтерактивний -c; claude -p --continue їх бере.
6. Для однієї лекції claude -p повернув код 1. Що зробити першим?
Так. У прогоні уроку неправильний флаг, ліміт бюджету і ліміт ходів дали той самий код 1. Розрізняє їх лише вміст stdout: error_max_turns, error_max_budget_usd.
Код 1 спільний для неправильного флага, ліміту ходів і ліміту бюджету, а 429 Claude Code повторює сам. Повтор допомагає лише при лімітах, і то зі зміненим лімітом.
7. Перший запуск повернув total_cost_usd: 0.0024, повтор через --resume — 0.0046. Скільки коштувала лекція?
Так. Це оцінка на клієнті, і вона наростаюча для сесії. Сума двох значень рахує перший запуск двічі.
Документація: при продовженні розмови запуск повідомляє загальну суму, включно з попередніми запусками. $0,0022 — ціна лише повтору.
8. В інтерактивній сесії працюють dev-сервер у фоні, фоновий субагент і монітор логу. Ви закриваєте сесію. Що станеться, якщо обрати Move to background and exit?
Так. Монітори при переході у фон не переносяться, і Claude Code попереджає про це діалогом.
Звичайний вихід справді все прибирає, але цей варіант робить те саме, що /bg: команди й субагенти переїжджають у новий процес, монітори — ні.
9. На Max ви запустили 8 фонових сесій і через годину отримали «You've hit your session limit». Допоможе перейти на Haiku через /model?
Так. Допоможе лише очікування скидання вікна, usage credits або менше паралельних сесій наперед.
Session limit — спільне вікно підписки для Claude і Claude Code, і кожна фонова сесія витрачає його окремо. Перемикання моделі допомагає лише при модельних лімітах на кшталт «Opus limit».
10. Ви додали хук WorktreeCreate, щоб виділяти порти. Тепер у нових worktree немає .env, хоча .worktreeinclude на місці. Чому?
Так. Копіюйте файл у самому хуку. Заодно хук має сам видаляти свою гілку в парному WorktreeRemove: Claude Code гілки хука не чіпає.
Останнім рядком хук друкує шлях до worktree, а .worktreeinclude копіює якраз gitignored-файли — але лише з git-логікою Claude Code, яку хук вимикає.
11. Треба прогнати claude -p по 40 стороннім репозиторіям з GitHub. Що обов'язково?
Так. -p не питає про довіру, тож чужа конфігурація виконується на вашій машині. --bare бере лише те, що передано флагами.
Worktree і режим дозволів не зупиняють чужих хуків: вони відпрацьовують ще до першої відповіді моделі, а ізоляція worktree — захист від помилки агента, не sandbox. Від цього захищає --bare (або --setting-sources user, урок 3.4).

Домашнє завданняДві задачі з AI-перевіркою

1. Два агенти у двох worktree на вашому репозиторії

Оберіть дві незалежні задачі, проженіть їх паралельно і послідовно (Claude Code -w, codex exec --worktree або agent -w), підготуйте середовище worktree, злийте результат і приберіть. Звіт — заміри, команди, проблеми середовища, злиття і прибирання.

2. Fan-out-скрипт з чесним підсумком

Напишіть скрипт над headless-агентом для N однотипних входів: ліміт паралельності, перевірка результату кодом, повтор через --resume, розрізнення причин збою, ліміт витрат. Здайте код, вивід реального прогону і розрахунок найгіршої вартості.
