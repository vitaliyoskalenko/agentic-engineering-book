Model Context Protocol: tools, resources, prompts, транспорти

Розбираємо MCP за поточною ревізією 2026-07-28, яка прибрала handshake і сесії: хто такі host, client і server, чим tool відрізняється від resource і prompt, як працюють stdio, Streamable HTTP та OAuth. Пишемо сервер на 46 рядків і читаємо сирий JSON-RPC від власного клієнта, Claude Code та MCP Inspector.

01

Навіщо протоколM + N замість M × N

Без спільного протоколу кожен AI-застосунок пише свій адаптер до кожної системи: 3 хости × 10 інтеграцій = 30 адаптерів з різними схемами, авторизацією й помилками. MCP робить це M + N: сервер Lectern пишеться один раз і працює в Claude Code, Codex, Cursor і через MCP connector у Claude API. Anthropic відкрила протокол 25.11.2024 (урок 0.1); відтоді специфікація має п'ять ревізій, і онлайн-туторіали описують різні з них.

Поточна (current) версія специфікації — 2026-07-28: реліз у репозиторії специфікації опубліковано 28.07.2026, кандидат (RC) — 29.05.2026. Python SDK mcp 2.0.0 вийшов того ж дня; ми працюємо з mcp 2.3.0 (02.10.2026). Claude Code 2.1.300 у наших прогонах говорив саме 2026-07-28.

Продуктове мислення

Більшість статей і відповідей моделей про MCP описують «legacy-еру»: initialize, Mcp-Session-Id, sampling. Такий сервер і далі працює з клієнтами, що знають обидві ери, але нову інтеграцію проєктуйте під 2026-07-28: стан — явні ідентифікатори в аргументах, будь-який екземпляр обробляє будь-який запит, і віддалений сервер масштабується звичайним балансувальником без sticky-сесій.

02

АрхітектураHost, client, server і що кожен бачить

РольВідповідає заЧого не робить
HostМодель, розмова, дозволи, згода користувача; вирішує, що показати моделі й чи виконати викликДоменної логіки інтеграцій
ClientОдне з'єднання з одним сервером: версія й можливості в кожному запиті, підпискиНе змішує сервери: межа безпеки — між клієнтами
ServerTools, resources, prompts над своєю системоюНе читає всю розмову й «не бачить» інших серверів (принцип специфікації)

Повідомлення — JSON-RPC 2.0: request (з id, який не може бути null), result або error у відповідь, notification без id і без відповіді. Ревізія 2026-07-28 додала три обов'язкові речі: кожен результат має resultType ("complete" або "input_required"), кожен запит несе в params._meta версію протоколу і можливості клієнта, а сервер не має права виводити щось із попередніх запитів того самого з'єднання.

Узгодження можливостей: тоді й тепер

legacy · до 2025-11-25

  • перший запит — initialize з версією і capabilities обох сторін;
  • далі notifications/initialized, і з'єднання стає сесією;
  • на HTTP сервер видає Mcp-Session-Id, тож запити мусять іти на той самий екземпляр.

modern · 2026-07-28

  • handshake немає: версія, clientCapabilities і clientInfo їдуть у _meta кожного запиту;
  • server/discover (сервер зобов'язаний його мати) одним запитом повертає версії, capabilities та instructions;
  • непідтримана версія → -32022 UnsupportedProtocolVersion зі списком supported, клієнт повторює запит.

Клієнт, що знає обидві ери, на stdio спершу шле server/discover: DiscoverResult або сучасна помилка означає modern-сервер, інша помилка чи тайм-аут — legacy, і тоді initialize.

Пастка

Legacy-клієнт із сервером, що вміє лише 2026-07-28, не працює взагалі: механізму «перейти вперед» у нього немає. Поки користувачі сидять на різних версіях клієнтів, тримайте сервер dual-era; Python SDK 2.x так і працює за замовчуванням (видно нижче на дроті).

03

Примітиви сервераTool, resource, prompt: хто вирішує

Примітиви відрізняються не форматом даних, а тим, хто вирішує, коли їх використати; від цього залежить, де примітив з'явиться в інтерфейсі хоста.

ПримітивХто вирішуєМетодиДе це в Claude Code
ToolМодель (model-controlled), людина підтверджує викликtools/list, tools/callІнструмент mcp__сервер__інструмент, правила дозволів
ResourceЗастосунок (application-driven): host або користувач обирає, що додати в контекстresources/list, resources/templates/list, resources/read@сервер:uri у промпті; модель — через ListMcpResourcesTool / ReadMcpResourceTool
PromptКористувач (user-controlled): явно обирає шаблонprompts/list, prompts/getКоманда /mcp__сервер__промпт (у меню — /сервер:промпт (MCP))

Tool

Визначення: name (1–128 символів, A-Z a-z 0-9 _ - .), description, inputSchema (JSON Schema, за замовчуванням діалект 2020-12, не може бути null), необов'язкові outputSchema, title, annotations. Якщо є outputSchema, сервер зобов'язаний повертати structuredContent, що їй відповідає, а для сумісності має дублювати його серіалізованим JSON у текстовому блоці content. Це дані для коду клієнта; зі «structured outputs» моделі (урок 2.1) вони не пов'язані.

Помилки бувають двох видів, і модель бачить їх по-різному:

  • протокольна (JSON-RPC error): невідомий інструмент, запит не за схемою, збій сервера. Клієнт може показати її моделі, але виправити таке вона здебільшого не здатна;
  • помилка виконання (result з isError: true): невалідна дата, відмова API, бізнес-правило. Клієнт має віддати її моделі, щоб вона виправила аргументи. З 2025-11-25 помилки валідації вхідних даних належать саме сюди.

Анотації (readOnlyHint, destructiveHint тощо) — підказки, а не гарантії: специфікація вимагає вважати їх недовіреними, якщо сервер не довірений. Дизайн інструментів і їхня безпека — урок 7.4.

Resource

Дані, ідентифіковані URI: file://, git://, https:// (лише якщо клієнт може завантажити його сам, без сервера) або власна схема, як lecture://. Шаблон (uriTemplate за RFC 6570, наприклад lecture://{lecture_id}) описує цілий простір ресурсів, яких немає в resources/list. Неіснуючий ресурс — помилка -32602 (раніше -32002), а не порожній contents: порожній масив неможливо відрізнити від порожнього файлу. Анотації audience, priority (0–1) і lastModified підказують хосту, що включати в контекст першим.

Підписки на зміни в 2026-07-28 переїхали з resources/subscribe у загальний subscriptions/listen: один довгий запит, у якому клієнт вмикає toolsListChanged, promptsListChanged, resourcesListChanged і resourceSubscriptions для конкретних URI.

Prompt

Шаблон повідомлень для перевіреного сценарію, який користувач запускає однією командою: prompts/get повертає messages (role user/assistant; текст, зображення, аудіо, resource link або вбудований ресурс). Аргументи за схемою — лише рядки ({[key]: string}): у нашому прогоні Claude Code передав "n": "2", і перетворення в число зробив SDK сервера.

Правило вибору

Модель має сама вирішити, коли це робити → tool. Це дані, які користувач чи застосунок прикріплює до контексту → resource. Це сценарій, який людина запускає свідомо → prompt. Якщо ж модель має сама дістати дані в будь-якому клієнті, дайте ще й tool: MCP connector у Claude API підтримує лише інструменти.

04

Можливості клієнта й утилітиElicitation, MRTR і що застаріло

Іноді серверу для завершення запиту потрібен клієнт: підтвердження користувача, токен до сторонньої системи, відповідь моделі. До 2025-11-25 сервер надсилав клієнту власний JSON-RPC-запит (elicitation/create, sampling/createMessage, roots/list). У 2026-07-28 сервер не ініціює запитів, і їх замінив патерн Multi Round-Trip Requests (MRTR):

  1. Клієнт надсилає tools/call, resources/read або prompts/get (лише ці три методи).
  2. Сервер відповідає resultType: "input_required": inputRequests — мапа запитів до клієнта, і непрозорий requestState.
  3. Клієнт збирає відповіді й повторює початковий запит з новим id, додавши inputResponses і той самий requestState.
  4. Сервер відновлює стан із requestState і повертає результат. Ні спільного сховища, ні sticky-сесії не потрібно.

requestState проходить через клієнта, тож специфікація вважає його контрольованим атакувальником: якщо від нього залежать права чи бізнес-логіка — HMAC або AEAD, прив'язка до користувача й запиту, короткий TTL.

Застаріле живе щонайменше 12 місяців: sampling, roots, logging і Dynamic Client Registration можна прибрати не раніше першої ревізії від 28.07.2027. Claude Code 2.1.300 досі шле в кожному запиті "roots": {"listChanged": true} поряд з "elicitation": {"form": {}, "url": {}}.

Чому їх прибирають

Обґрунтування SEP-2577: мало хто з клієнтів це реалізував, а складність висока. Sampling вимагає людини в циклі, вибору моделі й захисту від зловживань; roots мають розмиту семантику і дублюють параметри інструментів; logging дублює stderr і OpenTelemetry. Висновок для дизайну: не будуйте новий сервер на sampling. Якщо серверу потрібна LLM, він кличе API провайдера сам і сам контролює модель, бюджет і логи.

05

Транспорти й автентифікаціяstdio, Streamable HTTP, OAuth 2.1

Транспорт визначає лише доставку: кадрування, метадані, скасування. Семантика повідомлень однакова скрізь.

stdioStreamable HTTP
Хто запускає серверКлієнт, як підпроцесСервер працює сам, обслуговує багатьох клієнтів
КадруванняОдин JSON-RPC на рядок, без вкладених \n; stdout — лише MCP-повідомлення, логи — у stderrКожне повідомлення — окремий POST на один endpoint (/mcp); відповідь — JSON або SSE-потік саме цього запиту
МетаданіЛише в _meta тіла_meta + дзеркальні заголовки MCP-Protocol-Version, Mcp-Method, Mcp-Name; розбіжність з тілом → 400 і -32020 HeaderMismatch
Скасуванняnotifications/cancelledКлієнт закриває потік відповіді
СекретиЗ оточення процесу (env у конфігурації)OAuth 2.1, Authorization: Bearer у кожному запиті, ніколи в query string
Типовий випадокЛокальні файли, CLI-утиліти, БД розробникаSaaS: GitHub, Sentry, Linear; командний сервер Lectern

Заголовки Mcp-Method і Mcp-Name (нові в 2026-07-28) дають балансувальникам і WAF маршрутизувати tools/call execute_sql без розбору JSON; звірка з тілом не дає проксі й серверу спиратися на різні джерела правди.

Локальний HTTP-сервер

Специфікація вимагає перевіряти заголовок Origin (невалідний → 403) і радить слухати лише 127.0.0.1, а не 0.0.0.0. Без цього будь-який сайт у браузері розробника через DNS rebinding може звернутися до MCP-сервера на його машині.

Що прибрано і що застаріло

  • HTTP+SSE (2024-11-05: GET-потік і окремий POST-endpoint) застарів ще в 2025-03-26. Claude Code позначає --transport sse як deprecated, а з v2.1.265 --transport http сам переходить на SSE, якщо сервер не приймає HTTP.
  • Mcp-Session-Id (2025-03-26…2025-11-25) прибрано разом із GET-потоком і відновленням через Last-Event-ID. Сервер лише нової ревізії ігнорує цей заголовок, а на GET і DELETE відповідає 405. Обірваний потік означає, що запит втрачено, і клієнт повторює його з новим id. Стан між викликами тепер передають явні дескриптори в аргументах, наприклад basket_id, які сервер щоразу перевіряє на права.

Автентифікація віддаленого сервера

Авторизація в MCP необов'язкова і стосується лише HTTP; stdio-сервер не повинен її реалізовувати й бере ключі з оточення. Якщо ж сервер захищений:

  1. Запит без токена → 401 з WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource", scope="…".
  2. Клієнт читає Protected Resource Metadata (RFC 9728), знаходить authorization server і його метадані (RFC 8414 або OpenID Connect Discovery).
  3. Реєстрація клієнта: Client ID Metadata Document (рекомендовано; client_id — HTTPS-URL), заздалегідь виданий client_id або Dynamic Client Registration, яку 2026-07-28 оголосила застарілою.
  4. OAuth 2.1 з PKCE; параметр resource (RFC 8707) з канонічним URI сервера обов'язковий і в authorization-, і в token-запиті. Відповідь сервера авторизації клієнт перевіряє за iss (RFC 9207).
  5. Сервер приймає лише токени, видані для нього (перевірка audience), і не передає їх далі. Брак прав → 403 insufficient_scope з потрібними scope, і клієнт робить step-up.

Атаки, від яких захищають RFC 8707 і заборона token passthrough, — урок 7.4.

06

Протокол на дроті46 рядків сервера і сирий JSON-RPC

Щоб бачити протокол, а не SDK, пишемо мінімальний сервер Lectern з одним інструментом, одним шаблоном ресурсу й одним промптом, а потім говоримо з ним голим JSON через stdin/stdout. Python SDK 2.x перейменував FastMCP на MCPServer: імпорт mcp.server.fastmcp у 2.x падає з ModuleNotFoundError, у якому є посилання на гайд міграції. Повноцінний сервер Lectern з пошуком збираємо в уроці 7.3.

# lectern_mcp.py — мінімальний stdio MCP-сервер: 1 tool, 1 resource, 1 prompt
import sys
from pydantic import BaseModel
from mcp.server.mcpserver import MCPServer
from mcp.server.mcpserver.exceptions import ResourceNotFoundError

LECTURES = {
    "l01": "Сократ нічого не писав. Його вчення відоме з діалогів Платона "
           "і спогадів Ксенофонта.",
}

mcp = MCPServer("lectern", version="0.1", instructions="Матеріали курсу Lectern: лекції й перевірка цитат.")


class QuoteCheck(BaseModel):
    found: bool
    lecture_id: str
    position: int | None


@mcp.tool()
def check_quote(lecture_id: str, quote: str) -> QuoteCheck:
    """Перевіряє, чи цитата дослівно є в тексті лекції. Повертає позицію або found=false."""
    text = LECTURES.get(lecture_id, "")
    pos = text.find(quote)
    print(f"check_quote {lecture_id!r} -> {pos}", file=sys.stderr)  # stdout зайнятий протоколом
    return QuoteCheck(found=pos >= 0, lecture_id=lecture_id, position=pos if pos >= 0 else None)


@mcp.resource("lecture://{lecture_id}", mime_type="text/plain")
def lecture(lecture_id: str) -> str:
    """Повний текст лекції за її id."""
    if lecture_id not in LECTURES:
        raise ResourceNotFoundError(f"немає лекції {lecture_id}")  # → -32602
    return LECTURES[lecture_id]


@mcp.prompt()
def make_quiz(lecture_id: str, n: int = 3) -> str:
    """Шаблон: n питань квізу за лекцією, кожне з дослівною цитатою."""
    return (f"Склади {n} питань з 4 варіантами за лекцією lecture://{lecture_id}. "
            "До кожного додай дослівну цитату і перевір її інструментом check_quote.")


if __name__ == "__main__":
    mcp.run()  # transport="stdio" за замовчуванням

Квіз10 питань

10 питань
1. Автори мають прикріплювати текст лекції до розмови в Claude Code через @, а агент на Claude API з MCP connector має сам читати лекції під час генерації. Що виставити?
Так. Resource — шлях «вирішує користувач чи застосунок», tool — «вирішує модель». MCP connector підтримує лише tools, тож без інструмента агент на API лекції не дістане.
ReadMcpResourceTool є лише в Claude Code, а connector у Claude API підтримує тільки tools. Ресурси не застаріли: застаріли roots, sampling і logging. Потрібні обидва примітиви.
2. Ваш сервер підтримує лише 2026-07-28. Користувач підключає клієнт, що знає тільки 2025-11-25. Що станеться?
Так. У матриці сумісності специфікації пара Legacy-клієнт / Modern-сервер позначена «Fails»: механізму переходу вперед у старого клієнта немає.
Повторити запит з новою версією вміє лише клієнт, що знає нову ревізію. Dual-era — право сервера (MAY), а не обов'язок. Legacy-клієнт з modern-only сервером не працює.
3. Інструмент book_flight отримав дату в минулому. Як повідомити про це?
Так. Помилки валідації й бізнес-логіки — це помилки виконання, і клієнт має показати їх моделі, щоб вона виправила аргументи.
Протокольні помилки призначені для невідомого інструмента, малформованого запиту чи збою сервера; модель здебільшого не може їх виправити. Автоматичного повтору на -32603 протокол не передбачає.
4. Віддалений сервер за балансувальником має 4 екземпляри. Інструментам кошика потрібен стан між викликами. Як це робиться в 2026-07-28?
Так. Протокольних сесій більше немає; стан адресується явним непрозорим дескриптором, а сервер щоразу перевіряє права на нього.
Mcp-Session-Id прибрано з ревізії 2026-07-28, а специфікація прямо забороняє вважати з'єднання розмовою чи сесією.
5. Посеред tools/call серверу потрібен GitHub-токен користувача для стороннього API. Як отримати?
Так. Секрети й облікові дані специфікація дозволяє збирати лише URL-режимом; сервер зберігає сторонній токен сам, прив'язавши його до користувача.
Form-режим для секретів заборонено, а requestState проходить через клієнта. Пересилати токен клієнта в інший сервіс — token passthrough, теж заборонено (урок 7.4).
6. CI запускає claude -p у склонованому репозиторії з PR, де є .mcp.json із сервером. Що станеться і що робити?
Так. Запит на схвалення показує лише інтерактивний Claude Code; у -p, SDK і хмарі project-сервери вантажаться одразу.
Схвалення — захист інтерактивної сесії, а не CI. Пріоритет областей стосується лише однакових імен, а не того, чи стартує сервер.
7. Промпт сервера має аргумент n: int. Що надходить на сервер у prompts/get після команди /mcp__lectern__make_quiz l01 2?
Так. У нашому лозі було "arguments":{"lecture_id":"l01","n":"2"}; число з рядка зробив SDK сервера.
У промптів немає inputSchema, лише список аргументів, і схема протоколу задає їх як {[key]: string}. Claude Code викликав prompts/get з обома аргументами.
8. Що правда про sampling у ревізії 2026-07-28?
Так. Sampling позначено Deprecated (SEP-2577): він лишається щонайменше до першої ревізії від 28.07.2027, але приходить через MRTR, а не окремим запитом сервера.
Застаріле не означає видалене: впродовж вікна застарівання функція працює. І обов'язковим sampling ніколи не був, це можливість, яку клієнт оголошує.
9. Балансувальник має відправляти tools/call execute_sql в окремий пул, не розбираючи JSON. Що для цього дає Streamable HTTP у 2026-07-28?
Так. Стандартні заголовки дзеркалять тіло для проміжних вузлів; сервер звіряє їх, щоб проксі й сервер не спиралися на різні джерела правди.
Сесії прибрано, а заголовки не заборонені: їх додано саме для маршрутизації. Джерелом правди лишається тіло.
10. На неіснуючу лекцію SDK повернув -32603 «Error creating resource from template». Чим це погано?
Так. -32603 означає внутрішню помилку. Специфікація вимагає -32602 для неіснуючого ресурсу і забороняє порожній contents.
Порожній масив неоднозначний: ресурс може існувати й бути порожнім. -32603 залишено для внутрішніх збоїв; not found у 2026-07-28 — -32602.

Домашнє завданняДві задачі з AI-перевіркою

1. MCP-поверхня для вашої системи

Візьміть систему зі своєї роботи і спроєктуйте для неї MCP-сервер: 6–10 можливостей, кожна з примітивом і обґрунтуванням «хто вирішує», схеми і помилки двох ключових інструментів, транспорт і автентифікація, стан без сесій, область підключення в Claude Code.

2. Розбір логу на дроті

У завданні є лог обміну клієнта з сервером, у якому сім порушень специфікації 2026-07-28. Знайдіть їх, для кожного назвіть правило і запропонуйте виправлення.
