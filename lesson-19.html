Пастка хмари

У хмарі немає вашого ~/.claude/CLAUDE.md, user-skills, MCP-серверів, доданих без --scope project, і плагінів — навіть тих, що репозиторій вмикає в enabledPlugins. Агент, який локально знав ваші конвенції, тут їх не знає. Що має працювати в хмарі, комітьте; ключі — як network secrets середовища: його змінні бачить кожен користувач середовища.

Хмарні сесії, Desktop, Remote Control і Slack потребують входу через claude.ai. З ключем Console API чи на Bedrock, Agent Platform, Foundry лишаються CLI, VS Code і JetBrains.

02

Переходи між поверхнямиЩо переїжджає, а що ні

Три різні операції: та сама сесія в іншому вікні, копія (далі робота розходиться) і нова сесія з підсумком (деталі контексту втрачено).

Термінал → хмараclaude --cloud "задача"нова сесія з GitHub-remote поточної гілки: незапушені коміти не потраплять
Desktop → хмараOpen in → Cloudрозмова як підсумок; не для SSH і WSL
Хмара → терміналclaude --teleport [id], /teleportкопія розмови + гілка; потрібні чистий git і той самий репозиторій; назад не синхронізується
Локальна → телефон, браузер/remote-control, claude remote-controlта сама сесія, виконання на вашій машині; машина не спить; транскрипт зберігається на серверах Anthropic; недоступно з ключем API, через gateway і за ZDR

Із терміналу перенесення однобічне: хмарну сесію можна стягнути --teleport, а термінальну в хмару не відправиш. Документований патерн: спланувати локально в plan mode → закомітити й запушити план → claude --cloud "Execute the plan in docs/plan.md" → забрати результат PR-ом або телепортом.

Моделі в Claude CodeАліаси, opusplan, effort, fallback

Ціни й вибір моделі — урок 1.5, effort — 1.4. Тут лише важелі Claude Code. Значення для /model, --model, ANTHROPIC_MODEL і model у settings:

ЗначенняЩо вибирає (Anthropic API, 15.10.2026)Коли
defaultскидає вибір до типової моделі акаунта: Opus 5.5 на Pro, Max, Team, Enterprise і APIприбрати застарілий override
opus · sonnet · haikuOpus 5.5 · Sonnet 5.5 · Haiku 5.5, усі з 1M-вікном без суфікса [1m]; на Bedrock і Agent Platform sonnet і haiku — ще 4.5щоденна робота; аліас сам переїде на нову версію

Пріоритет джерел — урок 1.5. Неочевидне:

  • /model зберігає вибір у ~/.claude/settings.json (Enter), клавіша s — лише ця сесія. --model і ANTHROPIC_MODEL діють на один запуск: два термінали на різних моделях — це два --model.
  • model із project- чи managed-налаштувань повертається на кожному запуску; заголовок сесії називає файл. Перемикання моделі доходить і до субагентів, що її успадковують.
  • Effort: /effort, --effort, CLAUDE_CODE_EFFORT_LEVEL; на моделях 5.5 типово medium, на інших — high. Рівень зберігається для кожної моделі окремо, max — лише на сесію; ultrathink у промпті поглиблює один хід.
  • /fast — лише Opus 5.5, 5 і 4.8 (з іншої моделі перемкне на Opus); на підписках — тільки з usage credits.

Fallback у Claude Code — два різні механізми:

Як увімкнути--fallback-model sonnet,haiku або "fallbackModel": [...]; до 3 моделейпрацює сам на Fable, Opus 5.5, Sonnet 5.5, Opus 5; switchModelsOnFlag: false — питати

05

Режими дозволівШість режимів як робочий процес

Режим задає, що агент робить без запиту. Правила allow/ask/deny (урок 2.3) лягають зверху, і deny блокує в будь-якому режимі, навіть у bypass.

Режим (config)Без запитуДля чого
Manual (default)лише читаннянезнайомий код, чутливі зміни, рев'ю кожної дії
acceptEditsчитання, правки в робочих теках, mkdir, touch, rm, rmdir, mv, cp, sed у їхніх межахітерації з рев'ю через git diff після; решта команд питає
planчитання; команди дослідження — через класифікатор, якщо auto доступнийрозвідати й узгодити план до першої правки
autoусе; дії поза читанням і правками в робочій теці перевіряє класифікатордовгі задачі в напрямку, якому ви довіряєте
dontAskлише allow-правила і read-only; усе, що мало б спитати, — відмоваCI і скрипти з точним allowlist; лише CLI
bypassPermissionsусе, крім дій, які не пропускає жоден режимлише контейнер або VM без доступу до хоста

Shift+Tab у CLI: auto → Manual → acceptEdits → plan → [bypass, якщо сесію запущено з ним] → auto. dontAsk — лише прапорцем; один промпт у plan mode — префікс /plan.

Звідки береться стартовий режим

  1. Прапорець --permission-mode (або --dangerously-skip-permissions).
  2. permissions.defaultMode за пріоритетом налаштувань (managed > local > project > user). Але auto і bypassPermissions з .claude/settings.json і settings.local.json не діють: клонований репозиторій не вмикає вам автономію.
  3. Вбудований: auto в інтерактивному терміналі й VS Code з v2.1.283; Manual у -p і Agent SDK (у сесіях, що отримують feature flags) і там, де auto недоступний.

Перевірка на -p:

zsh — ~/scratch/defaultmode
$ for m in acceptEdits plan auto bypassPermissions; do
    rm -rf r && mkdir -p r/.claude && cd r && git init -q
    printf '{"permissions":{"defaultMode":"%s"}}\n' $m > .claude/settings.json
    claude -p "Відповідай одним словом: ок" --model haiku --tools "" --setting-sources project --strict-mcp-config \
      --no-session-persistence --output-format stream-json --verbose < /dev/null 2>/dev/null \
      | jq -r 'select(.type=="system" and .subtype=="init") | "project defaultMode=\"'$m'\" → permissionMode=\(.permissionMode)"'
    cd ..; done

project defaultMode="plan" → permissionMode=plan
project defaultMode="auto" → permissionMode=default
project defaultMode="bypassPermissions" → permissionMode=default

Дві осі: sandbox (read-only | workspace-write | danger-full-access) і схвалення (--ask-for-approval on-request | never). Пресети /permissions: Auto і Read Only; у застосунку й IDE — Ask for approval, Approve for me, Full access. Тека під git стартує в Auto (workspace-write + on-request), інша — read-only; мережа вимкнена.

  • Аналог класифікатора — approvals_reviewer = "auto_review": «a reviewer swap, not a permission grant», тобто він вирішує лише те, що й так дійшло б до вас.
  • --full-auto прибрано: замість нього --sandbox workspace-write або --approve-for-me.
  • У workspace-write лише для читання лишаються .git, .agents, .codex, .aws, рекурсивно.

Auto mode і захищені шляхиЩо перевіряє класифікатор і чого не пропускає ніхто

Кожна дія в auto mode проходить фіксований порядок, спрацьовує перший відповідний крок:

  1. Правила allow / ask / deny вирішують одразу. Але запис у protected path іде до класифікатора навіть з allow, а rm по critical path не схвалює жодне правило.
  2. Читання й правки в робочій теці схвалено автоматично (крім protected paths).
  3. Решта — класифікатор: окрема модель, типово Sonnet 5, а не ваша /model. Він бачить ваші повідомлення, виклики інструментів і CLAUDE.md, але не бачить результатів інструментів, тож ін'єкція у файлі не переконає його напряму.
  4. Блок: Claude отримує причину. Після 3 блоків поспіль або 20 за сесію повертаються звичайні запити; у -p дія просто не виконується.
Типово блокується (вибірка)Що робити
curl … | bash, --insecure, запуск іншого агента без sandboxнічого: це і є мета
force push, git reset --hard, git clean -fdруками або явним дозволом у повідомленні
деплой і міграції в прод, terraform destroy, DNS, секретиописати інфраструктуру в autoMode.environment
rm -rf "$VAR" зі значенням, якого класифікатор не бачивназвати точний шлях
  • Широкі allow (Bash(*), Bash(python*), allow на Agent) на час auto вимикаються, вузькі на кшталт Bash(npm test) лишаються. Повний список правил — claude auto-mode defaults.
  • Межі з розмови («не пуш до рев'ю») класифікатор перечитує з транскрипту; компакція може їх прибрати. Гарантію дає лише правило в settings.
  • Ціна: на Enterprise і з ключем API виклики класифікатора рахуються в токени, переважно за shell і мережу. Виміряні частки пропусків — урок 3.4.

Protected paths і critical paths

Protected paths — файли, запис у які змінює поведінку git, shell, інструментів чи самого агента: .git, .claude (крім worktrees, планів і auto memory), .vscode, .husky, .devcontainer, .zshrc, .envrc, .npmrc, .pre-commit-config.yaml, .mcp.json та інші. Allow на кшталт Edit(.claude/**) їх не відкриває: перевірка йде раніше за правила.

РежимЗапис у protected pathrm по critical path
Manual, acceptEditsзапитзапит; allow і hook «allow» не діють
planкласифікатор або запитзапит
autoкласифікаторзапит із 2-хвилинним таймером у терміналі; у -p, SDK, VS Code, Desktop — відмова
dontAskвідмовавідмова
bypassPermissionsдозволенозапит

Critical paths — корінь ФС, теки верхнього рівня, домашня тека, робоча тека та її батьки, а також rm -rf "$DIR"/*, що за порожньої змінної стає видаленням від кореня. Перевірка зазирає в $(…) і bash -c, але стосується лише rm/rmdir (і Remove-Item): це запобіжник від помилки моделі, а не від атаки. find -delete чи Python-скрипт ловлять уже класифікатор або sandbox.

Пастка bypass

bypassPermissions вимикає і запити, і класифікатор: «offers no protection against prompt injection». Під root чи sudo він не стартує поза розпізнаним sandbox, а хмарні сесії ігнорують його з settings. Для «менше запитів» документація радить auto.

ПрактикаПеревірте терміни

11

Квіз11 питань

11 питань
1. Ви закомітили виправлення фікстури і одразу запустили claude --cloud "Fix the flaky test". Хмарна сесія падає на старій фікстурі. Чому?
Так. --cloud створює нову сесію з клоном remote, а не з вашої локальної копії. Спершу git push.
--cloud щоразу створює нову сесію і клонує GitHub-remote саме вашої поточної гілки. Проблема не в гілці: локальний незапушений коміт туди просто не потрапляє.
2. Задача потребує локальної Postgres і внутрішнього MCP-сервера. Ви йдете на дві години й хочете відповідати на питання агента з телефону. Що обрати?
Так. Виконання лишається на вашій машині разом з БД і MCP, телефон — лише вікно в сесію.
Хмарна VM не бачить вашої Postgres і user-MCP, а телепорт тягне сесію з хмари в термінал, не навпаки.
3. CI запускає claude -p "оновити CHANGELOG" у репозиторії, де .claude/settings.json містить "defaultMode": "bypassPermissions". Що станеться?
Так. bypassPermissions і auto з project- і local-налаштувань не діють; у -p вбудований default — Manual, і кожен запит стає відмовою.
Bypass із project-налаштувань мовчки ігнорується, і заміни на dontAsk немає: ми перевірили — permissionMode=default. Інші значення defaultMode з проєкту (acceptEdits, plan) при цьому діють.
4. -p у dontAsk з allow на Bash(.venv/bin/python -m pytest *). Агент спробував heredoc-правку, отримав відмову і написав «Bash заборонено, тести не запускав». Найкраще виправлення?
Так. Модель узагальнила відмову про одну команду на весь Bash. Одне речення в промпті виправило прогін: Edit, Edit, pytest, 0 відмов.
Режим і правила були правильні; модель прочитала відмову ширше. Bash(*) розширює права, хоча бракувало знання, а в acceptEdits у -p запит на pytest — та сама відмова (прогін: «This command requires approval»).
5. Нічний скрипт у acceptEdits перевіряє лише is_error і щоранку звітує «успіх», хоча тести агент не запускав. Що змінити?
Так. Відмова не є помилкою прогону: в усіх наших прогонах is_error був false. Список відмов — у permission_denials.
У -p нікому відповісти на запит: Manual лише додасть відмов. Кількість ходів нічого не доводить; що саме відхилено, видно лише в permission_denials.
6. Хочете, щоб план будувала сильна модель, а правки робила дешевша, без ручного /model. Що задати?
Так. Модель перемикає режим: ми бачили Opus у modelUsage для plan і Sonnet — для Manual на тому самому питанні.
Fallback-ланцюжок спрацьовує лише на перевантаження чи недоступність моделі, а best — одна модель (Fable, де вона доступна, інакше Opus) на всю сесію.
7. Після запиту про аналіз експлойта сесія перейшла з Opus 5.5 на Opus 4.8 і там лишилась. Що сталося?
Так. Позначені як кібербезпека запити Opus 5.5 перезапускаються на Opus 4.8, і сесія лишається там до /model.
Ланцюжок fallbackModel діє один хід і лише на недоступність моделі, а availableModels не залежить від змісту запиту. Тут причина — тема запиту, тож сесія лишається на Opus 4.8 до /model.
8. Auto mode, у вас allow Edit(**). Агент хоче змінити .pre-commit-config.yaml. Що станеться?
Так. Protected paths перевіряються раніше за allow-правила; в auto вони йдуть до класифікатора, у dontAsk — відмова, і лише bypass пропускає.
Pre-commit-конфіг виконується при кожному коміті, тому він у protected paths, і Edit(**) його не відкриває. Але відмова без варіантів — це dontAsk; в auto запис іде до класифікатора.
9. На початку сесії ви сказали «не пуш до мого рев'ю». Через три години, після автокомпакції, агент в auto mode запушив гілку. Як запобігти цьому надійно?
Так. Межі з розмови класифікатор перечитує з транскрипту, і компакція може їх прибрати. Правило в settings переживе будь-яку компакцію, а ask спрацює навіть в auto.
Межа з розмови не зберігається як правило, а компакція прибрала повідомлення. Рядок у CLAUDE.md класифікатор бачить, але це однаково прохання, а не правило, і effort пам'яті не додає. Гарантію дає лише правило в settings.
10. Команда працює через Amazon Bedrock і хоче Desktop, хмарні сесії та Remote Control. Що реально?
Так. Хмарні сесії, Remote Control і звичайний Desktop вимагають входу через claude.ai; CLI та IDE-розширення працюють з будь-яким провайдером.
Змінна провайдера не дає входу через claude.ai, а саме він потрібен хмарним сесіям і Remote Control. IDE-розширення при цьому працюють і на Bedrock.
11. Перевіряєте бінарний файл: gpg --verify пише «Good signature» і «WARNING: This key is not certified». Що ще потрібно, щоб довіряти файлу?
Так. Підпис доводить цілісність маніфесту, відбиток — автентичність ключа, а збіг SHA-256 — що ваш файл є в маніфесті.
«Good signature» каже лише, що маніфест підписано цим ключем, а WARNING очікуваний для свіжоімпортованого ключа і підписувати його не вимагає. Ланцюжок довіри: відбиток ключа → підпис маніфесту → SHA-256 файла.
