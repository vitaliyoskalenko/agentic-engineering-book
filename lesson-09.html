Tool use / function calling: як LLM діє у світі; структурований вивід

Модель нічого не виконує сама: вона повертає запит на виклик функції з аргументами за JSON-схемою, а виконує його ваш код або сервер Anthropic. 01

КонтрактМодель просить, ваш код виконує

Модель не виконує нічого: «викликати функцію» для неї означає згенерувати назву інструмента й аргументи в JSON. Виконує (або відмовляє) ваш код, результат повертається в розмову, і модель продовжує. Read, Grep і Bash у Claude Code — такі самі інструменти: harness оголошує їх моделі й виконує кожен виклик.

Інструмент потрібенІнструмент зайвий
Дія з побічним ефектом: записати файл, надіслати лист, змінити записВідповідь є в навчанні моделі: переклад, підсумок, загальні знання
Свіжі чи приватні дані: БД, ціни, вміст репозиторіюРазове питання без побічних ефектів
Вихід гарантованої форми, який парсить кодЗайвий round trip довший за саму роботу

Правила, порушення яких API не прощає:

  • Кожен tool_use отримує свій tool_result з тим самим tool_use_id, і результати йдуть одразу наступним user-повідомленням. Інакше 400: tool_use ids were found without tool_result blocks immediately after.
  • Спершу всі tool_result, текст лише після них. Текст перед результатами — теж 400.
  • Відповідь assistant повертається без змін, з усіма блоками. content результату — рядок або блоки text, image, document, search_result.
  • is_error: true — виклик не вдався: модель спробує інакше або пояснить користувачеві; пропущений параметр вона виправляє 2–3 рази, перш ніж здатися.
  • name відповідає ^[a-zA-Z0-9_-]{1,128}$, а input_schema — це JSON Schema.
Пастка безпеки

У tool_result часто потрапляє чужий текст: вебсторінка, лист, файл користувача. Документація радить тримати його саме там, а не в system чи звичайному user-тексті, і вважати недовіреним: це канал непрямої prompt injection (урок 3.4).

02

Хто виконуєClient, Anthropic-schema і server tools

Головна вісь — де виконується код: від неї залежить, що робить ваша програма.

ТипПрикладиХто виконуєЩо робить ваш код
User-defined (client)ваші search_lectures, check_quoteваш кодпише схему, виконує, повертає tool_result
Anthropic-schema (client)bash_20250124, text_editor_20250728, memory_20250818, computer_toolset_20260801, browser_toolset_20260801ваш кодте саме, але схему не пишете: модель тренували на цих сигнатурах, тож викликає їх надійніше за саморобний аналог
Serverweb_search, web_fetch, code_execution, tool_search, advisor, MCP connectorAnthropicвмикає інструмент і читає результат; tool_result не формує

Серверний виклик приходить блоком server_tool_use (id на srvtoolu_), а результат, наприклад web_search_tool_result, лежить одразу за ним у тій самій відповіді: модель шукає, читає і шукає знову всередині одного HTTP-запиту.

  • pause_turn: серверний цикл має ліміт, типово 10 ітерацій на запит. Якщо модель його досягла, відповідь приходить зі stop_reason: "pause_turn", а останній server_tool_use може ще не мати результату. Надішліть її назад як є і з тим самим tools (інакше помилка валідації); обмежте кількість продовжень.
  • Змішаний хід: якщо модель в одній групі паралельних викликів звернулася і до серверного, і до вашого інструмента, відповідь приходить зі stop_reason: "tool_use", а server_tool_use ще без результату. У відповідь шлють лише tool_result, без тексту, і сервер виконає відкладений виклик на початку наступного запиту.
  • Гроші: серверні інструменти мають власну тарифікацію поверх токенів. Web search коштує $10 за 1 000 пошуків, а знайдене рахується як вхідні токени і в наступних ходах. Web fetch окремо не тарифікується. Code execution безкоштовний у парі з web_search_20260209 чи web_fetch_20260209, інакше — 1 550 безкоштовних годин на місяць, далі $0,05 за годину контейнера.
Архітектура

Server tool знімає з вас цикл, але й контроль: виклик не пройде через ваші дозволи, логування чи кеш. Якщо дію треба аудитувати або обмежувати своїми правилами (доступ до БД, гроші, PII), робіть її client tool.

03

Керування викликамиtool_choice, паралельність, ціна в токенах

tool_choiceПоведінкаКоли
{"type": "auto"}модель сама вирішує, кликати чи відповідати текстом; типове значення, коли є toolsмайже завжди
{"type": "any"}мусить викликати хоча б один інструментагентний крок, де текстова відповідь — помилка
{"type": "tool", "name": "…"}мусить викликати саме цейкласичний прийом «інструмент як формат виводу»
{"type": "none"}інструменти заборонені; типове значення без toolsпідсумковий хід без дій
Перевірено · 14.10.2026

Claude Opus 5.5, Sonnet 5.5, Fable 5.1 і Mythos 5.1 не підтримують примусовий виклик: any і tool дають 400 tool_choice: type "tool" and "any" are not supported for this model., навіть на count_tokens. Заміна — auto з явною інструкцією в промпті плюс strict: true для валідних аргументів, а якщо виклик існував лише заради JSON, то structured outputs. auto виклику не гарантує, тому перевіряйте, що він відбувся. На моделях, де примус є, він має ще дві ціни: API «підставляє» початок відповіді, тож тексту перед tool_use не буде, і пропускається thinking. З ручним extended thinking (type: "enabled") any і tool не працюють узагалі.

Зміна tool_choice між запитами інвалідує кеш блоків messages; tools і system лишаються в кеші (урок 1.5).

Паралельні виклики

Моделі Claude 4 і новіші типово можуть повернути кілька блоків tool_use в одній відповіді. Порядок виконання обираєте ви: незалежні читання — конкурентно (asyncio.gather), записи зі спільним станом — послідовно, до першої помилки. Обов'язково:

  1. Усі tool_result — в одному user-повідомленні. Окремі повідомлення API прийме, але модель «вчиться» з історії не паралелити.
  2. Невиконаний виклик теж отримує результат: is_error: true і причину, наприклад "Not executed: the preceding write_file call failed.".
  3. Залежні виклики не мають іти пачкою. Якщо згрупувала — поверніть помилку невиконаного, вона повторить. Профілактика в системному промпті: «Only batch tool calls that are independent of each other.»

Вимкнути паралельність можна прапорцем disable_parallel_tool_use: true усередині tool_choice, а не на верхньому рівні запиту. З auto він означає «щонайбільше один виклик».

Скільки коштує оголосити інструмент

Три шари токенів: схеми в tools, блоки tool_use/tool_result в історії і службовий системний промпт, який API додає, щойно є хоч один інструмент.

Кожен інструмент оплачується в кожному запиті, навіть якщо його не кличуть: десять зайвих схем по 200 токенів в агента на 50 кроків — 100 тис. вхідних токенів на задачу. Prompt caching знімає більшість цієї ціни, лише поки набір інструментів не змінюється. Для великих бібліотек є tool_search і defer_loading: модель бачить схему, лише коли інструмент знайдено.

05

Опис інструментаГоловний важіль якості виклику

Давайте надзвичайно детальні описи. Це найважливіший фактор продуктивності інструментів. […] Пишіть щонайменше 3–4 речення на опис інструмента, більше, якщо він складний.

“Provide extremely detailed descriptions. This is by far the most important factor in tool performance. … Aim for at least 3–4 sentences for each tool description, more if the tool is complex.”

Документація Claude API, «Define tools», перевірено 14.10.2026

Модель бачить лише назву, опис і схему. Опис відповідає на чотири питання: що робить інструмент, коли його кликати і коли ні, що означає кожен параметр, чого він не повертає.

слабкий

{ "name": "search",
  "description": "Search lectures.",
  "input_schema": { "type": "object",
    "properties": {
      "q": { "type": "string" } },
    "required": ["q"] } }
  • «search» конфліктує з будь-яким іншим пошуком;
  • q — фраза чи ключові слова?
  • невідомо, що повернеться і скільки.

Решта правил — зі статті Anthropic «Writing effective tools for agents — with agents» (11.09.2025) і сторінки Define tools:

ПравилоМеханізм
Менше, але змістовніших інструментів«Більше інструментів не завжди дає кращий результат». Замість create_pr, review_pr, merge_pr — один інструмент з параметром action: менше плутанини при виборі.

Виміряно Anthropic

У статті про інструменти Anthropic пише, що Claude Sonnet 3.5 вийшов на рекорд SWE-bench Verified після точних правок в описах інструментів. Модель і задачі ті самі, змінився лише текст, який модель читає про свої інструменти.

06

Структурований вивідЧотири рівні гарантій

Lectern зберігає питання квізу в БД, тож відповідь розбирає код. Між «попросити JSON» і «отримати JSON за схемою» — чотири рівні гарантій:

1
Інструкція в промпті«Відповідай лише JSON такого вигляду». Гарантій немає: можливі пояснення навколо, markdown-обгортка, пропущене поле. Старий прийом «префіл {» мертвий: моделі Claude 4.6 і новіші на префіл останнього assistant-повідомлення відповідають 400.
2
JSON modeТак його називають в інших API: синтаксично валідний JSON без гарантії схеми. OpenAI формулює прямо: «обидва гарантують валідний JSON, але лише Structured Outputs гарантують відповідність схемі». Окремого JSON mode у Claude API немає.
3
Інструмент як формат + strict: trueСхема вашого «запису» — це input_schema, а результат приходить в tool_use.input. Без strict схема лише підказка, тож можливі "2" замість 2 або пропущене поле. Зі strict: true sampling обмежено граматикою схеми.
4
JSON outputs: output_config.format{"type": "json_schema", "schema": {…}}. Відповідь моделі — валідний за схемою JSON у текстовому блоці. Python SDK: client.messages.parse() з Pydantic-моделлю повертає parsed_output. GA; старий параметр output_format застарів і без beta-заголовка дає 400.

Рівні 3 і 4 Anthropic об'єднує під назвою structured outputs і реалізує однаково — constrained decoding. Схему компілюють у граматику, і на кожному кроці модель може обрати лише токен, який її не порушує. Звідси обмеження, яких немає в «справжній» JSON Schema:

Граматика діє лише на прямий вивід: thinking лишається вільним.

Коли схема сильніша за промпт

Вмикайте structured outputs, коли вихід розбирає код, коли викликів тисячі і кожен збій означає повторний запит, і коли поля — це типи й переліки. Промпту досить, коли результат читає людина або форма гнучка. Валідуйте в коді в будь-якому разі. Граматика гарантує форму, але не зміст: що варіантів рівно 4, що correct_index вказує на правильний, що цитата дослівна. Перші два правила схема API навіть не може виразити, бо minItems понад 1 не підтримується.

4. Валідація. Pydantic-модель перевіряє те, чого не бачить граматика. Щоб показати, що вона ловить, ми навмисно зіпсували дві копії справжньої відповіді:

class QuizItem(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)   # "3" не стане 3
    question: str = Field(min_length=15)
    options: list[str] = Field(min_length=4, max_length=4)
    correct_index: int = Field(ge=0, le=3)
    explanation: str
    source_quote: str
    skill: Literal["remember", "understand", "apply", "analyze"]

    @model_validator(mode="after")
    def business_rules(self):
        if len({o.strip().lower() for o in self.options}) != 4:
            raise ValueError("варіанти повторюються")
        if self.source_quote not in LECTURE:
            raise ValueError("source_quote немає в тексті лекції дослівно")
        return self

11 питань
1. Сервіс витягає дані з рахунків через tool_choice: {"type": "tool", "name": "record_invoice"}. Після переходу на Opus 5.5 усі запити падають з 400. Що зробити?
Так. Opus 5.5 відхиляє і any, і tool. Коли примусовий виклик потрібен лише для форми, structured outputs дає ту саму гарантію без інструмента.
any на Opus 5.5 теж дає 400, префіл на моделях 4.6+ — так само, а промпт без схеми — це рівень 1 без гарантій. Правильна заміна — output_config.format (або auto + strict, якщо виклик справді потрібен).
2. Модель повернула три tool_use. Другий (запис файлу) впав, третій ви не запускали, бо він залежав від другого. Як відповісти?
Так. Кожен id отримує результат, усі в одному повідомленні; невиконаний виклик позначено помилкою з поясненням.
Без результату для кожного id API поверне 400, а окремі повідомлення «вчать» модель не паралелити. Усі три результати йдуть одним повідомленням.
3. Запит з web_search повернув stop_reason: "pause_turn". Що далі?
Так. Серверний цикл досяг ліміту ітерацій (типово 10). Відповідь, надіслана назад, дає йому продовжити з того самого місця.
Робота не завершена, а tool_result для серверних інструментів ви не формуєте: їх виконує Anthropic. Відповідь надсилають назад без змін і з тим самим tools, інакше буде помилка валідації.
4. Агент має 40 інструментів, більшість з яких кличе рідко, і рахунок за вхідні токени росте. Що найменше шкодить якості?
Так. Відкладені схеми не потрапляють у контекст, доки інструмент не знайдено, а стабільний набір дозволяє prompt caching спрацювати.
Описи — головний важіль якості виклику, різати їх найдорожче. Паралельність на токени схем не впливає: схеми оплачуються в кожному запиті.
5. У схемі output_config.format стоїть "options": {"type": "array", "minItems": 4}. Що станеться при прямому запиті до API?
Так. Граматика підтримує лише minItems 0 і 1. SDK-хелпери прибирають непідтримане обмеження, дописують його в опис і валідують відповідь.
Непідтримана можливість схеми дає 400 з поясненням, а не тихе ігнорування, і граматика підтримує лише minItems 0 і 1. Кількість варіантів перевіряє ваш код, наприклад Pydantic; SDK-хелпер робить це сам.
6. У нашому прогоні модель передала в Read шлях з дефісами замість слешів. Що завадило б такому виклику нашкодити?
Так. Тип правильний, рядок, тож схема виклику не відхилить. Значення перевіряє лише код, і з добрим текстом помилки модель виправляється з першої спроби.
strict гарантує форму, а не правильне значення, а опис параметра — лише підказка. Тип тут правильний, рядок, тож захист — валідація аргументів там, де їх виконують.
7. Pydantic-модель без strict=True отримує "correct_index": "3". Що буде?
Так, ми це бачили: у lax-режимі помилок було 2 замість 3. Якщо рядок замість числа означає зламаний генератор, вмикайте strict.
Типовий режим Pydantic — lax: рядок "3" перетворюється на int. Помилку дає лише strict=True.
8. Цитата пройшла перевірку quote in lecture, але виявилась шматком речення, бо в схемі стояв maxLength: 60. Що змінити?
Так. Обмеження схеми переважує промпт. Те, що суперечить задачі, має жити в перевірці після генерації.
Промпт уже просив ціле речення, і схема його перемогла. Будь-яка межа довжини знову зріже довге речення. Довжину й межі речень перевіряє код.
9. Агентові потрібен пошук в інтернеті і читання клієнтської БД з персональними даними. Як розподілити?
Так. Server tool знімає з вас цикл, але й контроль. Доступ до персональних даних має проходити через ваш код.
Серверний інструмент, MCP connector теж, виконує Anthropic, і повз ваш код такий виклик не перевірити й не залогувати. Для PII потрібен client tool, а пошук можна віддати серверу.
10. Модель кличе lectern_search_lectures на питання із загальних знань і плутає його з find_lectures. Перший крок?
Так. Два інструменти з описами, що перекриваються, — типова причина неправильного вибору. Опис зі сценарієм «коли не кликати» — найдешевше виправлення.
Класифікатор «загальних» питань — ще один виклик і ще одне джерело помилок, а сильніша модель не виправить двозначних описів. Почніть з набору інструментів і описів.
11. Потрібен JSON за схемою з Cursor CLI у CI. Як?
Так. У Cursor CLI немає прапорця для схеми, тож гарантію дає лише ваша валідація з повтором.
На 14.10.2026 у параметрах Cursor CLI немає ні --json-schema, ні аналога. stream-json — формат подій, а не схема відповіді.
