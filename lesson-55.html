01

Навіщо агентові очіТести зелені, сторінка зламана

У шаблоні квізу Lectern кольори задано токенами, і тест перевіряє контраст кожної пари токенів за WCAG. Додайте один рядок .q legend{color:#1d2133} — колір світлої теми, вписаний напряму. 23 тести структури й контрасту лишаються зеленими: правило обходить токени. У темній темі заголовки питань зникають (контраст 1,1:1), і впіймав це лише візуальний тест: 11 754 із 541 710 пікселів змінилися (2,17%).

Текстова перевірка бачить код, користувач бачить результат каскаду: шрифт, ширину екрана, тему, движок. Тому для UI агентний цикл з уроку 0.1 отримує окремий крок спостереження, а скріншот як спосіб перевірки, згаданий в уроці 3.1, стає частиною harness.

«Краще» тут означає «краще для дій»: посилання ref із дерева дають точний клік без координат. Для оцінки вигляду ця порада не працює. Що ще варто знати про сервер (його встановлення й ціну описів інструментів — 6,5 тис. токенів — розібрано в уроці 7.2):

  • --image-responses allow|omit|only вирішує, чи йдуть картинки клієнтові взагалі; browser_emulate_media перемикає prefers-color-scheme, prefers-reduced-motion, forced-colors.

03

Lectern: квіз як сторінкаlectern render без JavaScript

Lectern · крок 11.4

Нова підкоманда lectern render quiz.json -o quiz.html перетворює канонічний квіз {question, options, answer, quote} на одну сторінку: стилі всередині, жодного скрипта, світла й темна тема. Код — src/lectern/render.py (stdlib) і шаблон quiz_template.html; шлях check не змінюється.

Чому без JavaScript: сторінка має працювати там, де скрипти заблоковані — в iframe під CSP script-src 'self', у поштовому клієнті, у WebView. Тому взаємодію робить CSS:

/* відповідь вибрано — підсвітити правильний варіант і показати цитату з лекції */
.q:has(input:checked) .opt.ok{border-color:var(--ok);background:var(--ok-bg);color:var(--ok)}
.opt:not(.ok):has(input:checked){border-color:var(--bad);background:var(--bad-bg);color:var(--bad)}
.q:has(input:checked) .src{display:block}
/* рахунок без скрипта: CSS-лічильники, рядок рахунку стоїть після всіх питань */
.q:has(input:checked){counter-increment:answered}
.q:has(.opt.ok input:checked){counter-increment:answered right}
.score::after{content:counter(right) " з " counter(answered) " · питань: 3"}
/* телефон: fieldset типово має min-inline-size:min-content */
main{…;overflow-wrap:anywhere}
.q{…;min-width:0}

23 тести test_render.py перевіряють те, що дешево перевірити без браузера: одна радіогрупа на питання й унікальні імена, рівно один ok на позиції answer, екранування, відсутність vh і обидва правила для телефона. Контраст рахує 10 рядків stdlib — ті самі формули WCAG 2.2, 7 пар токенів × 2 теми:

def luminance(hex_color: str) -> float:
    """WCAG 2.x relative luminance of an sRGB colour #rrggbb."""
    def lin(c: float) -> float:
        return c / 12.92 if c <= 0.04045 else ((c + 0.055) / 1.055) ** 2.4
    r, g, b = (int(hex_color[i:i + 2], 16) / 255 for i in (1, 3, 5))
    return 0.2126 * lin(r) + 0.7152 * lin(g) + 0.0722 * lin(b)

def contrast(a: str, b: str) -> float:
    hi, lo = sorted((luminance(a), luminance(b)), reverse=True)
    return (hi + 0.05) / (lo + 0.05)   # ≥ 4.5 для звичайного тексту (SC 1.4.3)

До травня 2021 року в цьому визначенні W3C стояло 0,03928 замість 0,04045; на 8-бітних кольорах різниці немає. Поріг жорсткий: 4,499:1 вимогу не виконує. Сірий #777777 на білому дає 4,48:1, і калібрувальний тест це перевіряє.

У Node є expect(page).toHaveScreenshot() з базовими знімками і допусками. У Python його немає: запит у playwright-python закрито 30.04.2026 з формулюванням «No plans to implement this», запит у pytest-playwright — 08.10.2026, теж «not planned». Python дає page.screenshot(), а порівняння пишете ви. У Lectern це tests/pixeldiff.py: 60 рядків stdlib (zlib декодує PNG, рахує пікселі, у яких R, G або B зсунувся більше за допуск).

Агент з очима і безТри варіанти, три сторінки

Ми закладали в сторінки дефекти й давали Claude Code одне завдання: «Перевір, що сторінка коректно виглядає на телефоні у світлій і темній темі, і виправ, якщо щось не так». Варіанти відрізнялися лише інструментами:

  • текст: Read, Glob, Grep, Edit (для шаблону ще дві команди: lectern render і pytest), без MCP;
  • дерево: те саме + 8 інструментів Playwright MCP (navigate, snapshot, resize, emulate_media, click, wait_for, close, console_messages), скріншот заборонено;
  • очі: те саме + browser_take_screenshot.

У всіх варіантах заборонено browser_evaluate і browser_run_code_unsafe: з JavaScript агент виміряв би ширину скриптом, а це вже інваріант, не зір. Конфігурація MCP — запис playwright із dot-mcp.json Lectern: 0.0.83, headless, isolated, iPhone 15, --allowed-origins http://127.0.0.1:8765.

Усього 15 прогонів, разом із двома відкинутими (про них нижче) — $0,655. Що з цього випливає:

  1. Читабельний CSS сучасна модель розбирає без очей. На A і B текстовий агент виправив усе. На B він прочитав 66 тис. символів HTML і знайшов колонку на 340 px у медіазапиті, хоча на екрані 390 px контейнер має ~362 px. Очі тут потрібні не для пошуку, а для доказу. Обидва текстові агенти на A чесно написали, що візуально не перевіряли. «Очі» на A після правки знову знімали сторінку й дивилися на неї 2 з 2 рази.
  2. Геометрію SVG код показує погано. На C текстовий агент обчислив, що x="372" більше за ширину viewBox 360, але накладання двох підписів не помітив. Агент із деревом відповів «помилок не знайшов»: SVG з role="img" у дереві доступності — один вузол img, у якому всі підписи склеєно в рядок, без координат кожного.
  3. Очі бачать лише те, куди дивляться. Haiku подивився на 7 картинок: нечитабельний повний знімок і чотири ділянки (шапка, хронологія, практика, терміни) з ~26 екранів сторінки. Діаграми серед них не було, зате агент «виправив» те, чого ми не закладали: сховав декоративну ілюстрацію. Sonnet зняв скріншот одного елемента (target: "figure.fig.narrow"), побачив обидва дефекти, виправив і зняв той самий елемент ще раз. На n=1 внесок моделі й стратегії не розділити, але знімок компонента можна вимагати й від дешевої моделі — це питання інструкції, а не бюджету.
  4. Бонус, якого ми не закладали. Текстовий агент на C і Sonnet помітили справжній дефект у стилях цього курсу: у темній темі білий підпис на бірюзовій смузі діаграми має контраст 1,86:1, білий текст на акцентному кольорі — 2,91:1. Після цього уроку в стилях курсу з'явився токен --on-accent (білий у світлій темі, темний у темній): тепер усі пари мають щонайменше 5:1. Обидва значення нижчі за 4,5:1.
Гігієна експерименту

Перші прогони «дерева» й «очей» ми відкинули. Тека out/ у .gitignore, тому git clean -fd її не чистить, і наступний агент прочитав допоміжний скрипт, який лишив попередній. Між прогонами — git clean -fdx або свіжа копія.

  • Ваші скріншоти: перетягнути у вікно, вставити Ctrl+V або дати шлях до файлу. Інструмент Read повертає PNG і JPG як зображення, великі — зменшує.
  • claude --chrome: розширення Claude in Chrome (від 1.0.36) керує вашим справжнім Chrome; документація прямо називає перевірку візуальних регресій веб-застосунку. Це ваш браузер з вашими сесіями, тож для CI він не підходить.
  • Зображення на вході: codex -i screenshot.png "…" (кілька файлів через кому) або вставка в інтерактивний режим.
  • Браузер: вбудований браузер із Computer Use є в desktop-застосунку Codex (відкрити сторінку, клікнути, зробити скріншот). У CLI — через MCP: той самий Playwright MCP у config.toml з disabled_tools (урок 7.2).

Правило розподілу

Інваріант — для того, що можна сформулювати (ширина, контраст, видимість). Базовий знімок — для того, що важко сформулювати, але легко помітити. Модель з очима — для пошуку нового і для доказу після правки. Кожну знахідку моделі переводьте в інваріант (урок 9.4: перевірки, які агент може запустити сам).

Квіз11 питань

11 питань
1. Тести контрасту токенів зелені, а в темній темі заголовки питань зливаються з фоном. Найімовірніша причина і що це впіймає?
Так. Тест токенів бачить лише токени. Рядок .q legend{color:#1d2133} їх обходить, а візуальний тест показав 2,17% змінених пікселів.
Константа 0,03928 проти 0,04045 на 8-бітних кольорах нічого не змінює, а тест контрасту в pytest браузера не запускає: він читає токени з CSS. Колір, вписаний повз токени, видно лише після рендеру.
2. Агент має помітити текст, який у темній темі зливається з фоном. Що дозволити в Playwright MCP?
Так. Скріншот є в типовому наборі інструментів, тему перемикає browser_emulate_media. --caps vision додає кліки за координатами.
Дерево доступності з координатами показує розміри, але не колір. --caps vision — це інструменти на кшталт browser_mouse_click_xy, а скріншоти доступні й без нього.
3. Агент робить знімок усієї сторінки 390 × 21 867 px і читає його. Що отримає модель?
Так. Довга сторона обмежена 1568–2576 px, тож ширина 390 стає 28–46 px. Агент у прогоні так і написав: знімок «нечитабельний».
11 тис. токенів (14 × 781 патчів) — ціна без стиснення, але великі зображення зменшують до ліміту довгої сторони. Повний знімок працює і з емуляцією пристрою. Знімайте елемент або один екран.
4. Проєкт на Python, потрібні візуальні регресійні тести. Що обрати?
Так. У Python такого assert немає: обидва запити закрито як not planned (30.04.2026 і 08.10.2026).
У Python немає to_have_screenshot, а знімок дерева не бачить кольору й накладань. Лишається page.screenshot() плюс власний diff, як у Lectern, або раннер Node.
5. Базові знімки зроблено на Mac. У CI на Linux тест падає на кожному PR: 3% змінених пікселів. Що зробити?
Так. Шрифти й згладжування залежать від ОС, тому Playwright додає платформу до імені знімка.
Поріг 5% пропустить регресію темної теми (2,17%). Автооновлення в CI робить тест вічно зеленим — це baseline churn. Потрібні знімки для платформи CI.
6. Колега пропонує допуск каналу 0 і поріг 0% «для точності». Що буде?
Так. Нуль на одному браузері — правда, але оновлення Chromium змінює згладжування. Поріг треба вибирати за виміряним шумом.
0 пікселів дає лише той самий браузер. Між двома збірками Chromium при допуску 0 змінюється 5,26% пікселів, а це вдвічі більше за регресію теми. Такий тест вчить команду не дивитися на падіння.
7. Базовий знімок: device_scale_factor=1, scale="css". Новий тест знімає page.screenshot() без параметрів у контексті з DPR 3. Що станеться?
Так. У Python типовий scale — "device", тож знімок має 1170 × 4167 px замість 390 × 1389.
CSS-пікселі типові для Node toHaveScreenshot, а не для Python page.screenshot(). Там типово "device", і на DPR 3 розмір утричі більший, тож порівнювати немає що.
8. Тему сторінки ставить хост атрибутом data-theme. Агент емулює темну схему, а знімок світлий. Чому?
Так. Тестуйте тим механізмом, яким тему вмикає продукт. tools/shoot.sh цього курсу переписує атрибут у HTML.
Емуляція діє одразу і в headless-режимі: темну тему квізу Lectern ми знімали саме так. Але вона перемикає медіазапит, а атрибут data-theme від нього не залежить.
9. На довгому уроці Haiku з повним знімком знайшов 0 із 2 дефектів SVG, а Sonnet з одним знімком діаграми — 2 з 2. Що змінити, щоб дешева модель працювала?
Так. Haiku подивився на чотири ділянки з ~26 екранів і діаграми не бачив. Sonnet зняв саме діаграму. Покриття можна задати інструкцією, а сильнішу модель на кожну перевірку — ні.
Більший знімок однаково стискається до ліміту довгої сторони, і точність не зростає. Сильніша модель коштувала в 5,5 раза більше ($0,308 проти $0,056) і теж знайшла дефекти лише тому, що зняла потрібний елемент. Покриття задають списком компонентів.
10. Квіз має працювати в iframe під CSP script-src 'self', тому зроблений лише на CSS. Яка ціна цього рішення?
Так. Клас ok стоїть у розмітці. Для іспиту відповіді треба перевіряти на сервері.
Рахунок дають CSS-лічильники з :has(), а тема йде за prefers-color-scheme без жодного скрипта. Справжня ціна — ключ відповідей у HTML.
11. Агент без браузера виправив обидва дефекти шаблону, тести зелені, у звіті написав: «візуально не перевіряв». Що робити перед злиттям?
Так. Правка, ймовірно, правильна (на A вона була правильною 2 з 2 рази), але доказу немає. Крок 5 циклу — закріпити її тестом.
Зелені тести не бачили цих дефектів — інакше вони впали б раніше. А відкидати правильну правку через спосіб, яким її знайшли, немає сенсу. Потрібне спостереження і тест.

Терміни урокуВони є у ваших картках

ТермінКоротко
visual feedback loopЦикл «зміна → рендер → спостереження → оцінка → тест», у якому агент бачить результат каскаду, а не лише код.
accessibility snapshotДерево доступності сторінки (ролі, тексти, стан, за бажання — координати), яке Playwright MCP віддає моделі замість картинки.
screenshot verificationПеревірка вигляду зображенням, яке бачить модель; доказ після правки і пошук того, що не видно в коді.
visual regression testТест, що порівнює новий знімок сторінки чи компонента з базовим і падає, коли змінилося більше за поріг.
pixel diff toleranceДва допуски порівняння: на скільки може зсунутися канал кольору і яка частка пікселів може змінитися.
baseline churnЧасте, неперевірене оновлення базових знімків, після якого тест уже нічого не охороняє.
color-scheme emulationПідміна медіазапиту prefers-color-scheme у браузері для знімка темної чи світлої теми.
device scale factorDPR: скільки фізичних пікселів на один CSS-піксель; визначає розмір знімка й рендер.
WCAG contrast ratio(L1 + 0,05) / (L2 + 0,05) відносних яскравостей; ≥ 4,5:1 для звичайного тексту, ≥ 3:1 для великого.
CSS-only interactionІнтерактивність без JavaScript: радіокнопки, :has(), CSS-лічильники.

Домашнє завданняДві задачі з AI-перевіркою

1. Візуальний цикл для вашої сторінки

Для однієї сторінки чи компонента: інваріанти на 390 px у двох темах, політика базових знімків, виміряний шум і поріг, один закладений дефект і що його впіймало.

2. Огляд довгої сторінки агентом

Інструкція й конфігурація для дешевої моделі, яка має перевірити сторінку на ~26 екранів: покриття, знімки елементів, бюджет токенів, що стає інваріантом.
