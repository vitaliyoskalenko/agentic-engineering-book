01

Навіщо пакетВід теки .claude/ до одиниці дистрибуції

У модулі 4 Lectern отримав .claude/settings.json, у 6.1 і 6.2 — skills і хуки. Коли курси пишуть п'ять авторів у п'яти репозиторіях, теку .claude/ копіюють руками, і за місяць у кожного своя версія хука. Плагін розв'язує саме це: один каталог компонентів з іменем і версією, який ставлять однією командою й оновлюють з одного джерела.

Окремі файли в .claude/Плагін
Ім'я команди/check-quiz/lectern-tools:check-quiz: префікс прибирає конфлікти між плагінами
Як потрапляє до колегикопія теки або коміт у кожен репозиторійclaude plugin install lectern-tools@lectern
Оновленнявручну, без версіїз marketplace: за версією або за комітом
Де дієтам, де лежить текаscope: user, project або local
Хто може вимкнутивидалити файлиclaude plugin disable, без видалення

Правило з документації: окремий skill, хук чи MCP-сервер працює й без плагіна. Плагін потрібен, коли компонентів кілька й вони мають їхати разом, коли той самий набір треба ставити в багато проєктів або випускати версіями.

Продуктове мислення

Увімкнений плагін присутній у кожній сесії, а не лише тоді, коли ви ним користуєтеся. Назви й описи його skills та агентів сидять у контексті щоходу, хуки спрацьовують на кожну подію, MCP-сервери працюють фоном. Тож встановлення — це рішення про постійні витрати й постійні права, а не про одну команду.

02

Анатомія плагінаМаніфест, компоненти, змінні шляхів

Плагін — це тека. Маніфест .claude-plugin/plugin.json необов'язковий: без нього Claude Code бере компоненти зі стандартних місць, а ім'я — із запису в marketplace або з назви теки. Решта лежить у корені плагіна, а не всередині .claude-plugin/:

Файл або текаЩо дає
.claude-plugin/plugin.jsonманіфест; обов'язкове лише поле name
skills/check-quiz/SKILL.mdskill, який також є командою /lectern-tools:check-quiz
commands/старий формат команд; для нових — skills/
agents/*.mdсубагенти lectern-tools:<ім'я> (урок 6.4)
hooks/hooks.jsonхуки у форматі hooks з settings.json (урок 6.2)
.mcp.json, .lsp.jsonMCP-сервери (модуль 7) і мовні сервери (урок 3.1)
monitors/monitors.jsonфонові команди; їхній вивід приходить Claude як сповіщення
bin/виконувані файли в PATH інструмента Bash
output-styles/, themes/, workflows/стилі відповіді, кольорові теми, workflow-скрипти
settings.jsonдіють лише ключі agent і subagentStatusLine
scripts/ та іншедовільні файли, які викликають хуки

Деталі, які ламають перший плагін:

  • CLAUDE.md у корені плагіна не завантажується. Інструкції кладуть у skill, а правило, яке має виконуватися завжди, — у хук. claude plugin validate про такий файл попереджає.
  • Хуки плагіна не чекають на його skills. Їх реєструє завантаження плагіна, і далі вони спрацьовують на кожну подію. Обмежує лише matcher.
  • Ключ у маніфесті може замінити стандартну теку або доповнити її. commands, agents, outputStyles скасовують сканування своєї теки, skills і hooks додаються до неї.
  • Ім'я — kebab-case, і частина імен зарезервована. Префікси claude-, anthropic-, cc-plugin- і слово official поруч із claude валідатор відхиляє як «видає себе за Anthropic» (вивід нижче).
  • version — це закріплення. Якщо версію задано, користувачі сидять на ній, скільки б комітів ви не запушили, доки рядок не зміниться. Без version версією стає SHA коміту.

Три змінні шляхів

ЗміннаКуди вказуєДля чого
${CLAUDE_PLUGIN_ROOT}тека встановленої версії, ~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/скрипти й конфіги з плагіна. Шлях змінюється з кожною версією, тому стан тут не тримають
${CLAUDE_PLUGIN_DATA}~/.claude/plugins/data/<id>/; переживає оновленняnode_modules, кеші, журнали. Видаляється разом із плагіном з останнього scope, якщо не передати --keep-data
${CLAUDE_PROJECT_DIR}корінь проєктуінструменти проєкту, наприклад .venv/bin/ruff

Підставляються вони в command і args хуків, у command/args/env stdio MCP- та LSP-серверів і в текст skills та агентів. У середовищі команд, які Claude запускає через Bash, цих змінних немає, тому шлях до файлу плагіна пишуть прямо в тексті skill. У shell-формі хука шлях беруть у лапки: "\"${CLAUDE_PLUGIN_ROOT}/scripts/x.sh\"", бо шлях із пробілом інакше розпадеться на два слова.

03

Marketplace і встановленняКаталог, scope, версія, сесія

Marketplace — це не магазин, а файл-каталог .claude-plugin/marketplace.json у репозиторії чи теці. Обов'язкові поля: name, owner і масив plugins, де кожен запис має name і source. Ідентифікатор для встановлення — <name запису>@<name marketplace>.

{
  "name": "lectern",
  "owner": { "name": "Lectern team" },
  "plugins": [
    { "name": "lectern-tools", "source": "./plugins/lectern-tools",
      "description": "Перевірка квізів і ruff після кожної правки .py" }
  ]
}

source буває відносним шляхом від кореня marketplace (без ..), а також github, git-subdir (тека в монорепозиторії), url, archive (zip з необов'язковим sha256), npm або command. Каталог може посилатися на чужі репозиторії, тож marketplace і плагін часто мають різних власників. Ім'я запису і name у plugin.json мають збігатися, інакше встановлення за ім'ям з маніфесту дає Plugin "…" not found in marketplace.

Три scope

ScopeКуди пишеться enabledPluginsДля кого
user (типово)~/.claude/settings.jsonдля вас у всіх проєктах; також у VS Code і в локальних сесіях desktop
project.claude/settings.json, комітитьсядля всіх у репозиторії, але кожен колега один раз запускає install --scope project сам
local.claude/settings.local.jsonдля вас лише в цьому репозиторії

Пріоритет: local > project > user, тож claude plugin disable x --scope local вимикає командний плагін лише для вас. Плагін зі scope project приходить з репозиторію, тому вантажиться тільки після діалогу довіри до теки (урок 3.4): -p і довіра до батьківської теки не рахуються, монітори не стартують, MCP-сервери чекають окремого схвалення. Для user і local таких обмежень немає. Хмарні сесії плагінів з локальних налаштувань не бачать (урок 4.1).

Від налаштувань до сесії

  1. Налаштування: extraKnownMarketplaces (звідки брати) і enabledPlugins (що ввімкнено) у файлі обраного scope.
  2. Диск: ~/.claude/plugins/: клони marketplace, cache/<marketplace>/<plugin>/<version>/, data/, installed_plugins.json. Плагін з локального marketplace з відносним шляхом читається на місці, без копії: правки діють з наступної сесії, version піднімати не треба.
  3. Сесія: плагіни вантажаться на старті або після /reload-plugins. Оновлення, що додає чи прибирає MCP-сервер, ламає prompt cache, тому без --force reload його не застосує.
ДіяУ сесіїУ shell або скрипті
Додати каталог/plugin marketplace add owner/repoclaude plugin marketplace add <src> --scope …
Встановити/plugin → Discover, або /plugin install x@m (відкриває панель)claude plugin install x@m -s project
Побачити склад і ціну/plugin → Will installclaude plugin details x
Вимкнути / видалити/plugin disable|uninstall xclaude plugin disable|uninstall x
Перевірити маніфест/plugin validate <path>claude plugin validate <path> --strict
Застосувати зміни/reload-pluginsнаступний запуск
Завантажити без встановлення—claude --plugin-dir ./x (тека або .zip), --plugin-url

У claude -p панелі /plugin немає, а встановлені плагіни вантажаться, тож у скриптах і CI плагіни ставлять лише через claude plugin …. --plugin-dir вантажить плагін як <name>@inline на одну сесію. Якщо його ім'я збігається з встановленим, у цій сесії перемагає копія з --plugin-dir, і на цьому побудований цикл розробки: правка → новий запуск, без marketplace. --resume цей прапорець не відновлює, його передають знову (урок 4.3).

Перевірено · 15.10.2026

Оновлення: автооновлення увімкнене для офіційних каталогів Anthropic (окрім knowledge-work-plugins і first-party-plugins) і вимкнене для community, сторонніх і локальних. Оновлений плагін діє з наступної сесії або після /reload-plugins. Стару версію Claude Code позначає й видаляє через 14 днів, щоб уже відкриті сесії не зламалися.

04

ДовіраПлагін виконує код від вашого імені

Документація формулює прямо: встановлений плагін може виконати довільний код на вашій машині з правами вашого користувача. Ось як саме:

КомпонентЩо відбуваєтьсяЧи бачать це дозволи і sandbox
hooks, monitorsshell-команди на події сесії або фоном від її стартуні: працюють поза sandbox із повними правами
stdio MCP, LSPпроцеси, які Claude Code запускає самсам процес — ні; виклик MCP-інструменту моделлю — так
bin/файли в PATH інструмента Bash (після ваших, тож git не підмінять)так: це Bash-виклик моделі
skills, agents, commandsтекст, що стає інструкціями моделіопосередковано: модель діє вже наявними інструментами
автооновленняфайли, які ви переглянули, змінюються на диску у фоніні

Три рівні каталогів. Офіційні імена (claude-plugins-official, claude-code-plugins та ще дванадцять) і community-імена (claude-community, claude-plugins-community, healthcare) Claude Code приймає лише з репозиторіїв github.com/anthropics/, тож сторонній каталог під офіційного не замаскується. Решта — third-party, зокрема каталог вашої компанії. Рівень каталогу каже, хто веде список, а не що робить кожен плагін у ньому: більшість записів офіційного каталогу належить партнерам, і попередження перед встановленням однакове для всіх рівнів: «Anthropic does not control what MCP servers, files, or other software are included in plugins».

Чекліст перед install

  1. Джерело каталогу: claude plugin marketplace list показує, звідки його додано. Запис офіційного каталогу може вказувати на чужий репозиторій. У community-каталозі майже кожен запис закріплено на commit SHA, і інший коміт Claude Code не встановить.
  2. Склад без встановлення: клонуйте репозиторій і запустіть claude --plugin-dir <тека> plugin details <ім'я>. Команда читає файли без сесії й друкує інвентар компонентів і прогноз токенів.
  3. Що виконується: прочитайте hooks/hooks.json (команда кожного хука), .mcp.json (команда чи URL сервера), усе в bin/. Окремо шукайте npx -y пакет без версії: він щоразу тягне найновішу версію з npm, тобто код, якого ви не бачили.
  4. Що піде назовні: хуки, що шлють diff у LLM або сторонній сервіс, і MCP-сервери з токенами в env/headers.
  5. Найвужчий scope: спершу local в одному репозиторії, а не user для всіх проєктів.
  6. Оновлення: для стороннього каталогу автооновлення типово вимкнене, тож вирішуйте свідомо, чи вмикати його, коли перевіряли лише одну версію.
  7. Вийти з довіри: claude plugin uninstall x --scope … лишає копію в ~/.claude/plugins/cache/ ще на 14 днів; щоб прибрати одразу, видаліть теку вручну або видаліть marketplace разом з усіма його плагінами.
Виміряно в прогоні нижче

У недовіреній теці claude -p написав «Ignoring 5 permissions.allow entries from .claude/settings.json: this workspace has not been trusted», тобто правила проєкту проігнорував. А хук плагіна, встановленого зі scope local, у тій самій сесії відпрацював двічі. Особистий scope не проходить через діалог довіри: рішення про довіру ви ухвалюєте один раз, у момент install.

Організація закриває це керованими налаштуваннями (managed settings): allowlist і blocklist каталогів, примусове ввімкнення плагінів, заборона --plugin-dir і --plugin-url, хуки лише з керованих джерел. Як вести власний командний каталог, розбирає урок 13.1, а supply chain плагінів і MCP — урок 12.4.

Наскрізний проєктLectern як плагін для авторів курсів

Lectern · модуль 6 · плагін lectern-tools

Автори курсів працюють у власних репозиторіях лекцій, а не в репозиторії Lectern. Їм потрібні правила й перевірки Lectern, але не його код. Тому Lectern постачає плагін, який ставиться в репозиторій курсу:

  1. 0.1.0, сьогодні: skill check-quiz (лише lectern check --json, без правок) і хук ruff на .py. Вихідний код лежить у консолі уроку.
  2. Ворота для квізу: PostToolUse на *quiz*.json запускає lectern check --json і повертає exit 2 зі списком errors, щоб агент не завершив роботу з вигаданою цитатою.
  3. Захист даних: PreToolUse відмовляє в доступі до lectures/private/** і data/learners/**. Це дубль deny з settings, але він їде разом із плагіном у кожен репозиторій курсу.
  4. Агент quiz-reviewer (урок 6.4): лише Read і Grep, перевіряє дистрактори й баланс відповідей (пункт B4 у BACKLOG.md).
  5. MCP-сервер lectern (модуль 7) у .mcp.json через ${CLAUDE_PLUGIN_ROOT}, з закріпленою версією і без npx -y.
  6. Не класти в плагін: CLAUDE.md (не завантажується, правила йдуть у skill) і сам пакет lectern (ставиться через pip у .venv курсу).
  7. Дистрибуція: marketplace.json у корені репозиторію Lectern; курси вмикають плагін зі --scope project; version закріплено, реліз позначає claude plugin tag; CI запускає validate --strict, а в модулі 12 додасться claude plugin eval.
  8. Бюджет: прогноз details не більше ~500 токенів щоходу. Зараз ~108.

Ваш крок: зберіть lectern-tools зі skill і хуком, пройдіть claude plugin validate --strict і поставте плагін зі scope local у копію Lectern з тимчасовим CLAUDE_CODE_PLUGIN_CACHE_DIR. Типові помилкиДе плагіни ламаються і де обманюють

ПомилкаЯк насправді
«Він з офіційного каталогу, отже перевірений»Рівень каталогу каже, хто веде список. Більшість записів офіційного каталогу партнерські, а playwright звідти запускає @playwright/mcp@latest.
«Запушив фікс — користувачі вже отримали»Із закріпленим version користувачі лишаються на кешованій копії, доки ви не зміните рядок версії. А для стороннього каталогу автооновлення до того ж типово вимкнене.
«Покладу стан у ${CLAUDE_PLUGIN_ROOT}»Шлях змінюється з кожною версією, а стару теку через 14 днів видаляють. Стан тримають у ${CLAUDE_PLUGIN_DATA}.
«Поки я не викликаю команди, плагін нічого не коштує»Описи skills і агентів сидять у контексті щоходу: у Task Master це ~2 579 токенів, а хуки дописують своє поверх прогнозу.
«Хук плагіна спрацює лише разом з його skill»Хуки реєструються під час завантаження плагіна і спрацьовують на кожну подію, що підходить під matcher.
«У -p skill плагіна просто запуститься»Виклик Skill підлягає дозволам. У CI додають --allowedTools "Skill(плагін:skill)".
«Ім'я в каталозі неважливе»Ім'я запису і name у plugin.json мають збігатися, а імена на claude- валідатор відхиляє.

Квіз10 ситуацій

10 питань
1. Автор запушив виправлення хука, але "version": "1.2.0" у plugin.json не змінив. Користувачі встановили плагін із каталогу на GitHub. Що вони отримають?
Так. Порядок визначення версії: version маніфесту, потім запису в каталозі, і лише тоді SHA. Закріплений рядок тримає всіх на кешованій копії.
SHA стає версією, лише коли version не задано ні в маніфесті, ні в записі каталогу. Scope визначає, хто отримує плагін, а не звідки береться копія. Підніміть рядок версії або приберіть його, щоб версією був коміт.
2. Сторонній плагін містить hooks/hooks.json і .mcp.json з npx -y some-mcp. Що з цього ваші permission rules і sandbox не обмежують?
Так. Дозволи стосуються tool calls моделі, а хуки, монітори, MCP- і LSP-процеси Claude Code запускає сам, без sandbox.
Виклик MCP-інструменту і запуск файлу з bin/ — це tool calls моделі, тож правила до них застосовуються, а bin/ стоїть у PATH після ваших записів. Поза контролем лишаються процеси, які стартують без участі моделі: хуки, монітори, сервери.
3. Команда хоче, щоб lectern-tools був у кожного, хто працює з репозиторієм курсу. Як це зробити?
Так. Коміт вмикає плагін для всіх, але не завантажує його. Кожен виконує claude plugin install … --scope project, і плагін вантажиться після діалогу довіри до теки.
Claude Code не сканує .claude/plugins/ проєкту, а user-налаштування живуть на одній машині й нікуди не синхронізуються. Спільним є лише закомічений enabledPlugins у scope project.
4. Для security-guidance команда claude plugin details показує «Always-on ~0 tok». Що це означає для рахунку?
Так. «Always-on» — це назви й описи компонентів у контексті. Виклики LLM з хуків і текст, який хуки дописують у контекст, прогноз не бачить.
Хуки справді не займають контекст, але цей плагін на кожному Stop надсилає diff найновішому Opus, а на commit і push ще й запускає агентне рев'ю. Нуль у прогнозі описує контекст, а не витрати.
5. У CI claude -p повертає permission_denied: Execute skill: lectern-tools:check-quiz. Що дасть мінімально потрібний доступ?
Так, саме так зроблено в прогоні уроку. Після цього allowed-tools самого skill дозволили lectern check.
Обхід усіх дозволів відкриє набагато більше, ніж потрібно, а scope впливає на те, де плагін увімкнено, а не на дозволи. Skill — це інструмент, і його дозволяють так само, як Bash чи Edit.
6. Ваш плагін завантажує модель на 500 МБ і кешує її між сесіями. Куди класти кеш?
Так. DATA — постійна тека плагіна, яку видаляють при uninstall з останнього scope (якщо не передати --keep-data).
ROOT — тека конкретної версії: після оновлення шлях інший, а стару теку через 14 днів видаляють, тож кеш довелося б завантажувати знову. Кеш у кожному проєкті множить 500 МБ на кількість репозиторіїв і переживає видалення плагіна.
7. Сторонній каталог має "name": "claude-plugins-official" і додається з github.com/acme/tools. Що зробить Claude Code?
Так. Офіційні й community-імена зарезервовані, тож підробити рівень каталогу не вийде. Проте це захищає лише назву каталогу, а не вміст плагінів.
Резервування імен існує саме для того, щоб сторонній каталог не видав себе за Anthropic. Claude Code відмовить уже під час marketplace add: «The name … is reserved for official Anthropic marketplaces».
8. Ви розробляєте плагін і хочете перевіряти кожну правку в новій сесії, нічого не встановлюючи. Що обрати?
Так. Плагін вантажиться як my-plugin@inline лише на цю сесію, а в уже відкритій сесії правки застосовує /reload-plugins.
Обидва інші варіанти встановлюють плагін. Крім того, плагін з локального каталогу з відносним шляхом і так читається на місці, тож піднімати версію там не потрібно.
9. Ви хочете один плагін для Claude Code, Codex і Cursor. Що реально переносить формат Agent Plugins?
Так. Стандарт покриває plugin.json, skills/ і mcp.json. Хуки Codex підтримує лише в плагінах, встановлених вручну, а Cursor — у власному форматі .cursor-plugin.
Skills — найпереносиміша частина, бо всі три читають SKILL.md. Хуки якраз найменш переносимі: у Codex плагін із хуками не потрапить у публічний каталог, а Cursor тримає їх у своєму форматі.
10. Для Task Master plugin details показує «MCP servers (0)», хоча в теці є mcp.json. Який висновок?
Так. Стандартне ім'я — .mcp.json у корені плагіна, а маніфест не вказує на інший файл. Звіт читає саме те, що Claude Code завантажить.
details показує MCP-сервери ще до запуску (для GitHub-плагіна там «MCP servers (1)»), а попередження validate нічого не вимикають: плагін з ними завантажується.

Домашнє завданняДві задачі з AI-перевіркою

1. Аудит чужого плагіна до встановлення

Оберіть плагін з офіційного або community-каталогу, в якому є хоча б один хук або MCP-сервер. Не встановлюючи його, складіть звіт: склад і прогноз токенів з claude --plugin-dir … plugin details, що виконує кожен хук і сервер, що йде назовні, незакріплені залежності, рекомендований scope і вердикт «ставити / ставити з умовами / не ставити».

2. Плагін Lectern 0.2.0: проєкт релізу

Спроєктуйте наступну версію lectern-tools з воротами для квізу й захистом приватних лекцій: дерево файлів, plugin.json, hooks.json, запис у marketplace.json, стратегія версій і оновлень, команди CI і бюджет токенів.
