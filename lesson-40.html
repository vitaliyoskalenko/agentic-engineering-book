Специфікації в спільному репозиторії: рев'ю, версіонування, трасування, spec drift

Специфікація в командному репозиторії корисна, лише поки їй можна вірити: на неї спираються рецензенти, тести й агенти, які пишуть код. Даємо вимогам id, статуси й власників, рев'юїмо їх окремо від коду, виводимо матрицю трасування з тестів і комітів і ловимо spec drift — від червоного CI до аудиту агентом.

Після уроку ви зможете

  • обрати розкладку специфікацій у репозиторії, дати вимогам глобальні id і статуси та призначити власників через CODEOWNERS;
  • рев'юїти spec-PR окремо від code-PR і використати агента як дешевого першого рецензента, розуміючи межі його точності;
  • версіонувати вимоги: уточнення, заміна (supersede), delta-специфікації, журнал змін із git-трейлерів;
  • побудувати автоматичну матрицю трасування «вимога → тест → коміт», яка валить CI на непокритих вимогах і осиротілих тестах;
  • розпізнати три типи spec drift, підібрати детектор під кожен і вирішити, що є джерелом істини, коли документ і код розійшлися.
01

Spec як командний артефактЗелені тести, неправдивий документ

Дослід на копії Lectern. Один коміт «wip: quote handling tweaks» робить три зміни: norm() перестає розрізняти регістр; validate() починає приймати коротку цитату, якщо вона дослівно є в лекції, і тест «підправлено» під це; у специфікації поріг MIN_QUOTE_WORDS записано як «6 слів», хоча в коді 5. Результат:

$ .venv/bin/python scripts/trace.py | tail -1

реальний вивід · 15.10.2026 · зміни — console/runs/drift/drift-seeded.diff

Документ бреше в трьох місцях, і жодна перевірка не червона. Виконувана таблиця з уроку 5.4 мовчить, бо в ній немає рядка з різним регістром; тест відповідає коду, бо його змінили разом із кодом. Це і є spec drift — розбіжність між специфікацією, кодом і тестами.

У спільному репозиторії вона множиться: кілька гілок пишуть вимоги паралельно, агенти читають docs/spec як інструкцію, а рев'юери дивляться diff коду. Для людини застаріла spec — незручність; для агента, якому CLAUDE.md каже «поведінка — у docs/spec», це вхідні дані для наступної зміни. Агент, що прочитає «6 слів», чесно «виправить» код під документ.

Продуктове мислення

Специфікація окуповується, лише поки їй можна вірити без перевірки. Тому все, що нижче, служить одній меті: щоб розбіжність ставала червоним CI або коментарем рецензента в момент PR, а не відкриттям через місяць.

Lectern поєднує дві схеми: фічі в роботі — docs/specs/S-NN-*.md за шаблоном 8.1, чинна поведінка — docs/spec/. Склеює їх глобальний id вимоги: LEC-Q-004 (проєкт, область, номер). Локальні R1–R6 зручні в одному документі, але маркер тесту req("R1") у репозиторії з двадцятьма специфікаціями нічого не означає.

Пастка нумерації

Spec Kit за замовчуванням бере для теки фічі наступний вільний трицифровий номер, сканувавши specs/. Дві гілки, створені з того самого main, отримають однаковий 004. Для паралельної роботи шаблон пропонує "feature_numbering": "timestamp" (префікс YYYYMMDD-HHMMSS). Те саме стосується id вимог — розв'язки в розділі про гілки.

Два рівні статусу

Статус документа (у шаблоні 8.1: чернетка → на рев'ю → затверджено; у Spec Kit — рядок **Status**: Draft) відповідає на питання «чи можна за цим будувати». Статус вимоги відповідає на інше: «чи це вже в коді і чим доведено». Саме його читає перевірка трасування.

Власники: CODEOWNERS

# .github/CODEOWNERS
# останній збіг перемагає:
# загальне правило — першим
*                      @lectern/maint
/docs/spec/            @lectern/spec
/docs/adr/             @lectern/arch
/src/lectern/tools.py  @lectern/spec
/scripts/trace.py      @lectern/spec
  • Файл шукається в .github/, у корені, потім у docs/; діє перший знайдений, і він має бути в базовій гілці PR.
  • Власників запитують на рев'ю автоматично, але не для чернеток PR — лише коли PR позначать готовим.
  • Блокує злиття не CODEOWNERS, а правило захисту гілки «Require review from Code Owners»; і тоді достатньо схвалення будь-кого з власників шляху.
  • Власник мусить мати явний доступ write; рядок з неіснуючим користувачем або без доступу не призначає нікого — помилка видна лише у вікні файла на GitHub. Ліміт — 3 МБ.

Навіщо окремий власник tools.py: вимоги LEC-Q реалізовано саме там, тож зміна коду без участі власника специфікації — найкоротший шлях до дрейфу першого типу.

Шаблон PR

GitHub бере pull_request_template.md з кореня, docs/ або .github/; кілька шаблонів — у підтеці PULL_REQUEST_TEMPLATE/ з вибором через параметр ?template=. Шаблон діє після злиття в гілку за замовчуванням. У Lectern він вимагає поле Refs: і одну позначку типу PR: spec-PR, код за вимогою, зміна поведінки (нова вимога + superseded) або «без впливу на вимоги» — повний текст у кроці проєкту.

03

Рев'ю специфікаціїSpec-PR перед code-PR

Рев'ю коду питає «чи правильно зроблено», рев'ю специфікації — «чи те робимо». Змішані в одному PR, ці питання програють: рецензент бачить 300 рядків коду і 20 рядків вимог і читає код.

Що перевіряютьУ spec-PRУ code-PR
Наміряку проблему розв'язуємо і за якою ознакою зрозуміємо, що розв'язалине обговорюють: вирішено в spec-PR
Перевірюваністькожна вимога має вхід і очікуваний результат, без «швидко» й «зручно»на кожен змінений id є тест з req, і без зміни він падає
Межіnon-goals названо явноdiff не виходить за них
Ризикисуперечності між вимогами, нездійсненність, злам чинного контрактурегресії, безпека, продуктивність
Хто схвалюєвласник docs/spec/ за CODEOWNERSвласник коду

Мінімум для spec-PR збігається з тим, що документація Claude Code називає найкориснішою специфікацією для агента: вона самодостатня, називає файли й інтерфейси, каже, що поза обсягом, і закінчується наскрізною перевіркою, яка доводить, що фіча працює.

Правило: код посилається лише на вимоги в статусі approved, а цей статус з'являється тільки зі злиттям spec-PR. Якщо реалізація показала, що вимога хибна, code-PR зупиняють і відкривають окремий spec-PR, а не правлять документ мовчки разом із кодом. Виняток — уточнення формулювання без зміни поведінки. Розмір spec-PR — одна здатність системи: OpenSpec з тієї ж причини тримає кожну зміну в окремій теці.

Агент як перший рецензент

Рецензент-людина дорогий, а частина вад специфікації механічна: дублікат id, порожній статус, оцінні слова. Їх дешево віддати агентові до того, як spec-PR побачить власник. Дослід: специфікація перемішування варіантів квізу з вісьмома вадами, внесеними навмисно (список — у console/runs/review/seeded.txt; моделі його не показували).

Найгірша вада тут — відсутня: ніде не сказано, що answer (індекс у options) після перемішування має вказувати на той самий варіант. Рецензент отримує системний промпт з чинним контрактом квізу і шістьма пунктами перевірки, без інструментів:

Виміряно · 15.10.2026

Хибних тривог серед знахідок не було, але кількість знахідок не падає після виправлення (9–10 → 7–10): рецензент, якого просять знайти проблеми, знаходить їх завжди, зміщуючись до дрібніших. Тому метрика — не «нуль зауважень», а «нуль critical після рев'ю людини». Важкість теж нестабільна: дубль id — то critical, то major.

Що агентові не доручати: рішення, яка з двох суперечливих вимог правильна, і чи варто фіча роботи. Він бачить текст, а не продукт.

04

Версіонування вимогId сталий, зміст змінюється через заміну

Git версіонує файл, але не вимогу: diff рядка таблиці не каже, чи змінилась поведінка, чи лише кома. Тому зміни класифікують явно.

ЗмінаIdСтатусЩо ще
Уточнення без зміни поведінкитой самийбез зміну PR: «поведінка не змінюється»; тести ті самі й зелені
Зміна поведінкиновийстарий → superseded → новийтести старої переносять або видаляють (інакше ERROR); ADR, якщо рішення архітектурне
Скасуваннятой самийsuperseded → новий, де нова вимога описує «не робить X»: заміни без нащадка trace.py не приймаєстарі коміти з Refs: лишаються валідними
Нова вимоганаступний вільнийdraft → approvedномер «бронює» злиття spec-PR

Чому не переписати рядок на місці: на LEC-Q-003 посилаються тести й коміти. Якщо поведінка інша, а id той самий, тест старої поведінки виглядатиме доказом нової. Новий id робить розрив видимим.

Delta-специфікації

OpenSpec розв'язує ту саму задачу інакше: зміна лежить у openspec/changes/<назва>/specs/… і описує лише різницю розділами ## ADDED Requirements, ## MODIFIED Requirements, ## REMOVED Requirements. Під час архівації ADDED дописується в основну spec, MODIFIED замінює наявну вимогу, REMOVED її видаляє, а тека зміни переїжджає в changes/archive/ з датою.

Різниця з підходом Lectern — де живе історія. OpenSpec тримає в основній spec лише чинний стан, історія — в архіві змін. Lectern лишає замінений рядок у таблиці, бо на нього посилаються маркери тестів і трейлери комітів. Правило вибору: якщо id вимог ніде, крім документа, не згадуються, заміна на місці чистіша; якщо на них посилаються тести й коміти, заміна на місці зробить ці посилання осиротілими.

Журнал змін вимог

Окремий CHANGELOG вимог не потрібен, якщо коміти несуть трейлер. git commit --trailer "Refs: LEC-Q-004" додає його, а %(trailers:…) у форматі git log дістає:

Кома у separator записується як %x2C, інакше git сприйме її як роздільник опцій. Зв'язок з ADR (урок 5.4) — односторонній: ADR пояснює, чому змінилось рішення, рядок вимоги посилається на нього в тексті, а не дублює аргументацію.

05

ТрасуванняВимога → тест → коміт, без ручної таблиці

Трасування вимог — це здатність описати й простежити життя вимоги в обох напрямках: вперед і назад.

“Requirements traceability refers to the ability to describe and follow the life of a requirement, in both a forwards and backwards direction.”

Orlena Gotel, Anthony Finkelstein, «An Analysis of the Requirements Traceability Problem», ICRE, 1994

«Вперед» — від вимоги до тестів і коду: що зламається, якщо її змінити. «Назад» — від тесту чи коміту до вимоги: навіщо цей код. Специфікація S-07 з уроку 8.1 має таблицю трасування, написану руками, і вже в день написання в ній дірка: у R6 немає критерію приймання. Ручна матриця гниє так само, як CLAUDE.md з уроку 5.4, тому її треба виводити з артефактів, а не підтримувати.

ЛанкаЯк посилаєтьсяЩо ловить розрив
Вимогарядок таблиці «## Вимоги»: id, текст, статус, номери прикладівtrace.py: дублікат id, невідомий статус, неіснуючий рядок прикладу
Прикладрядок таблиці «## Приклади», який виконує test_spec_quotes.pypytest; trace.py рахує рядки лише тоді, коли файл специфікації згадано в тестах
Тест@pytest.mark.req("LEC-Q-004")--strict-markers — помилку в назві маркера; trace.py — невідомий id
Коміттрейлер Refs: LEC-Q-004trace.py, лише попередження: історію не переписують

Хто правий: політика джерела істини

Коли детектор спрацював, треба вирішити, що правити. «Spec завжди права» не працює: користувачі могли місяцями покладатися на поведінку коду. «Код завжди правий» робить специфікацію описом випадковостей.

СитуаціяДжерело істиниДія
Вимога draftкодspec ще не погоджена; уточнити її в spec-PR

Spec суперечить сама собіжоднезаморозити залежні PR, spec-PR з рішенням власника

У досліді: регістр і коротка цитата — порушення implemented-вимог, які ще не в релізі, отже код повертають. «6 слів» — spec змінилась без рішення: або spec-PR з новою вимогою і реалізацією, або відкат рядка.

Тут git хоча б зупинився. Якби друга гілка дописала рядок в інше місце таблиці або в інший файл, злиття пройшло б без конфлікту, і дубль виявила б лише перевірка унікальності. Способи розвести id:

  • Бронювання: id видає злиття spec-PR у main; гілка з кодом посилається лише на вже злиті id. Найпростіше, але spec-PR стає вузьким місцем.
  • Префікс області чи автора: LEC-Q-…, LEC-S-…, LEC-STATS-… — паралельні фічі рідко ділять область.
  • Позначка часу, як feature_numbering: timestamp у Spec Kit: колізій немає, але id довгі й не читаються вголос.
  • Теки змін, як в OpenSpec: зміни лежать у різних теках і, за документацією, не конфліктують, доки змінюють різні вимоги; про дві зміни однієї вимоги ця гарантія нічого не каже.

Паралельні агенти на одній специфікації

Схема з уроків 4.4 і 3.5 (worktree на агента, людина-оркестратор) додає одне правило: специфікацію пише один, реалізують багато. Агенти-виконавці отримують spec лише для читання; хто знайшов суперечність, зупиняється і звітує обидві сторони з файл:рядок. Інакше п'ять агентів «уточнять» той самий рядок п'ятьма способами, і конфлікт злиття стане найменшою з проблем: кожна гілка буде внутрішньо узгодженою зі своєю версією вимоги.

Технічно це три шари. Інструкція в CLAUDE.md (вкладки нижче) — прохання. Правило ask на Edit(./docs/spec/**) у Claude Code зупиняє вбудовані інструменти редагування й розпізнані shell-команди (sed, tee, перенаправлення), але не скрипт на Python, що відкриває файл сам. Остаточний бар'єр — на сервері: CODEOWNERS і захист гілки не дадуть злити зміну docs/spec/ без власника.

Той самий текст — в AGENTS.md. Codex збирає ці файли від кореня репозиторію до поточної теки, не більше одного на теку; ближчий до теки файл іде пізніше і має перевагу. Правило проєкту — файл .mdc у .cursor/rules/ (звичайний .md там ігнорується). Тип «Apply to Specific Files» з globs підтягує правило лише тоді, коли агент працює з тестами:

---

alwaysApply: false
---
Every test that verifies behaviour from docs/spec carries

Cursor також читає AGENTS.md у корені й підтеках, тож одне спільне правило для Codex і Cursor можна тримати там.

Що насправді змушує

Усі три механізми — інструкції. Примус — поза агентом: хук commit-msg може відхилити коміт без Refs:, але він локальний і обходиться --no-verify. Гарантію дає лише CI, де trace.py падає разом із тестами, і захист гілки, що не дає злити червоний PR.

Так. Це дрейф типу 1, і детерміновано його ловить лише приклад саме на цей випадок: з рядком 7 така зміна дала червоний тест.
Кількість тестів на вимогу не змінює того, що вони перевіряють; trace.py бачить зв'язки, а не зміст. Інструкція в CLAUDE.md — прохання, а не перевірка. Ловить приклад, що виконується: рядок 7 (регістр → missing) зробив цю зміну червоною.
2. trace.py зелений: кожна implemented-вимога має тест з маркером req. Що це гарантує?
Так, і лише це. Маркер на чужому існуючому id (LEC-Q-007 у досліді) проходить перевірку, хоча зв'язок безглуздий.
Трасування перевіряє наявність зв'язку, не його зміст: «перенумерований» на існуючий LEC-Q-007 маркер дав 2 помилки замість 3. А зелені тести можуть кодувати іншу поведінку (дрейф типу 3).
3. Продукт вирішив: парафраз отримує окремий вердикт замість missing. Що робити з LEC-Q-003?
Так. Новий id робить розрив видимим, а trace.py видасть ERROR, доки на старій вимозі висить тест.
На LEC-Q-003 посилаються тести й коміти. Якщо поведінка інша, а id той самий, тест старої поведінки виглядатиме доказом нової. Зміна поведінки — це новий id і superseded для старого.
4. Після виправлення специфікації агент-рецензент знову повернув 10 зауважень. Як це трактувати?
Так. У досліді кількість знахідок не впала (9–10 → 7–10), але серед них не було хибних, і була нова справжня критична вада, внесена виправленням.
Рецензент, якого просять знайти проблеми, знаходить їх завжди, зміщуючись до дрібніших. Хибних знахідок у досліді не було — проблема не в моделі. Метрика — нуль critical після рев'ю людини.
5. Дві гілки додали вимогу LEC-Q-007 у різні файли docs/spec/. Що станеться під час злиття?
Так. Git порівнює рядки файлів, а не значення id. Навіть у тому самому файлі конфлікт буде лише тоді, коли рядки стоять в одному місці.
Git не знає про id: різні файли зливаються без конфлікту. CODEOWNERS призначає рецензентів за шляхами, зміст не аналізує. Дубль ловить trace.py («duplicate id … :26 and … :27»).
6. CODEOWNERS призначає /docs/spec/ команді spec-owners, але зміну специфікації злили без їхнього схвалення. Найімовірніша причина?
Так. Сам файл лише запитує рев'ю; блокує злиття правило захисту гілки або ruleset.
GitHub шукає CODEOWNERS у .github/, корені й docs/ — не в підтеках. Власників визначають за шляхами змінених файлів, а не за текстом PR. Без «Require review from Code Owners» запит на рев'ю ні до чого не зобов'язує.
7. У прозі специфікації «поріг — 6 слів», у коді MIN_QUOTE_WORDS = 5, усі перевірки зелені. Що запобіжить повторенню?
Так. Друга копія значення, яку ніщо не синхронізує, рано чи пізно розійдеться. Рядок-приклад на межі виконується і падає.
Аудит знаходить розбіжність, але не запобігає їй і коштує прогону щоразу; порівняння «всіх чисел» дасть шум від кожної дати й номера рядка. Причина — дубль значення в тексті; лікування — посилання на константу або приклад, що виконується.
8. Тест суперечить специфікації, код погоджений з тестом, поведінка ще не в релізі. Що є джерелом істини?
Так. Це дрейф типу 3: тест могли «підправити», щоб пройшов. git log -p тесту покаже, чи було рішення; несвідому зміну відкочують разом із кодом.
Згода коду з тестом нічого не доводить, якщо тест змінили разом із кодом, — саме так виник дрейф у досліді. Поки поведінка не в релізі, правою лишається погоджена вимога.
9. Чому trace.py зараховує рядки прикладів як покриття лише тоді, коли файл специфікації згадано в тестах?
Так. Таблиця, яку ніхто не виконує, — та сама проза, що може розійтися з кодом.
GitHub тут ні до чого, а AST trace.py читає незалежно від цієї умови. Суть у доказовості: приклад є доказом, лише коли тест його виконує.
10. Агентові-виконавцю додали правило ask на Edit(./docs/spec/**). Що воно не зупинить?
Так. Правила Edit поширюються на вбудовані інструменти й розпізнані shell-команди, але не на довільний підпроцес. Тому остаточний бар'єр — CODEOWNERS і захист гілки.
За документацією Claude Code, правила Edit діють для вбудованих інструментів, sed, tee і перенаправлень. Не діють вони для скрипта, що відкриває файл сам.
11. Під час реалізації агент виявив, що approved-вимога нездійсненна для квізів з 1–4 питань. Що робити?
Так. Зміна поведінки йде через spec-PR і власника з CODEOWNERS; code-PR продовжують після злиття.
У змішаному PR рецензент читає код, а не вимогу. Реалізація заздалегідь хибної вимоги — свідомий дрейф. Правку робить окремий spec-PR, і власник вирішує по суті.

traceability matrixТаблиця «вимога → тести → коміти → статус»; тут вона виводиться з маркерів і трейлерів, а не пишеться руками.

orphan / untestedТест з id, якого немає в специфікаціях / implemented-вимога без жодного тесту чи прикладу.
source of truthПравило, що правити, коли spec і код розійшлися: залежить від статусу, релізу й класу вимоги.

Домашнє завданняДві задачі з AI-перевіркою

1. Специфікація під трасуванням

Візьміть 5–8 вимог свого проєкту (або S-07 з уроку 8.1), дайте їм глобальні id і статуси, пов'яжіть із тестами і зберіть матрицю: власним скриптом або trace.py з Lectern. Зламайте трасування трьома способами, покажіть вивід і опишіть, що перевірка принципово не бачить.

2. Дрейф і джерело істини

Розберіть кейс з трьома розбіжностями (текст — у завданні): класифікуйте кожну за типом, вирішіть за політикою джерела істини, що правити, і перетворіть кожну знахідку на перевірку, яка зловить її наступного разу.
