01

Порядок bootstrapОдинадцять кроків, кожен спирається на попередній

Bootstrap — це стан репозиторію, у якому перша сесія агента вже має одну команду середовища, одну команду перевірки, записані правила, межі дозволів і gate у CI. Порядок визначають посилання між артефактами. Інструкція, що називає неіснуючу команду, — саме та розбіжність, яку ловить check_context.py (5.4). Дозвіл на Bash(scripts/check.sh) без самого скрипта нічого не дає. Required check можна вибрати лише за назвою job, який уже існує.

Розподіл ролей задає не смак, а harness. У Claude Code запис у protected paths ніколи не схвалюється автоматично. Серед захищених шляхів — .git, .claude, .husky, .devcontainer, .vscode, .pre-commit-config.yaml, lefthook.yml, .mcp.json. У режимі dontAsk такий запис відхиляється, а правила permissions.allow його не відкривають: перевірка спрацьовує раніше за них. Без запитів туди пише лише bypassPermissions. Отже, конфігурацію, яка виконує код (хуки git) або розширює права агента (settings, MCP), пише людина.

Захист перевіряє запис файлів інструментами агента, а не те, що змінює запущена команда. В експерименті нижче обидва «вільні» прогони перевели git на хуки з репозиторію через core.hooksPath. Перший записав git config у свій scripts/setup.sh і запустив його, другий виконав git config напряму, бо моє правило Bash(git *) було надто широким. В обох випадках .git/config змінився без жодного запиту. Скрипти bootstrap рев'юйте так само, як settings, а git дозволяйте підкомандами (Bash(git add *), Bash(git commit *)).

02

Bootstrap-специфікаціяКонтракт, який перевіряють командами

Промпт «зроби репозиторій, готовий до агентів і CI» змушує модель ухвалити десяток рішень, які ви потім рев'юїте. Bootstrap-специфікація переносить ці рішення до вас. На пів сторінки в ній є п'ять блоків:

  1. Продукт — 3–4 рядки: вхід, вихід, коди виходу. Без них агент вигадає формат.
  2. Фіксований стек — мова, розкладка, інструменти і що заборонено («pip + venv, без uv, poetry, tox, Makefile»).
  3. Контракт репозиторію — пронумеровані пункти, кожен перевіряється командою зі свіжого клону: що робить setup.sh, які кроки в check.sh, точний склад ci.yml з версіями дій.
  4. Межі harness — що агент не може записати сам і куди класти чернетку.
  5. Done і поза межами — команда приймання, коміт; що не робити (Docker, матриця, поріг покриття).
## Repository contract — I will verify exactly this from a fresh clone
1. `scripts/setup.sh` creates `.venv` with python3.12, installs `requirements/dev.txt`
   with `--require-hashes`, then the package with `--no-deps -e .`.
2. `scripts/check.sh` runs `ruff check .`, `ruff format --check .`, `pytest -q` with `.venv/bin`
   tools; runs every step, then exits 1 if any failed. No network, no secrets.
3. `.github/workflows/ci.yml`: … `actions/checkout@v7`, `actions/setup-python@v7`
   (python 3.12, `cache: pip`, `cache-dependency-path: requirements/dev.txt`),
   `PYTHON=python scripts/setup.sh`, `scripts/check.sh`. Nothing else: CI logic lives in scripts.
4. Claude Code never auto-approves writes to `.pre-commit-config.yaml` or `.claude/` (protected
   paths), so write them as `bootstrap/pre-commit-config.yaml` and `bootstrap/claude-settings.json`;
   `scripts/install-agent-config.sh` copies them into place — a human runs it after review.

Специфікацію пишуть англійською, бо вона йде агентові як є. Повний текст (415 слів) лежить у console/bootstrap/bootstrap-spec.md. Версії дій вписано явно: без них модель обирає версії сама, і в обох вільних прогонах це були checkout@v4 і setup-python@v5 за поточної v7.

Як повторювати

Тримайте специфікацію в skill /bootstrap (6.1). Стек і контракт команди лежать у SKILL.md, а з аргументу береться лише абзац «Продукт». Скрипт перевірки зі свіжого клону (console/bootstrap/measure.sh) кладіть поруч: skill без приймання дає неперевірені звіти.

04

Одна перевірка на всіхcheck.sh, pre-commit і агент

Скрипт перевірки однією командою — єдине місце, де записано, що таке «зелено». Його викликають агент (як Done в AGENTS.md), Stop-хук (6.2), CI і людина перед PR. Друга копія списку перевірок, у YAML чи в інструкції, рано чи пізно розійдеться з першою. Так вийшло у free-1: check.sh і ci.yml перелічують ті самі п'ять інструментів окремо.

#!/bin/sh
# Lectern: повна перевірка без мережі й без моделі (ADR 0014)
set -u
cd "$(dirname "$0")/.."
PY=${LECTERN_PY:-.venv/bin/python}
failed=""
step() { name=$1; shift; echo "== $name: $*"; "$@" || failed="$failed $name"; }
step lint "$PY" -m ruff check .
step tests "$PY" -m pytest -q -p no:cacheprovider
step context "$PY" scripts/check_context.py
if [ -n "${LECTERN_BASE:-}" ]; then step trace "$PY" scripts/trace.py --require-refs "$LECTERN_BASE"
else step trace "$PY" scripts/trace.py; fi
step tasks "$PY" scripts/plan_tasks.py docs/specs/module-from-pdf/tasks.md
step mcp-contract "$PY" scripts/mcp_contract.py check
if [ -n "$failed" ]; then echo "FAILED:$failed"; exit 1; fi
echo "all checks passed"
  • Усі кроки, потім код виходу. Fail-fast показує агентові одну проблему за запуск. Скрипт, що доходить до кінця, показує всі, а це менше ітерацій циклу.
  • Команда перед кожним кроком (== tests: …): агент повторює лише впалий крок, не вгадуючи прапорців.
  • Один інтерпретатор з .venv, тобто версії з lock, ті самі, що в CI. Ruff 0.17.1 з lock знайшов у новому коді Lectern PLW1510 (subprocess.run без check=), і локально, і в CI він дасть ту саму відповідь.
  • Без мережі, секретів і моделі: ті самі результати на ноутбуці, у fork-PR і в агентному sandbox.

05

CI, що дзеркалить локальнеci.yml без власної логіки

CI дзеркалить локальне, коли кожен його крок — скрипт, який так само запускають людина й агент. Тоді червоний CI відтворюється однією командою, і агент лагодить його без доступу до логів GitHub.

on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  check:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          fetch-depth: 0 # trace.py читає трейлери Refs з git log
          persist-credentials: false
      - uses: actions/setup-python@5fda3b95a4ea91299a34e894583c3862153e4b97 # v7.0.0
        with:
          python-version: "3.12"
          cache: pip
          cache-dependency-path: requirements/ci.txt
      - run: scripts/setup.sh
        env: { PYTHON: python }
      - run: scripts/check.sh
        env:
          LECTERN_BASE: ${{ github.event_name == 'pull_request' && format('origin/{0}', github.base_ref) || '' }}
      - run: .venv/bin/pre-commit run --all-files --show-diff-on-failure
  lock:
    # checkout і setup-python ті самі; один крок:
      - run: scripts/lock.sh --check

Тести без секретів — вимога до коду, а не до CI. Для workflow з fork-PR GitHub не передає раннеру жодного секрету, крім GITHUB_TOKEN; для подій Dependabot секретів немає взагалі. Тест, якому потрібен ключ API, на таких PR падає або тихо пропускається. Тому моделі в тестах підробні (FakeClient, 2.5), а все, що справді ходить у мережу, — окремий workflow, не required.

Required status checks

Захист гілки або ruleset вимагає, щоб названі checks пройшли до злиття. Три факти з документації GitHub змінюють те, як пишуть workflow:

  • strict (гілка має бути актуальною з базовою) проти loose: loose пропускає PR, який після злиття ламається через несумісну зміну в базі;
  • назви jobs мають бути унікальними в усіх workflow, інакше результат неоднозначний і злиття блокується;
  • check зі статусом skipped вважається пройденим. Job, який на цьому PR не запустився через умову if:, дає зелений gate без жодної перевірки.

Тому в Lectern два jobs без умов, і обидва required. Правило для CODEOWNERS (8.3) прив'язує до перевірки людину, а required checks — машину.

actionlint і локальний прогін

LockfileДіапазони в pyproject, точні версії в lock

pyproject.toml задає сумісність (anthropic>=1.14,<2). Lockfile задає одне конкретне середовище: точні версії всіх транзитивних залежностей і sha256 кожного файла. Без нього агент у понеділок і CI у вівторок ставлять різні пакети. Тоді «у мене зелено» перестає щось означати, а помилка з'являється в чужому PR. З --require-hashes pip відмовляється ставити будь-що без піна і хеша. Саме це зупинило spec-1.

Квіз10 ситуацій

10 питань
1. Агент завершив bootstrap і пише: «scripts/setup.sh і scripts/check.sh проходять». Що зробити, перш ніж приймати?
Так. Приймання зі свіжого клону ловить те, що ховає вже наявний .venv: так spec-1 «пройшов» у своїй теці і впав у новій.
Повторний запуск у тій самій теці перевіряє той самий забруднений стан: старий .venv приховав непіннутий setuptools у spec-1. Код виходу каже правду лише про середовище, в якому скрипт запустили.
2. Required job integration має if: github.event_name == 'push'. Відкрили PR. Що з gate?
Так. За документацією required check має бути successful, skipped або neutral. Умову переносять у кроки, а job лишають безумовним.
GitHub зараховує skipped як пройдений статус і не ігнорує if. Тому зелений gate тут нічого не перевірив.
3. У claude -p --permission-mode dontAsk агент не може записати .claude/settings.json, хоча в allow є Edit(.claude/**). Чому і що робити?
Так. Перевірка protected paths спрацьовує до allow-правил; у dontAsk запис відхиляється, автоматично його дозволяє лише bypassPermissions.
Ні Write-правило, ні перезапуск не допоможуть: protected path перевіряється раніше за будь-які allow. Конфігурацію, що розширює права агента, переносить людина.
4. ci.yml і check.sh окремо перелічують ті самі інструменти. CI червоний, локально зелено. Перший крок?
Так. Дві копії списку перевірок і різні версії інструментів — найчастіша причина розбіжності. Одна копія прибирає її назавжди.
Повтор ховає детерміновану розбіжність, а матриця множить хвилини, нічого не пояснюючи. Причина — дві копії логіки і версії поза lock.
5. Тест ходить в API моделі з ключем із секретів. Контриб'ютори з fork кажуть, що CI на їхніх PR червоний. Що робити?
Так. Workflow з fork не отримують секретів, крім GITHUB_TOKEN. Тест, якому потрібен ключ, не може бути частиною обов'язкового gate.
pull_request_target запускає код fork із секретами базового репозиторію, і checkout v7 саме тому відмовляється таке робити без allow-unsafe-pr-checkout. Тест без секретів — властивість коду, а не налаштувань CI.
6. Команда: усі мають uv, CI на Linux, розробники на macOS і Windows. Який lock?
Так. uv.lock універсальний і комітиться; --locked падає, якщо lock застарів.
pip-compile пише lock під поточне середовище: збіг у Lectern — властивість конкретного набору, а не гарантія. pip freeze фіксує випадковий стан без хешів і зв'язку з pyproject.
7. actionlint дає 0 проблем, хоча в actions/setup-python@<SHA> вхід написано з помилкою. Чому?
Так. На @v6 та сама помилка знайдена, на @v7 і SHA — ні. Входи закріплених дій звіряють з їхнім action.yml.
Для setup-python@v6 actionlint 1.7.12 помилку у вході знайшов, тож входи він перевіряє, але лише для відомих версій. SHA і v7 у його каталог не входять.
8. У pre-commit ruff підключено через ruff-pre-commit rev: v0.17.1, а в lock — інша версія ruff. Наслідок?
Так. Дві версії інструмента — дві думки про той самий код. Локальний хук з .venv тримає одну версію з lock.
pre-commit ставить хук із rev у власне середовище і lock не читає. Між версіями ruff з'являються нові правила і змінюються типові налаштування, тож та сама зміна може пройти хук і впасти в check.sh.
9. Колега хоче почати bootstrap із CLAUDE.md, «щоб агент одразу знав правила», а скрипти написати потім. Що не так?
Так. Інструкції посилаються на команди, тому пишуться після кроків 2–4 і перевіряються скриптом контексту.
/init — лише один зі способів отримати чернетку. Порядок важить і в межах одного PR: агент працює з проміжним станом, і інструкція з неіснуючою командою відправляє його в глухий кут.
10. Вільні прогони дешевші на 37% і мають удвічі більше тестів. Навіщо тоді специфікація?
Так. Формат входу, коди виходу, версії дій, відсутній lock, хук через .git/config — усе це рішення агента. Специфікація переносить їх до вас.
Вільні прогони в свіжому клоні якраз пройшли, а впав spec-1; прогони зі специфікацією довші (41–43 ходи проти 23–28). Цінність — у тому, хто ухвалює рішення.
