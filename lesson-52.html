01

Цикл, а не промптКоли чотири фази окупаються

У настановах Anthropic базовий робочий процес Claude Code — чотири фази: Explore (читати без змін), Plan (детальний план), Implement (код, звірений із планом), Commit (коміт з описовим повідомленням і PR). Далі скорочено — EPCC. Механіку plan mode і сесій розібрано в уроці 4.3, ланцюжок spec → plan → tasks — у 8.1. Тут цикл розглядаємо як дисципліну: що є виходом кожної фази, за якою умовою її закривати і скільки це коштує.

Якщо дати Claude одразу кинутися в код, він може розв'язати не ту задачу. […] Якщо diff можна описати одним реченням, план пропустіть.

“Letting Claude jump straight to coding can produce code that solves the wrong problem. […] If you could describe the diff in one sentence, skip the plan.”

03

ЕкспериментB50 двічі: один промпт проти EPCC

Задача. BACKLOG B50 — реалізувати ADR 0013 з уроку 10.2: задачі lectern serve у data/service/jobs.db (sqlite3, WAL), власник — pid, задачі мертвого власника знову в черзі, задачі живого не чіпаємо, одноразовий імпорт jobs/*.json. Зачіпає стан, що переживає процес, і два процеси на одному каталозі — саме той випадок, де план має сенс.

Умови. Три копії канонічного Lectern, кожна — окремий git-репозиторій із гілкою b50-job-store і власним .venv. Реалізує claude-sonnet-5-5. В усіх прогонах однаковий allowlist без голого Bash (pytest, scripts/*, ruff, check.sh, git add/commit/diff/log), --permission-mode dontAsk, --setting-sources project --strict-mcp-config, Claude Code 2.1.302.

  • A1, A2 — один промпт: «Implement backlog item B50 (BACKLOG.md): the SQLite job store for lectern serve decided in docs/adr/0013-job-store-sqlite.md. Commit when done.»
  • B1 — EPCC: розвідка (Haiku, лише читання) → план (Sonnet, лише читання, з відповідями власника) → схвалення → реалізація в новій сесії за файлом плану.

Приховані тести написано до першого прогону; агенти їх не бачили. Це справжні процеси uvicorn зі справжнім create_app і фейковим агентом. Ідея лави взята з bench.py уроку 10.2.

  2. Розвідка знайшла саме цей клас. Розділ звіту «припущення одного процесу» перелічив усіх читачів store.jobs. План перетворив цей список на явні рішення: resume забирає чужу failed-задачу, свій pid на старті вважається мертвим, SSE чужої задачі віддає збережені події й завершується.

Межі виміру

B1 — один прогін, A — два. Це тенденція на одній задачі, а не закон. Рев'юер був сліпий, але відбір «підтверджено / ні» робив той самий власник, що схвалював план B1. Сирі дані — у console/: потоки подій, промпти, вердикти, проби.

Промпт вимагає п'ять розділів і «лише факти з file:line»: символи й усіх читачів store.jobs; як тести підміняють агента; обмеження з CLAUDE.md, docs/process.md і ADR, зокрема що ADR явно лишає невирішеним; припущення одного процесу, які ламає спільна база; питання до власника.

Цінність розвідки — питання. На кожне власник відповів одним рядком: рівень P1; атомарний claim між живими процесами — поза B50; задача мертвого власника повертається в чергу, історія й витрати лишаються; артефакти лишаються в jobs/<id>/; JSON-файли не видаляємо; тести мають іти й на Linux CI до 15 с. Ці дев'ять відповідей стали частиною промпту плану. Відкрите питання без відповіді агент закриє сам — здогадом.

Чому не вбудований Explore-субагент

Він дешевший для головного контексту (урок 5.2), але стартує без CLAUDE.md (урок 6.4). У нашому звіті розділ «Constraints» цитує правила з CLAUDE.md: трейлер Refs: лише для id з docs/spec/, заборону правити специфікацію під код, Done = check.sh. Субагент без CLAUDE.md цих рядків не побачив би. Коли проєктні правила впливають на рішення, розвідуйте окремою сесією з проєктними налаштуваннями.

Не вмикайте для розвідки на Haiku plan mode: він піднімає Haiku до Sonnet (урок 4.3). У нашому прогоні з --tools у modelUsage є лише claude-haiku-5-5.

План у 17 разів дорожчий за розвідку, бо Sonnet перевіряє кожну тезу звіту в коді. За ці гроші він знайшов чотири речі, яких не було ні в ADR, ні в промптах A:

  • tests/test_layout.py вимагає рядок у src/lectern/README.md для кожного нового модуля, а README поза рамкою файлів. Тому сховище лишилось у service.py, а не в новому jobstore.py.
  • Якщо в пам'яті лише власні задачі, resume після рестарту тихо зламається. A1 зламав його саме так.
  • Свій pid на старті означає, що старий власник мертвий: pid успадкував новий процес.
  • Не звільнений зомбі після SIGKILL досі відповідає на kill(pid, 0) як живий. Тому в тестах proc.wait() після кожного kill.

Чекпойнт. План повернув три питання. Власник схвалив усі три рішення і додав одне: рядок у BACKLOG для застарілих документів. Правка — п'ять рядків у файлі плану (console/plan/owner-edits.diff), а не повідомлення в чаті. Схвалений план закомічено першим комітом гілки, docs: B50 plan (approved by owner). Рев'юер PR бачить, що саме погоджено, і звіряє diff із цим, а не з власною уявою.

06

CodeМалі кроки, кожен перевірений

Реалізація — нова сесія, якій дали лише файл плану. Контекст розвідки й планування туди не тягнеться, що відповідає пункту меню «clear context and …» з уроку 4.3.

Implement the approved plan docs/plans/b50-job-store.md (backlog B50, ADR 0013), step by step.
- After each step run that step's verification command; do not start the next step while it fails.
- Touch only the files in the plan's Files table. If another file must change, do not change it:
  stop and explain why in your final report.
- Make the commits from the plan's Commits section, in order. Before each commit read `git diff --staged`.
- Done = both `scripts/check.sh` and `LECTERN_BASE=main scripts/check.sh` print `all checks passed`.

Перевірений крок — зміна, після якої агент запустив команду кроку, прочитав результат і не пішов далі на червоному. У потоці подій це видно: перший pytest B1 запустив після 5 правок і одного нового файлу, далі перевіряв перед кожним комітом. Тобто реальна гранулярність — три чекпойнти на три коміти, а не десять на десять кроків плану. A1 вперше запустив тести після 8 правок і 2 нових файлів, і це був увесь код фічі. Різниця не в тому, чи агент перевіряє, а в тому, скільки змін стоїть між перевірками: що їх менше, то дешевше знайти, яка з них зламала.

Дрейф від плану. Коли ADR став «Прийнято», check_context.py вимагав перегенерувати індекс docs/adr/README.md, а цього файлу в таблиці плану не було. B1 зупинився:

  docs/adr/README.md is stale: run check_context.py --write-index. Fixing it means
  regenerating docs/adr/README.md, which is not in the plan's Files table. I did not touch it.
  Please either allow that file (commit 3 grows by one regenerated file) or tell me to leave

result · num_turns 46 · 296,8 с · total_cost_usd 0.7769

A1 перегенерував той самий файл мовчки. Тут обидва результати однаково правильні, але слід рішення лишив лише один. Відповідь власника — «згенерований індекс іде в коміт 3» — коштувала 5 ходів і $0,099 через --resume. Правило на майбутнє: згенеровані файли, які зачепить гейт (індекси, lock, контракти), вносьте в таблицю файлів плану одразу.

Перевірено · 17.10.2026

Обидва підходи пробували редагувати service.py через python3 - <<'EOF': A1, A2 і B1 по одному разу, і кожного разу отримували відмову allowlist-а. Це саме той обхід правил Edit(...) і хука ruff, від якого docs/process.md забороняє голий Bash (урок 8.4). План не змінює звичок моделі — їх тримають дозволи.

07

CommitАтомарні коміти, трейлери, рев'ю diff

Атомарний коміт — одна ідея, яка сама проходить check.sh і має повідомлення з поясненням «чому». B1 розклав зміну на три такі коміти: сховище з імпортом; повторна черга з тестами процесів; документи. Кожен можна відкотити окремо. Коли сквошити: якщо проміжні коміти не проходять гейт або це шум («fix test», «ruff»), зведіть їх в один перед злиттям. Якщо кожен атомарний і зелений — лишайте: revert і bisect працюють з атомами. B1 сам зізнався, що check.sh на комітах 1–2 окремо не запускав. Отже, «кожен зелений» ще треба перевірити, а не повірити.

Трейлери — рядки Ключ: значення наприкінці повідомлення. У Lectern два: Refs: (вимога або none; перевіряє trace.py --require-refs, урок 10.3) і Co-Authored-By:, який Claude Code типово додає сам (налаштування attribution.commit). Усі п'ять комітів агентів (чотири з них зачіпають src/) вийшли такими:

zsh — ~/A1
$ git log -1 --format=%B | tail -4
Refs: none

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>

$ git log -1 --format=%B | git interpret-trailers --parse
Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
$ LECTERN_BASE=main scripts/check.sh 2>&1 | grep -E "ERROR|FAILED"
ERROR commit 385cfdf changes src/ without «Refs: <id>|none»: service: SQLite job store (ADR 0013, B50)
FAILED: trace
реальний вивід · git 2.50.1 · console/trailers-A1.txt

Блок трейлерів — це остання група рядків повідомлення. Порожній рядок між Refs: і Co-Authored-By: робить Refs: звичайним текстом. A1 і A2 звітували, що закомітили й check.sh зелений: вони запускали check.sh без LECTERN_BASE, а без нього трейлери не перевіряються. B1 мав у Done обидва гейти. Він знайшов причину, спробував переписати історію через git filter-branch, отримав відмову і зупинився. Повідомлення переписав власник, одним rebase -x. Виправлення — один блок наприкінці:

service: write the job row before the first await in submit

by_key() reads only jobs.db, so a job first saved by its first emit was
invisible during the cache gate: two requests with one Idempotency-Key
made two jobs (review of B50). ADR 0013 lists the known costs; B71.

Refs: none
Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>

Документація Claude Code каже, що ваші інструкції про атрибуцію в CLAUDE.md мають пріоритет над стандартним рядком. Тож правило «Refs: одразу над Co-Authored-By:, без порожнього рядка» місце в CLAUDE.md, а надійніше — в хуку commit-msg з git interpret-trailers --parse.

Рев'ю diff перед комітом: що шукати

Кожен пункт нижче — дефект, який справді був у наших diff-ах.

  1. Межі. git diff --name-only main проти таблиці файлів плану; без плану — проти того, що назвала задача (A2 не оновив статус ADR).
  2. Хто читав замінене. Кожен читач структури, яку ви замінили, — кандидат на регресію: store.jobs читали get, resume, events, by_key. Звідси resume → 409 в A1.
  3. Нові точки await і порядок записів. Що бачить другий запит між першим await і першим записом? Звідси гонка ключа в A2 і B1.
  4. Очікування зовнішнього стану. Цикл, що чекає на чужий процес, мусить мати умову виходу, коли той процес помер (SSE в A2).
  5. Припущення середовища. pid 1 у контейнері, macOS-шрифт у фікстурі (B57): «на моїй машині» в коді.
  6. Тест доводить свою назву? Видаліть фічу подумки: тест упаде? test_idempotency_key_is_shared_between_processes в A1 працює в одному процесі; рев'юер: «delete the child() call — the test still passes».
  7. Повідомлення. git interpret-trailers --parse показує ті трейлери, які бачитиме CI.

Сліпий рев'юер (той самий промпт для трьох diff-ів: «лише коректність, вимоги ADR, регресії, тести, що не доводять своєї назви; file:line і як відтворити») знайшов регресію resume, гонку і вічне SSE. Трейлерів він не помітив: їх видно в історії, а не в коді. Документація попереджає, що рев'юер, якого просять шукати прогалини, зазвичай їх знаходить, навіть коли робота нормальна. Тому ми рахували лише підтверджене пробою (console/review/) або читанням коду. Регресійний тест на гонку спершу впав на B1 (дві різні задачі), потім пройшов після виправлення в один рядок.

Квіз10 ситуацій

10 питань
1. Задача: додати один рядок логування в gate() у service.py. Як її вести?
Так. Правило з настанов Anthropic: diff в одне речення — план пропускаємо. Гейт лишається: тест або check.sh.
EPCC на B50 коштував у 2,1–2,5 раза більше за один промпт. На рядку логування ця надбавка нічого не купує. Розвідка без реалізації задачу не виконує. Правило: diff в одне речення — один промпт і команда перевірки.
2. У звіті розвідки написано: «resume, мабуть, теж читає store.jobs». Що робити до планування?
Так. Вихід розвідки — факти й питання. «Мабуть» не є ні тим, ні іншим. Саме читачі store.jobs вирішили долю resume у B50.
План B1 справді перевіряв тези, але це коштувало в 17 разів більше за розвідку. До того ж впевненість не те саме, що точність: plan mode піднімає Haiku до Sonnet, а здогад так і лишається здогадом. Потрібен file:line або питання власнику.
3. Агент зупинився: гейт вимагає перегенерувати docs/adr/README.md, а цього файлу немає в плані. Ваша відповідь?
Так. Зупинка на дрейфі — це правильна поведінка. Рішення власника лишає слід, а урок для плану в тому, що згенеровані файли гейтів належать до таблиці файлів.
Відкат статусу ADR підганяє результат під план, а не навпаки. Загальний дозвіл на будь-які файли знищує сам сенс межі. Власник вирішує конкретний випадок і виправляє шаблон плану.
4. Повідомлення коміту закінчується так: Refs: none, порожній рядок, Co-Authored-By: …. Що скаже trace.py --require-refs main?
Так. git interpret-trailers --parse бачить лише Co-Authored-By. Саме так червоніли всі коміти агентів у B50.
Git шукає блок трейлерів наприкінці повідомлення, і порожній рядок цей блок обриває. trace.py читає трейлери через git log --format=%(trailers…), тож Refs для нього не існує, і це помилка, а не попередження.
5. Чому розвідку B50 провели окремою сесією з проєктними налаштуваннями, а не вбудованим Explore-субагентом?
Так. Розділ «Constraints» звіту прямо спирається на CLAUDE.md. Субагент без нього їх би не побачив.
Explore читає будь-які файли й обирає глибину пошуку. Модель від цього вибору не залежить. Його обмеження в іншому: він стартує без CLAUDE.md і git status (урок 6.4), а тут правила проєкту впливали на рішення.
6. Приховані тести за текстом ADR пройшли всі три реалізації B50. Який висновок правильний?
Так. Resume після рестарту, pid 1, гонка на await, вічне SSE — нічого з цього ADR не називав. Їх знайшли розвідка (B1) і рев'ю.
Підтверджених дефектів у коді було 2 і 3 проти 1, тож «рівноцінні» не випливає з даних. Тести не погані: вони перевірили все, що обіцяли (база 2/6). Вони просто не могли бачити того, чого ніхто не назвав.
7. За планом кожен крок закінчується pytest. Агент зробив кроки 1–5 і лише тоді запустив тести: два червоні. Що втрачено?
Так. Цінність перевіреного кроку в малій кількості змін між перевірками. B1 мав три чекпойнти, A1 — один на весь код фічі.
Результат не той самий: замість «крок 4 зламав write path» маєте п'ять підозрюваних. Атомарність коміту — окреме питання, і її можна відновити розбиттям коміту. А от час на пошук причини вже витрачено.
8. Рев'юер у свіжому контексті знайшов 5 «проблем» у diff-і, який проходить усі тести. Як діяти?
Так. У B50 гонку ключа спершу відтворили тестом (червоний на B1), потім виправили одним рядком (зелений).
Документація попереджає: рев'юер, якого просять шукати прогалини, зазвичай їх знаходить, навіть коли робота нормальна. Тому «виправити все» веде до переускладнення, а «нічого» пропустило б регресію resume в A1. Фільтр — підтвердження.
9. Який коміт атомарний у сенсі цього уроку?
Так. Одна ідея, тести до неї, гейт проходить на цьому коміті, тож його можна відкотити або знайти bisect-ом окремо.
Атомарність вимірюється не розміром. Коміт «усе за сесію» змішує ідеї, а «fix test» лишає попередній коміт червоним, і такі пари перед злиттям зводять сквошем в один.
10. A1 записував задачу в базу одразу в submit, B1 — лише на першому emit. Чому це важливо?
Так. На шляху кешу між створенням задачі й першим записом стоїть await gate(). Регресійний тест із двома одночасними POST це відтворив.
Ідеться не про швидкодію й не про імпорт: jobs/*.json після B50 лише читають, один раз. Причина — ідемпотентність: старий by_key шукав у пам'яті, новий — лише в базі.
