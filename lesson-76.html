Домен 3 зводиться до питання «куди покласти». Пам'ять (CLAUDE.md, rules) Claude отримує як контекст, а не примусову конфігурацію — так прямо пише документація, і для блокування дії радить хук PreToolUse. Між завжди завантаженим CLAUDE.md і skill, який підвантажується на вимогу, різниця в тому, скільки коштує правило і хто вирішує його завантажити.

Інструкція проти примусу: одне слово в правилі

Те саме прохання «створи docs/note.md інструментом Write» у двох чистих репозиторіях, які відрізняються одним словом у deny-правилі.

zsh — perm-writ, потім perm-edit
$ cat .claude/settings.json
{"permissions":{"deny":["Write(docs/**)"]}}
$ claude -p "Create the file docs/note.md containing the single line: hello. Use the Write tool." --model haiku --setting-sources project --strict-mcp-config --permission-mode acceptEdits --output-format json > run.json
$ ls docs; jq -r ".permission_denials | length" run.json
note.md
0

$ cat .claude/settings.json
{"permissions":{"deny":["Edit(docs/**)"]}}
$ claude -p "…той самий промпт…" …ті самі прапорці… > run.json
$ ls docs; jq -r ".permission_denials | length" run.json
2
реальний вивід · Claude Code 2.1.302 · claude-haiku-5-5 · 18.10.2026 · $0,0025 і $0,0027 · команду другого прогону скорочено · каталог docs порожній, модель двічі спробувала Write і зупинилась

Файлові правила перевіряються лише як Edit(path) і Read(path): правило Write(docs/**) Claude Code приймає, але ніколи не застосовує (документація: з v2.1.210, з попередженням на старті інтерактивної сесії; у -p у stderr його не було). Правило без шляху — deny: ["Write"] — діє на рівні інструмента. Для іспиту з цього випливає ширше: «заборонити в CLAUDE.md» — не заборона, і навіть дозвіл — лише стільки, скільки покриває його синтаксис.

Пастка CI

В обох прогонах stderr містив Warning: no stdin data received in 3s, proceeding without it: -p не чекає діалогу, але читає stdin. У джобі без конвеєра додайте < /dev/null. Без -p те саме перенаправлення не допоможе — звідси дистрактор у зразках гайда.

Домен 4Промпти й структурований вивід

Домен 4 розводить три речі, які на практиці зливають: критерії (що повідомляти), форму (схема) і зміст (валідація після схеми). Схема зі strict компілюється в граматику: синтаксичних помилок не буде, але сума позицій може не збігатися з total, а значення — опинитися не в тому полі.

4.1 Design prompts with explicit criteria to improve precision and reduce false positivesКатегорії «повідомляй / пропускай» з визначенням кожної і прикладом коду на кожен рівень серйозності. Категорію з високою часткою хибних спрацювань тимчасово вимкнути, доки промпт для неї не покращено: вона підриває довіру й до точних категорій.«Будь консервативним», «лише high-confidence» — загальні слова точності не додають.12.2, 5.1
4.2 Apply few-shot prompting to improve output consistency and qualityІнструкції дають нестабільний формат — 2–4 цільові приклади; для неоднозначних випадків — з поясненням, чому обрано саме цю дію; приклади «це не проблема» проти хибних спрацювань; приклади різних структур документа проти порожніх обов'язкових полів.П'ятнадцять прикладів «на кожне формулювання» (модель копіює, а не узагальнює) або правила там, де бракує зразка формату.5.1, 5.3

4.1 + 4.3 + 4.4 в одному прогоні

CI-рев'ю зміни в invoice.py, де є три проблеми: цикл починається з індексу 1, знижка повертає дробові копійки, а коментар обіцяє округлення, якого немає. Промпт задає категорії «що повідомляти» і явно виключає стиль; рівні серйозності визначено через наслідок; схема вимагає detected_pattern.

Report ONLY:
1) bug: code that returns a wrong result for some valid input;
2) security: untrusted input reaching a shell, a path or SQL;
3) comment_contradicts_code: a comment or docstring whose claimed behaviour differs from what the code does.
Do NOT report naming, style, formatting or missing tests.
Severity: blocker = a wrong money amount for typical input; major = wrong result only for edge input; minor = misleading text, output still correct.

Усі три проблеми знайдено, ім'я змінної s (стиль) не згадано. Але один прогін — не вимір точності: другий рядок модель назвала major, хоча за нашим визначенням це blocker (будь-яка знижка дає дробові копійки — типовий вхід). 3.1 · Монорепо, у якого кореневий CLAUDE.md на 900 рядків

Кореневий CLAUDE.md монорепо містить стандарти Python-бекенду, Terraform, мобільного клієнта й процес релізу — 900 рядків. Агент у мобільному пакеті застосовує правила Python. Мейнтейнери кожного пакета знають, які стандарти їм потрібні. Найкращий крок?

  1. Розбити кореневий файл на .claude/rules/python.md, terraform.md, mobile.md без frontmatter — так правила стануть модульними.
  2. Винести стандарти в окремі файли, а в CLAUDE.md кожного пакета імпортувати через @ лише ті, що потрібні цьому пакету.
  3. Скоротити кореневий файл до 200 рядків, прибравши стандарти, які модель і так знає з навчання.
  4. Додати на початок кореневого файла інструкцію «застосовуй лише розділ, що відповідає поточному пакету».

Відповідь: B. @import у CLAUDE.md пакета — механізм, яким гайд пропонує вибірково підключати стандарти на основі знань мейнтейнера; CLAUDE.md пакета завантажується, коли агент працює в його теці.

  • A — rules без paths завантажуються на старті з тим самим пріоритетом, що й .claude/CLAUDE.md: модульність для людей є, для контексту нічого не змінилось.
  • C — проблема не в довжині, а в тому, що чужі правила лежать поруч; викинуті стандарти просто зникнуть.
  • D — покладається на здогад моделі, який розділ доречний; саме цього збою ми й позбуваємось.
3.2 · Персональний варіант командного skill

У репозиторії є командний skill /release (.claude/skills/release/). Розробниця хоче інший формат changelog для своїх релізів, не змінюючи нічого для колег. Що зробити?

  1. Додати в свій CLAUDE.local.md інструкцію «у /release використовуй мій формат changelog».
  2. Відредагувати .claude/skills/release/SKILL.md і додати цей файл у .git/info/exclude, щоб зміна не потрапила в коміт.
  3. Створити персональний skill з іншою назвою в ~/.claude/skills/, наприклад my-release, на основі командного.
  4. Додати в командний SKILL.md argument-hint: [format] і передавати свій формат аргументом.

Відповідь: C. Персональні варіанти — у ~/.claude/skills/ під іншою назвою: колеги їх не бачать, а командний skill лишається єдиним джерелом для всіх.

  • A — дві суперечливі інструкції в контексті; документація попереджає, що за конфлікту Claude може обрати будь-яку.
  • B — exclude не діє на файли, які git уже відстежує: правка з'явиться в git status і рано чи пізно в коміті.
  • D — змінює командний файл під одну людину; формат changelog — не параметр релізу для всіх.
3.3 · Правила для SQL-міграцій у дванадцяти сервісах

У монорепо 12 сервісів, у кожному migrations/*.sql. Правила zero-downtime (expand → contract, жодного DROP COLUMN в одному релізі з кодом) мають з'являтися лише тоді, коли Claude працює з міграціями, і автоматично охоплювати нові сервіси. Як?

  1. Створити skill migrations з описом «use when editing SQL migrations», щоб Claude підвантажував правила сам.
  2. Покласти CLAUDE.md з правилами в кожну з 12 тек migrations/ і додати пункт у шаблон нового сервісу.
  3. Додати розділ «Міграції» в кореневий CLAUDE.md із заголовком, який важко не помітити.
  4. Створити .claude/rules/migrations.md з paths: ["**/migrations/**/*.sql"].

Відповідь: D. Path-scoped правило завантажується, коли агент читає або редагує файл, що відповідає глобу, — у будь-якій теці, включно з сервісами, яких ще немає.

  • A — skill з'являється, коли модель вирішить, що він доречний: це не детерміноване завантаження за шляхом.
  • B — 12 копій розійдуться, а пункт у шаблоні забудуть; CLAUDE.md прив'язаний до каталогу, а не до типу файлу.
  • C — правило в контексті завжди, навіть у сесіях без міграцій; «помітність» не робить завантаження умовним.
3.5 · Конвертер дат, який щоразу трактує «12/10» інакше

Розробник просить конвертер старих дат курсу («12 жовт.», «2026-10-12», «12/10») в ISO. Тричі уточнював правила прозою, і щоразу «12/10» трактується по-іншому. Домен йому добре знайомий. Найефективніший наступний крок?

  1. Попросити Claude спершу поставити уточнювальні питання про формати (interview pattern), а потім писати код.
  2. Дати три пари «вхід → очікуваний вихід», включно з 12/10 → 2026-10-12, і тести на них, а далі ітерувати за падіннями.
  3. Переписати опис детальніше, з окремим абзацом для кожного формату й прикладом неоднозначності.
  4. Увімкнути вищий effort, щоб модель ретельніше міркувала над неоднозначними форматами.

Відповідь: B. Коли прозу трактують по-різному, 2–3 конкретні приклади і тести — найпряміший спосіб передати перетворення; тест ще й фіксує рішення для наступних змін.

  • A — interview pattern виявляє міркування, яких розробник не передбачив у незнайомому домені; тут він знає відповідь, бракує лише її однозначного запису.
  • C — проза вже тричі не спрацювала; четверта версія тієї самої форми — той самий ризик.
  • D — глибше міркування над неоднозначною вимогою не робить її однозначною.
3.6 · Знахідки рев'ю для inline-коментарів

CI-джоба публікує знахідки рев'ю як inline-коментарі через GitHub API. Зараз скрипт витягує їх regex-ом з markdown-відповіді claude -p і приблизно раз на 20 прогонів падає на іншій розмітці. Як виправити?

  1. Повторювати джобу до трьох разів, якщо regex не знайшов жодної знахідки.
  2. Додати в промпт «відповідай лише валідним JSON без markdown-обгортки» і розбирати відповідь json.loads.
  3. Перейти на --output-format stream-json і збирати текст відповіді з подій потоку.
  4. Запускати з --output-format json --json-schema '<схема знахідок>' і читати поле structured_output.

Відповідь: D. --json-schema дає вихід, перевірений на відповідність схемі, в окремому полі structured_output — без парсингу тексту.

  • A — «немає знахідок» буває валідним результатом; повтор маскує збій формату і тричі оплачує той самий ризик.
  • B — інструкція не гарантує формату; це найнижчий рівень гарантій.
  • C — змінює транспорт, але не форму тексту, який генерує модель.
4.1 · Серйозність знахідок «пливе»

Той самий тип дефекту — розіменування можливого None — рев'ю-бот в одному PR позначає major, в іншому minor. У промпті визначено: «major — серйозна проблема, minor — незначна». Що дасть узгоджену класифікацію?

  1. Явні критерії кожного рівня через наслідок і конкретний приклад коду для кожного рівня.
  2. Шкала від 1 до 10 замість трьох рівнів, щоб модель могла точніше виразити серйозність.
  3. Класифікувати кожну знахідку тричі й брати медіану, щоб згладити випадкові коливання.
  4. Додати до кожної знахідки впевненість і відкидати ті, де вона нижча за 0,7.

Відповідь: A. Нестабільність походить із розмитої межі між рівнями; явні критерії з прикладом коду на кожен рівень цю межу задають.

  • B — дрібніша шкала з тими самими розмитими межами дає більше розкиду, а не менше.
  • C — утричі дорожче і стабілізує середнє, але не визначає, де закінчується major.
  • D — відсіює знахідки, а не класифікує їх; самооцінка впевненості не відкалібрована.
4.2 · Пауза послуги чи розірвання договору

Агент підтримки інтернет-провайдера має інструменти pause_service і cancel_contract з детальними описами меж. На запити на кшталт «хочу відпочити від вашого інтернету на літо» він у чверті випадків обирає cancel_contract. Що додати насамперед?

  1. П'ятнадцять–двадцять прикладів різних формулювань запиту на паузу, щоб покрити всі варіанти.
  2. Класифікатор намірів перед агентом, який вмикає лише один з двох інструментів.
  3. Три-чотири приклади неоднозначних запитів із поясненням, чому обрано паузу, а не розірвання, і один — коли справді розірвання.
  4. Правило в системному промпті «ніколи не викликай cancel_contract без прямого слова "розірвати"».

Відповідь: C. Описи вже детальні, тож бракує демонстрації судження на межі. Цільові приклади з поясненням вибору дозволяють узагальнити на нові формулювання, а контрприклад не дає перегнути в інший бік.

  • A — масив однотипних прикладів модель копіює, а не узагальнює, і платить за них токенами в кожному запиті.
  • B — інфраструктура до того, як спробували приклади; класифікатор ламається на тих самих неоднозначних запитах.
  • D — ключове слово блокує законні розірвання, сформульовані інакше («закрийте мій рахунок»).
4.3 · Модель вигадує LinkedIn

Витяг даних із резюме за схемою зі strict: true. Поле linkedin_url — обов'язковий рядок. У 30% резюме LinkedIn немає, і для них модель повертає правдоподібні, але вигадані адреси. Як виправити?

  1. Додати в схему pattern: "^https://www\\.linkedin\\.com/in/", щоб модель не могла повернути довільний рядок.
  2. Лишити поле обов'язковим, але додати в промпт «нічого не вигадуй».
  3. Перевіряти кожну адресу HTTP-запитом і повторювати витяг, доки сторінка не відкриється.
  4. Зробити поле nullable і в його описі вказати: null, якщо в документі адреси немає.

Відповідь: D. Обов'язкове поле змушує модель щось туди покласти; nullable дає чесний варіант «немає в джерелі».

  • A — вигадані адреси якраз відповідають шаблону; граматика гарантує форму, не правдивість.
  • B — інструкція конфліктує зі схемою, яка вимагає значення; схема перемагає.
  • C — повтор не створить відсутнього факту, а відкрита сторінка може належати іншій людині.
4.4 · Третина знахідок відхилена, але невідомо яких

Розробники відхиляють 35% знахідок рев'ю-бота. Знахідки зберігаються як {file, line, severity, issue}. Команда хоче системно знайти, які конструкції коду породжують хибні спрацювання. Що додати?

  1. Поле confidence і поріг відсікання, налаштований так, щоб відхилених стало менше 10%.
  2. Поле detected_pattern у кожній знахідці і звіт відхилень у розрізі цього поля.
  3. Обов'язковий коментар розробника з причиною відхилення у вільній формі.
  4. Друге рев'ю тією ж моделлю, яке має підтвердити знахідку перед публікацією.

Відповідь: B. detected_pattern перетворює відхилення на дані, які можна згрупувати: видно, що, наприклад, broad_except_in_cli відхиляють у 90% випадків, і саме цю категорію треба переписати в промпті.

  • A — підганяє поріг під метрику, не пояснюючи, що саме хибне; самооцінка не відкалібрована.
  • C — вільний текст важко агрегувати, а заповнюють його неохоче й непослідовно.
  • D — подвоює вартість і несе той самий упереджений погляд, не показуючи патерну.
4.5 · SLA 36 годин і батч до 24 годин

Договір: результат витягу — не пізніше ніж за 36 год після надходження документа. Обробка йде через Message Batches (до 24 год, без гарантованої затримки). Близько 2% запитів падають і потребують повторної відправки. Яка стратегія гарантує SLA?

  1. Один батч на добу о 00:00, бо більшість батчів завершується протягом години.
  2. Батч кожні 12 год; невдалі запити — у наступний батч за custom_id.
  3. Батч кожні 6 год; невдалі запити одразу повторно через синхронний API за custom_id.
  4. Батч кожні 6 год; невдалі запити — у наступний батч разом із новими документами.

Відповідь: C. Найгірший випадок: документ чекає до 6 год відправки + 24 год обробки = 30 год, лишається 6 год на синхронний повтор. Будь-який повтор через батч додає ще до 24 год.

  • A — до 24 год очікування + до 24 год обробки = 48; «зазвичай за годину» — не гарантія.
  • B — 12 + 24 = 36 уже без запасу, а повтор у наступному батчі виводить за SLA.
  • D — 6 + 24 + 6 + 24 = 60 год для невдалого документа.
5.1 · Замовлення на 46 полів

Агент підтримки викликає lookup_order, який повертає 46 полів на замовлення; для рішення про повернення потрібні 5 (статус, дата доставки, сума, спосіб оплати, позиції). Клієнт питає про шість замовлень, і до кінця розмови агент плутає дати. Що змінити?

  1. Частіше запускати компакцію розмови, щоб старі результати інструментів стискались у підсумок.
  2. Обрізати результат lookup_order до потрібних полів у коді, до того як він потрапить у контекст.
  3. Переносити повні результати інструментів у кінець промпту, щоб уникнути ефекту lost in the middle.
  4. Додати в системний промпт «зважай лише на статус, дату доставки, суму, спосіб оплати і позиції».

Відповідь: B. 41 нерелевантне поле на замовлення множиться на кожен виклик і забирає увагу й токени; обрізати треба до того, як воно накопичиться.

  • A — компакція стискає вже накопичене і при цьому може загубити якраз дати й суми.
  • C — переставляє той самий обсяг, не зменшуючи його.
  • D — поля все одно лежать у контексті; інструкція «не зважай» не звільняє ні токенів, ні уваги.
5.2 · Політика мовчить про випадок клієнта

Клієнт мобільного оператора їде на рік на навчання за кордон і просить заморозити тариф на 12 місяців. Політика описує заморозку лише до 3 місяців за медичною довідкою і про інші підстави не каже нічого. Агент технічно може оформити заморозку на будь-який строк. Що він має зробити?

  1. Ескалювати людині: політика не покриває цей випадок, а рішення про виняток — не рівень агента.
  2. Оформити заморозку на 3 місяці як найближчий дозволений варіант і повідомити клієнта.
  3. Відмовити, бо політика прямо дозволяє заморозку лише з медичної причини.
  4. Оцінити роздратування клієнта й ескалювати, лише якщо тон стане різко негативним.

Відповідь: A. Мовчання політики — прогалина, а не дозвіл і не заборона; гайд прямо називає прогалини й винятки тригерами ескалації.

  • B — вибір «за аналогією» підміняє рішення, яке агентові не делеговано, і клієнт отримує не те, що просив.
  • C — трактує мовчання як заборону; рішення про виняток теж належить людині.
  • D — тон не корелює зі складністю випадку; ескалація за sentiment — ненадійний проксі.
5.4 · Три години в legacy-монорепо

Агент досліджує legacy-монорепо (≈2 млн рядків), щоб спланувати міграцію платежів. Після трьох годин в одній сесії на питання «хто викликає RefundService?» відповідає «зазвичай у таких системах це робить контролер…», хоча годину тому сам знайшов конкретні класи. Що робити?

  1. Перейти на модель з найбільшим вікном і завантажити ключові каталоги цілком на старті.
  2. Продовжити в цій сесії, попросивши агента пригадати знайдене раніше і відповідати конкретно.
  3. Підняти effort до максимуму, щоб агент ретельніше перевіряв відповіді перед видачею.
  4. Записувати знахідки у scratchpad-файл, окремі питання віддавати субагентам, а наступну фазу починати з підсумком попередньої.

Відповідь: D. Це деградація довгої сесії: «типові патерни» замість конкретних класів. Знахідки мають жити у файлі, розвідка — в ізольованих субагентах, а кожна фаза — починатися з короткого підсумку.

  • A — 2 млн рядків не вміщуються навіть у 1M токенів, а довший контекст погіршує використання фактів із середини.
  • B — «пригадай» звертається до того самого переповненого контексту, який і став причиною.
  • C — більше міркувань над деградованим контекстом не повертає загублених фактів.
5.6 · 31% чи 24%

Дослідницький конвеєр готує огляд ринку. Субагент веб-пошуку: «частка лідера — 31%» (галузевий звіт, 2024). Субагент аналізу документів: «24%» (опитування, 2026). Синтезатор пише «близько 27%». Як мало бути влаштовано?

  1. Синтезатор бере свіже значення і в примітці згадує, що раніше оцінка була вищою.
  2. Координатор запускає третій субагент знайти «остаточну» цифру і використовує лише її.
  3. Субагенти повертають claim → джерело з уривком і датою; синтез показує обидва значення з атрибуцією і позначає, що різниця може бути часовою.
  4. Синтезатор зводить розбіжні цифри до діапазону 24–31% без джерел, щоб звіт був лаконічним.

Відповідь: C. Мапа claim → джерело з датою дозволяє не загубити атрибуцію при синтезі й побачити, що 2024 і 2026 — різні моменти, а не суперечність.

  • A — «свіже» не означає «правильне»: інша методологія (звіт проти опитування) теж пояснює різницю, а вибір довільний.
  • B — третє значення може розійтися з обома, а відкинуті джерела зникають зі звіту.
  • D — діапазон без атрибуції ховає, звідки кожна межа і чому вони різняться.

1. (3.1) Тімлід платіжного монорепо на 40 розробників записав правило «гроші — лише Decimal, ніколи float» у свій ~/.claude/CLAUDE.md і переконався, що Claude його виконує. Новий розробник за тиждень отримує від Claude код із float. Що виправить це для всієї команди?
Так. Інструкції в ~/.claude/CLAUDE.md бачить лише їхній автор — git їх не переносить. Стандарт для всіх живе у файлі репозиторію; /memory допоможе переконатися, що його завантажено.
Копії в домашніх теках розходяться, а новачки їх не отримають. settings.local.json особистий і не в git, а дозволи керують інструментами й шляхами, а не типами в коді. Skill з'являється на розсуд моделі, тоді як універсальний стандарт має бути в контексті завжди.
2. (3.2) Командний /audit-deps аналізує lock-файли 30 сервісів і друкує довгий звіт. Після нього розробники продовжують фічу в тій самій сесії, але агент «забуває» план: дві третини контексту зайнято звітом. Що змінити в skill?
Так. context: fork запускає skill в окремому субагенті: його розвідка і проміжний вивід не потрапляють у головну розмову, туди приходить лише результат.
allowed-tools дозволяє інструменти без запиту, а не обмежує їх, і на обсяг звіту не впливає. CLAUDE.md зробить інструкції постійними, а звіт однаково ляже в головний контекст. /compact стискає з втратами — план фічі може зникнути разом зі звітом.
3. (3.4) У Lectern дві задачі: (1) у save_quiz додати перевірку, що answer — ціле від 0 до 3, стек-трейс із продакшну вказує на рядок; (2) замінити бібліотеку витягу тексту з PDF: 23 файли, два кандидати з різною обробкою таблиць і ліцензіями. Як вести?
Так. Задача (1) — одна зрозуміла правка з відомим місцем. У (2) є вибір між підходами з різними наслідками і багато файлів — класичний випадок для plan mode, а затверджений план далі виконується напряму.
План для однорядкової правки — зайва церемонія. Детальний промпт не замінить розвідки, коли ще треба обрати між кандидатами. Критерій — не «продакшн чи ні», а кількість рішень і файлів: у (2) їх найбільше.
4. (3.6) CI-рев'ю перезапускається на кожен новий коміт у PR, і в PR накопичуються дублікати тих самих зауважень. Розробники перестали їх читати. Що змінити?
Так. Попередні знахідки в контексті дозволяють відрізнити нове від уже сказаного і виправлене від невиправленого.
Один прогін пропускає проблеми з пізніших комітів. Фільтр за впевненістю не прибирає повторів і не підвищує точність. Видалення коментарів знищує обговорення і статус виправлень, а невиправлене знову з'являється як нове.
5. (4.1) Рев'ю-бот у 40% PR пише «коментар не відповідає коду», і розробники почали ігнорувати всі його знахідки, зокрема справжні баги. Що зробити насамперед?
Так. Явний категорійний критерій замість розмитого і тимчасове вимкнення шумної категорії повертають довіру до решти знахідок, поки промпт для неї покращують.
«Будь консервативним» не підвищує точності — гайд називає це прямо. Модель не винна в розмитому критерії. Згорнутий шум лишається шумом, і довіра до інших категорій не повертається.
6. (4.3) Конвеєр на Claude Haiku 5.5 обробляє рахунки трьох типів (інвойс, кредит-нота, акт); тип наперед невідомий, на кожен є свій інструмент-екстрактор. Як гарантувати, що відповідь — завжди виклик одного з них з аргументами за схемою?
Так. any вимагає викликати один з інструментів, strict — аргументи за схемою; Haiku 5.5 примусовий виклик приймає. На Opus 5.5 чи Sonnet 5.5 any дав би 400 — там auto + strict з перевіркою виклику або JSON outputs.
auto дозволяє відповісти текстом. Примус extract_invoice застосує схему інвойсу до кредит-ноти. required для полів, яких у документі цього типу немає, змусить модель їх вигадати.
7. (4.4) Pydantic-валідація витягу з рахунків: (1) у 6% сума позицій не дорівнює total, хоча в документі все сходиться; (2) у 3% порожнє поле «номер договору», бо в рахунку лише «згідно з договором, наданим окремо». Який план?
Так. Повтор із конкретною помилкою виправляє структурні й арифметичні збої витягу. Номера договору в документі немає, і жоден повтор його не створить.
Без тексту помилки модель не знає, що виправляти. Strict-схема прибирає синтаксичні помилки, а не семантичні. «Обов'язковий» номер, якого немає в джерелі, — пряме запрошення його вигадати.
8. (4.5) Щотижневий аудит 8 000 договорів має бути готовий у понеділок о 9:00; у реальному часі на нього ніхто не чекає. Для висновку модель потребує даних реєстру, які зараз отримує інструментом lookup_registry посеред відповіді. Як здешевити?
Так. Задача не блокує людей, тож батч дає −50%. Інструмент посеред запиту батч не виконає, тому дані реєстру готують заздалегідь; невдалі запити повторюють за custom_id.
Батч не підтримує багатокроковий tool use в одному запиті. Строку «понеділок, 9:00» вистачає з запасом, якщо відправити батч щонайменше за 24 год, тож синхронний API — лише переплата. Результати батча приходять у довільному порядку.
9. (4.6) Агент згенерував міграцію бази, і в тій самій сесії його попросили «уважно перевір свою роботу». Він нічого не знайшов, а рецензент-людина знайшла два дефекти. Що змінити в процесі?
Так. Незалежний рецензент не несе міркувань автора, тому ставить під сумнів те, що автор вважав вирішеним.
Усе інше — самоперевірка: модель зберігає контекст генерації й рідше сумнівається у власних рішеннях. Гайд прямо ставить незалежний екземпляр вище за self-review і extended thinking.
10. (5.1) Агент підтримки, близько 40 ходів: на третьому клієнт назвав суму 1 249 грн, номер замовлення і що чекає повернення до п'ятниці. Після автоматичного підсумку історії агент пише «повернемо кошти найближчим часом» і називає не те замовлення. Що змінити?
Так. Транзакційні факти живуть в окремому блоці, якого підсумовування не торкається, і потрапляють у кожен запит.
Рідше підсумовування відкладає втрату, але не скасовує її. Без підсумку результати інструментів однаково розпухають, а факт із середини довгого контексту використовується гірше. Прогресивне підсумовування стискає саме числа й обіцянки, хоч би що просили в промпті.
11. (5.3) Субагент збору матеріалів для Lectern не дістав два PDF з п'яти (таймаут сховища), а в третьому пошук за темою нічого не знайшов. Як повідомити координатора?
Так. Координатор бачить, що два джерела недоступні (можна повторити чи взяти інші), а одне доступне, але порожнє (повторювати марно), і продовжує з анотацією прогалин.
Порожній «успіх» перетворює таймаут на «нічого немає». Загальний статус ховає різницю між недоступним і порожнім. Виняток зупиняє весь модуль, хоча часткових даних достатньо, щоб продовжити.
12. (5.5) Витяг полів зі страхових заяв: загальна точність 97% на 2 000 перевірених документах. Керівник пропонує прибрати людську перевірку там, де модель повідомляє впевненість понад 0,9. Що зробити спершу?
Так. Середні 97% можуть ховати провал на одному типі документа чи полі; поріг впевненості має сенс лише після калібрування, а стратифікована випадкова вибірка й далі міряє помилки серед high-confidence.
Скарги — запізнілий і неповний сигнал, а середнє ховає сегменти. Точніша шкала не робить самооцінку відкаліброваною. Некалібрована самооцінка не може вирішувати, що перевіряти людині.
