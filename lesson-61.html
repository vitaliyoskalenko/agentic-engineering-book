Observability: трасування агентів і моніторинг

Агентна система, яку видно лише через логи, відповідає на «що сталося», але не на «де пішли час і гроші» і «як часто каскад ескалює». Траса однієї задачі Lectern від HTTP-запиту до гейта, з модельними запитами Claude Code всередині, показала прихований п'ятий запит на кожну сесію і 15-секундний холодний старт, а escalation rate 0 з 6 виявився інтервалом від 0 до 39%.

Після уроку ви зможете

  • скласти дерево спанів агентної задачі й перелік полів для кожного рівня: запуск, виклик моделі, інструмент, результат;
  • увімкнути OpenTelemetry-експорт Claude Code, прочитати його метрики, події й спани та знати, що в них потрапляє за замовчуванням;
  • передати trace id через чергу і через межу процесу (Agent SDK → CLI), щоб одна задача була однією трасою;
  • інструментувати власний агентний сервіс за GenAI semantic conventions з нульовою ціною у вимкненому стані і тестами на in-memory exporter;
  • рахувати метрику-частку (escalation rate) з правильним знаменником і довірчим інтервалом, обирати семплінг і не відправляти вміст у телеметрію.

Журнал сесії (2.3) пояснює одну сесію, статус-рядок і /usage (4.3) — витрати однієї людини. Сервіс, який крутить сотні агентних запусків, ставить інші питання, і кожне потребує свого сигналу:

02

Три сигнали OpenTelemetryТраси, метрики, журнали і як їх зшити

  • Траса (trace) — дерево операцій однієї логічної дії; вузол — спан (span): назва, початок, тривалість, атрибути, статус, батько. Для агента траса — один запуск, спани — запити до моделі й виклики інструментів.
  • Метрика — агрегат: лічильник, гістограма. Дешева, не семплюється, придатна для алертів, але тримає лише атрибути з малою кардинальністю: модель, вердикт, стадія. Id задачі в атрибуті метрики — кожна задача стає окремим часовим рядом.
  • Журнал (logs) — окремі записи з довільними полями. Подія (event) — іменований структурований запис: у Claude Code це claude_code.api_request, у Lectern — attempt.end. Подія з trace_id веде з журналу прямо в трасу.

Траса цілісна, лише коли trace id перетинає кожну межу. Стандарт — W3C Trace Context: заголовок traceparent: 00-<trace-id 32 hex>-<span-id 16 hex>-<flags>. У Lectern три межі:

  1. Клієнт → сервіс: вбудований OTel FastAPI читає traceparent запиту POST /quizzes.
  2. Запит → воркер: черга asyncio.Queue контекст не переносить; його треба зберегти при постановці й відновити у воркері як батька lectern.job.
  3. Сервіс → Claude Code: Agent SDK запускає CLI дочірнім процесом і кладе в його оточення TRACEPARENT активного спану. У режимах -p і SDK CLI читає цю змінну, і його claude_code.interaction стає дитиною вашого спану. Інтерактивні сесії вхідний TRACEPARENT ігнорують.

Статус конвенцій — Development, тобто назви можуть змінитися. З 2026 року вони живуть в окремому репозиторії open-telemetry/semantic-conventions-genai (створено 05.05.2026, релізів ще немає). Сторінки gen-ai на opentelemetry.io лише посилаються туди. gen_ai.system позначено застарілим на користь gen_ai.provider.name.

Дві пастки, які видно на справжніх даних:

  • Токени з кешем. input_tokens в API Anthropic не містить кешованих токенів, а gen_ai.usage.input_tokens за конвенцією містить. Перший запит нашого прогону Claude Code: input_tokens: 2, cache_read_tokens: 13873, cache_creation_tokens: 4116. Скопіюйте поле 1:1 — і дашборд покаже 2 вхідні токени там, де модель прочитала 17 991. Claude Code сам gen_ai.usage.* не ставить і в документації пояснює, як скласти три поля.
  • Дрейф назв. Документація Claude Code для claude_code.llm_request перелічує gen_ai.system, а версія 2.1.302 у нашому прогоні пише і gen_ai.system, і gen_ai.provider.name, і gen_ai.conversation.id. Тому в Lectern усі назви gen_ai.* зібрано в одному модулі: перейменування конвенції — одна правка, а не пошук по коду.

06

Codex, Cursor і бекендиХто що експортує

Змінні оточення, OTLP gRPC або HTTP, експортер console, otlp або prometheus. Три сигнали, спани — бета. Агент на Agent SDK експортує те саме, бо всередині той самий CLI. Для SDK документація забороняє console: експортер пише в stdout, а stdout — канал протоколу SDK.

~/.zshrc або managed settings
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
з офіційної документації Claude Code (Monitoring) · експорт у console перевірено прогоном вище

Секція [otel] лише в користувацькому ~/.codex/config.toml: проєктний .codex/config.toml її ігнорує. Типово exporter = "none": події записуються, але нікуди не йдуть. Події codex.conversation_starts, codex.api_request, codex.user_prompt, codex.tool_decision, codex.tool_result; промпт редагується, доки не ввімкнено log_user_prompt. Окремо є trace_exporter, а metrics_exporter типово statsig — анонімна статистика для OpenAI, яку вимикає [analytics] enabled = false.

Локального експорту в Cursor немає. OpenTelemetry Export (план Enterprise) шле дані команди з серверів Cursor у ваш публічний OTLP/HTTP-колектор. Метрики cursor.token.usage, cursor.tool.calls, cursor.cost.usage доставляються at-most-once, журнали — at-least-once, з дедуплікацією за cursor.event.id. Трас немає, ретроспективних даних теж. Вміст розмов — окрема опційна група подій. Admin API і Analytics API (теж Enterprise) віддають використання й витрати за запитом.

Куди відправляти: будь-який бекенд, що приймає OTLP. Спеціалізовані LLM-бекенди розуміють gen_ai.* і показують трасу як розмову:

  • Черга: submit зберігає telemetry.capture(), воркер відкриває lectern.job з ним як батьком. traceparent клієнта стає коренем траси задачі, і trace_id повертається в GET /quizzes/{id}.
  • FastAPI 0.143 має вбудований OTel (FastAPI(telemetry=…)). Ми передаємо йому свої провайдери, не глобальні, вимикаємо його журнали й спани на кожну залежність і виключаємо GET: опитування статусу дало б сотні однакових спанів на задачу.
  • Інструменти виконуються в процесі Lectern (MCP in-process), тож execute_tool — справжня тривалість з підсумком аргументів: quote.words, quiz.items, але не текст.
  • B35: lectern.escalations і знаменник lectern.cascade_jobs (лише задачі model: auto, що викликали модель; кеш не рахується). GET /stats рахує те саме з SQLite-журналу задач, без OTel-бекенда, з 95% інтервалом Вілсона.
  • Тести: InMemorySpanExporter + InMemoryMetricReader і фейковий агент: дерево спанів, traceparent через чергу, ескалація як подія плюс лічильник, жодного речення лекції в спанах і журналі, семплінг з OTEL_TRACES_SAMPLER; окремий процес перевіряє, що вимкнений сервіс не вантажить opentelemetry.sdk.

Приватність, семплінг, зберіганняТелеметрія — ще одне сховище даних

Колектор і бекенд — новий отримувач даних, і для нього діють ті самі класи даних, що в ADR 0005. Конвенції GenAI кажуть прямо: інструкції, повідомлення й відповіді моделі інструментації не повинні записувати за замовчуванням, лише за явним увімкненням; у продакшні вміст радять тримати в окремому сховищі з власним доступом і класти в спан посилання.

Не пишемо ніколи

  • текст лекції, питання, варіанти, цитати;
  • вміст промптів і відповідей, тіла запитів API;
  • id задачі в атрибутах метрик (кардинальність);
  • секрети в заголовках експортера в репозиторії.

Пишемо

  • id задачі й лекції, sha256-префікс тексту, довжини;
  • токени, вартість, тривалість, TTFT, stop_reason;
  • вердикти, причини, ескалації, рішення дозволів;
  • trace_id у журналі й відповіді API.

Семплінг. Head sampling вирішує на старті траси, ще до результату: OTEL_TRACES_SAMPLER=parentbased_traceidratio з OTEL_TRACES_SAMPLER_ARG=0.1 залишить 10% трас, і рідкісні провали зникнуть пропорційно. Tail sampling вирішує після того, як зібрано всю трасу (процесор колектора). Правило для Lectern (B150): усі траси з error.type або ескалацією плюс 10% чистих. Метрики не семплюються ніколи, тому escalation rate і вартість рахуються з лічильників і журналу задач, а не з трас.

Зберігання. Траси потрібні для розбору — 14 днів; метрики — для трендів, 13 місяців; журнал задач — за політикою даних сервісу. Це гіпотези, переглядаються після пілоту. Чим коротше зберігання, тим менша шкода, якщо в атрибут все ж потрапить щось зайве.

ПрактикаПеревірте терміни

11

Квіз10 питань

10 питань
1. Задача Lectern іде 29 с. Модельні запити в трасі разом дають 12 с, інструменти й гейт — 0,5 с. Що робити першим?
Так. Більша частина часу лежить поза модельними спанами. У прогоні уроку це був холодний старт CLI: 15,7 с між початком спроби і першим запитом.
Модель тут — 12 с з 29, а інструменти — соті частки секунди. Найбільший шматок — проміжок між спанами: старт CLI, черга, завершення процесу. Його й видно в трасі як «порожнє» місце.
2. Спан запиту показує input_tokens: 2, cache_read_tokens: 13873, cache_creation_tokens: 4116. Що записати в gen_ai.usage.input_tokens?
Так. Конвенції GenAI: gen_ai.usage.input_tokens включає всі вхідні токени, кешовані теж; деталі — у cache_read/cache_write як підмножини.
В API Anthropic input_tokens не містить кешу, а в конвенції — містить. Деталізація кешу — підмножини загального числа, а не заміна. Сума: 2 + 13 873 + 4 116.
3. Сервіс на Agent SDK. Хтось додав в оточення OTEL_TRACES_EXPORTER=console і CLAUDE_CODE_ENABLE_TELEMETRY=1, «щоб бачити спани». Що станеться?
Так. SDK читає stdout дочірнього CLI як потік повідомлень. Документація забороняє console для SDK і радить локальний OTLP-колектор.
CLI не відрізняє «режим SDK» для експортера: console пише в stdout, а stdout CLI — це канал, з якого SDK читає повідомлення. Тому Lectern передає CLI CLAUDE_CODE_ENABLE_TELEMETRY=0, якщо агентна телеметрія не замовлена.
4. Спан lectern.job відкрито в обробнику POST /quizzes, а агент працює у воркері черги. Що побачите в бекенді?
Так. Воркер створено при старті, і контекст запиту через asyncio.Queue він не отримує. Контекст треба зберегти при постановці й відкрити спан у воркері з ним як батьком.
contextvars копіюються в задачу в момент її створення, а воркер створено при старті сервісу, ще до запиту. Дитина, що живе довше за батька, OTel допускає. Проблема саме в розриві контексту на черзі.
5. За тиждень каскад отримав 6 задач і жодної ескалації. Продакт пропонує прибрати Sonnet зі сходинок. Відповідь?
Так. Частка без інтервалу на малій вибірці нічого не доводить. Інтервал Вілсона для 0/6 — 0–0,39.
«0%» на шести задачах сумісне і з 0%, і з 39% ескалацій. «Якість важливіша» — не аргумент без даних: каскад якраз і купує якість лише там, де гейт не пройдено.
6. Потрібно ловити всі провалені задачі, а зберігати лише 10% трас. Який семплінг?
Так. Лише tail sampling бачить результат траси до рішення.
Head sampling вирішує на старті, коли результат ще невідомий, тож провали відкидаються з тією самою ймовірністю 90%. Лічильник скаже, скільки провалів було, але трасу вже не поверне.
7. Команда ділить один OTel-колектор на кількох розробників і вмикає телеметрію Claude Code з типовими прапорцями. Що бачать усі, хто має доступ до бекенда?
Так. За OAuth user.email іде в кожен запис; промпт і відповідь — <REDACTED>, аргументи інструментів не пишуться.
Промпти типово редагуються (OTEL_LOG_USER_PROMPTS вимкнено), а події йдуть одразу, щойно задано OTEL_LOGS_EXPORTER. Зате user.email є завжди, коли він доступний. Видаляйте його процесором колектора, якщо доступ до бекенда ширший.
8. Чому в Lectern провал гейта ставить на спан error.type, але не статус ERROR?
Так. Timeout чи падіння агента — збій, ERROR. Вгадуваний ключ чи провал гейта — штатна робота каскаду; його видно через error.type і lectern.verdict.
Конвенції не обмежують ERROR HTTP-кодами, і бекенди показують такі спани. Причина в семантиці алертів: ERROR на кожен провал гейта будив би чергового від нормальної роботи каскаду.
9. Як у тесті перевірити, що спроба агента — дитина спану задачі, без мережі й без моделі?
Так. In-memory експортер дає справжні спани з parent, атрибутами й подіями; синхронний процесор кладе їх у пам'ять одразу після завершення.
Jaeger — мережа, Docker і нестабільність у CI. Мок перевіряє виклики, а не структуру: він пропустить і розрив контексту, і неправильного батька.
10. Сума cost_usd подій claude_code.api_request за сесію збігається з total_cost_usd SDK, а запитів у подіях 5, у потоці SDK — 4. Висновок?
Так. У прогоні це був generate_session_title: 3,3–5,8% вартості задачі; CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1 його прибрав.
Якби подія задублювалась, сума перевищила б total_cost_usd. Якби SDK щось втратив, вартість не зійшлась би. Збіг сум при різній кількості запитів означає оплачений запит, якого немає в потоці повідомлень.
