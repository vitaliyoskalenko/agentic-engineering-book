01

Від in-process до сервераЩо змінюється, коли інструменти стають окремим процесом

В уроці 2.5 три функції Lectern жили всередині агента: create_sdk_mcp_server загортав Session в MCP-сервер у тому самому процесі. Ними міг користуватися лише цей один агент. Автор курсу працює в Claude Code, його колега в Cursor, CI запускає Agent SDK. Окремий сервер lectern mcp дає їм усім один контракт: ті самі імена, схеми, перевірку цитат і ті самі помилки.

Цінність Lectern у правилі «цитата дослівно з лекції». Поки воно живе в одному агенті, кожен новий клієнт (Cursor автора, CI, чужий агент) або обходить його, або копіює. MCP-сервер робить правило частиною інфраструктури, а не промпту.

Сервер — тонкий шар над Session. Описи інструментів беруться з SCHEMAS уроку 2.5, схеми входу генеруються з type hints, схеми виходу — з Pydantic-моделей повернення:

# src/lectern/mcp_server.py (фрагмент; повний файл — console/lectern-mcp/)
READ_ONLY = ToolAnnotations(read_only_hint=True, open_world_hint=False)
# save_quiz перезаписує out/<id>.quiz.json: це зміна стану, і попередній квіз зникає
WRITES = ToolAnnotations(read_only_hint=False, destructive_hint=True, idempotent_hint=True,
                         open_world_hint=False)

def _tool[T](fn: Callable[..., T], *args) -> T:
    """tools.ToolError -> mcp ToolError. Без цього SDK вважає помилку збоєм сервера, і модель
    бачить лише «Error executing tool …» замість «Unknown lecture …, Available: …»."""
    try:
        return fn(*args)
    except tools.ToolError as e:
        raise ToolError(str(e)) from None

def build_server(lectures_dir: Path, out_dir: Path, skill_dir: Path | None = None) -> MCPServer:
    lectures = load_lectures(lectures_dir)
    library = Library(Session(lectures, out=out_dir), lectures_dir, out_dir)
    mcp = MCPServer("lectern", version=__version__, instructions="…")

    def scoped(lecture_id: str, **changes) -> Session:
        """Session з однією лекцією: validate() шукає цитату в УСІХ лекціях сесії."""
        text = _tool(library.session.read_lecture, lecture_id)
        return dataclasses.replace(library.session, lectures={lecture_id: text}, **changes)

    # structured_output=False: інакше текст лекції їде двічі (content + {"result": …})
    @mcp.tool(description=SCHEMAS["read_lecture"][0], annotations=READ_ONLY, structured_output=False)
    def read_lecture(lecture_id: str) -> str:
        return _tool(library.session.read_lecture, lecture_id)

    @mcp.tool(description=SCHEMAS["check_quote"][0], annotations=READ_ONLY)
    def check_quote(lecture_id: str, quote: str) -> QuoteVerdict:
        return QuoteVerdict(**_tool(library.session.check_quote, lecture_id, quote))

    @mcp.tool(description=SCHEMAS["save_quiz"][0] + " Writes <lecture_id>.quiz.json …", annotations=WRITES)
    def save_quiz(lecture_id: str, items: list[QuizItem]) -> SavedQuiz:
        session = scoped(lecture_id, n=len(items), out=library.out_dir / f"{lecture_id}.quiz.json")
        library.out_dir.mkdir(parents=True, exist_ok=True)
        saved = _tool(session.save_quiz, [it.model_dump() for it in items])
        return SavedQuiz(**saved | {"path": session.out.name})   # без абсолютного шляху машини

Session.validate() шукає цитату в усіх лекціях сесії. У CLI лекція одна, і це непомітно. Сервер вантажить усі lectures/*.txt, тож без scoped() цитата з лекції про стеки пройшла б save_quiz для лекції про хеш-таблиці. Тест test_quote_from_another_lecture_does_not_pass це фіксує.

Чому немає lifespan. Lifespan у MCPServer потрібен для ресурсів з асинхронним відкриттям і закриттям: пул з'єднань, HTTP-клієнт, індекс. Лекції — звичайні файли, тож стан тримає замикання. Друга причина виявилася під час збирання: статичний ресурс не отримує Context взагалі, отже й lifespan_context:

03

Що бачить модельДва канали результату, чотири види помилок

Інструмент з анотацією повернення -> QuoteVerdict отримує outputSchema у tools/list, а результат має два канали: content (текст) і structuredContent (дані за схемою). Специфікація радить дублювати JSON у текстовому блоці для зворотної сумісності, і SDK так і робить. Який канал потрапляє в контекст моделі, вирішує клієнт. Перевірили на сервері, що свідомо повертає в каналах різне:

Claude Code віддав моделі structuredContent, а текст відкинув. Звідси правило: усе, що модель має прочитати (підказку closest_sentence, warnings), кладіть у структуровану модель, а не лише в текст. Інші клієнти можуть показувати content, тож обидва канали мають бути рівнозначні, і SDK це гарантує, коли ви повертаєте модель.

Docstring — теж контекст моделі

Перша версія QuizItem мала docstring «Канонічне питання Lectern; має збігатися з SCHEMAS…». Pydantic поклав його в description схеми, тобто в кожен виклик моделі, разом із $defs. Пояснення для людей — у коментарях, а тест перевіряє, що description у схемі немає.

Помилки SDK ділить на очікувані й збої і показує їх по-різному. Усі рядки нижче отримано на цьому сервері:

04

Ресурси й промптlecture://{lecture_id} і generate-quiz як slash-команда

Інструменти викликає модель. Ресурси й промпти обирає людина або застосунок: ресурс підтягують у контекст через @, промпт запускають командою. Для Lectern це два різні сценарії: «покажи лекцію, я сам поставлю питання» і «зроби квіз за правилами курсу».

@mcp.resource("lecture://index", mime_type="application/json",
              description="Lecture ids with their size; read one as lecture://{id}.")
def lecture_index() -> str:
    return json.dumps([{"id": k, "uri": f"lecture://{k}", "chars": len(v)} for k, v in lectures.items()])

@mcp.resource("lecture://{lecture_id}", mime_type="text/plain", description="Full text of one lecture.")
def lecture(lecture_id: str) -> str:          # змінні шаблону = параметри функції, інакше ValueError
    if lecture_id not in lectures:
        raise ResourceNotFoundError(f"Unknown lecture {lecture_id!r}")
    return lectures[lecture_id]

render = load_render(skill_dir)   # importlib з .claude/skills/generate-quiz/scripts/render.py — не копія

@mcp.prompt(name="generate-quiz", title="Generate a Lectern quiz")
def generate_quiz(lecture_id: str, n: str = "5") -> str:   # перевірку невідомої лекції пропущено
    try:
        task = render.render_task(str(library.lectures_dir / f"{lecture_id}.txt"), n)
    except render.PromptError as e:
        raise MCPError(INVALID_PARAMS, str(e)) from None
    rules = render.load("quiz.system")[1]                 # у промпті MCP немає ролі system
    return f"{rules}\n{task}\nUse the lectern MCP tools with lecture_id …"
  1. Шаблон проти статичного. lecture://index і lecture://{lecture_id} перетинаються: SDK віддає перевагу статичному, тож лекцію з файлу index.txt як ресурс не прочитати (інструментом можна). Записано в BACKLOG.
  2. Аргументи промпту — рядки. Протокол передає {"n": "3"}. З анотацією n: int SDK перетворить "3", але "abc" впаде ще до функції, і клієнт отримає Internal server error. Тому n: str: число перевіряє render_task() зі skill, а її PromptError перекладено в MCPError.
  3. Один текст правил на два шляхи. Промпт імпортує render.py skill з уроку 6.1, тому quiz.system.txt довелося зробити нейтральним до каналу (v2, BACKLOG B6): «інструмент check_quote, якщо підключено, інакше lectern check --quote». Заодно прибрано застарілий рядок «--quote не перевіряє довжину» (неправда з часу B2).

У Claude Code промпт з'являється в меню / як /lectern:generate-quiz (MCP), а в -p його викликають повним ім'ям; аргументи розділяються пробілами. Ресурс, за документацією, додають у повідомлення як @lectern:lecture://hashing.

Тести без моделіСправжній MCP-клієнт у пам'яті

У SDK 2.x той самий mcp.Client, що підключається до URL чи підпроцесу, приймає об'єкт сервера і говорить із ним у пам'яті: без порту й підпроцесу, але через ті самі tools/list, tools/call, валідацію аргументів і перетворення винятків. Хелпер 1.x create_connected_server_and_client_session видалено.

raise_exceptions=True не змінює інструменти: виняток у тілі інструмента все одно стає is_error. Прапорець показує справжній текст збою поза інструментами, який інакше ховається за Internal server error. Тому тест помилки промпту свідомо створює клієнт без нього: так його бачить Claude Code. Перевірили, що цей тест ловить стару версію з ValueError: «Actual message: 'Internal server error'».

Версії контрактуЛамкі зміни схем і депрекація інструмента

У MCP немає версії окремого інструмента. Контракт сервера — це імена, inputSchema, outputSchema, аргументи промптів і URI-шаблони; версію пакета сервер повідомляє в serverInfo (у кожному результаті Lectern видно {"name": "lectern", "version": "0.3.0"}). Модель читає схеми заново в кожній сесії, тому сама до нової схеми пристосується. Ламаються ті, хто запам'ятав стару:

  • код, що викликає інструмент напряму або читає structuredContent (сервіс 6.5, CI, скрипти);
  • тексти з іменами інструментів і аргументів: промпти, skills, CLAUDE.md, правила дозволів, matcher-и хуків;
  • клієнти, що кешують tools/list: у ревізії 2026-07-28 результат несе ttlMs, а Claude Code тримає кеш discovery для віддалених серверів.

Квіз11 ситуацій

11 питань
1. read_lecture викликає Session.read_lecture, яка кидає власний lectern.tools.ToolError("Unknown lecture 'l9'. Available: l4, l5"). Сервер виняток не перекладає. Що отримає модель?
Так. Для SDK лише його ToolError (і ResourceError) — передбачена помилка з текстом для моделі. Решта — збій: текст ховається, трасування йде в stderr.
Виняток у тілі інструмента справді стає isError-результатом, а не JSON-RPC помилкою, але текст збереже лише ToolError з SDK. Власний клас — «Error executing tool read_lecture», і модель не дізнається, які лекції є.
2. read_lecture(lecture_id) -> str зареєстровано без structured_output=False. Що зміниться для Claude Code?
Так. Скаляр SDK загортає в {"result": …} і дублює в content. Прогін-зонд показав, що Claude Code 2.1.300 дає моделі саме structuredContent.
-> str дає схему {"result": string}, тож реєстрація проходить. А ігнорувати structuredContent клієнт не зобов'язаний: Claude Code показав моделі саме його і відкинув текст.
3. save_quiz перезаписує out/<id>.quiz.json; повтор з тими самими аргументами дає той самий файл. Які анотації чесні?
Так. Інструмент змінює середовище, попередній результат втрачається, а повтор безпечний. Клієнт може попросити підтвердження саме для такого виклику.
Read-only означає «нічого не змінює», а файл перезаписується. Destructive false — лише для суто додавальних змін, а тут старий квіз зникає. Повтор з тими самими аргументами нічого не додає, тож idempotent — true.
4. Щоб узяти стан з lifespan, ви пишете def lecture_index(ctx: Context) -> str для ресурсу lecture://index. Що станеться?
Так. Context отримують лише ресурси-шаблони. Для Lectern це ще й аргумент проти lifespan: лекції — файли, і замикання простіше.
SDK перевіряє сигнатуру під час декорування: «Context injection for static resources is not supported». До запиту справа не доходить, тож -32603 ви не побачите.
5. Промпт оголошено як generate_quiz(lecture_id: str, n: int = 5). У claude -p запускають /mcp__lectern__generate-quiz hashing п'ять. Що буде?
Так. Pydantic відхиляє «п'ять» для int, SDK перетворює це на прихований збій. Тому в Lectern n: str, а PromptError з render_task() перекладено в MCPError.
Аргументи промпту в MCP мають лише ім'я, опис і ознаку обов'язковості, типу немає, тож Claude Code перевірити його не може. До render_task() рядок не дійде: int-анотація падає раніше.
6. Чому тест помилки промпту створює Client(server) без raise_exceptions=True, хоча фікстура інших тестів його вмикає?
Так. Прапорець показує справжній текст збою поза інструментами. Тест має перевіряти саме те, що отримає справжній клієнт.
На інструменти прапорець не впливає: їхні винятки однаково стають is_error. Режим протоколу задає mode=, а не raise_exceptions.
7. Сервер Lectern тепер іде в плагіні lectern-tools. У налаштуваннях лишилися правило allow: mcp__lectern__check_quote і хук PreToolUse з matcher mcp__lectern__.*. Що відбувається?
Так. Повне ім'я містить ім'я плагіна і ключ сервера. Документація прямо попереджає, що matcher за голим ключем для сервера з плагіна не спрацює ніколи.
Нормалізації немає: сервер реєструється як plugin:lectern-tools:lectern, а його інструменти — mcp__plugin_lectern-tools_lectern__*. Регулярні вирази matcher підтримує, але ім'я не збігається.
8. У версії 0.3.x read_lecture(lecture_id) стало read_lecture(lecture, page=None), і mcp_contract.py check падає. Що робити?
Так. Видалений lecture_id і новий обов'язковий lecture ламають код, промпти, дозволи й хуки, що пам'ятають старе ім'я. До 1.0 ламка зміна — новий minor.
page справді сумісний, але разом з ним зник lecture_id і з'явився обов'язковий lecture. Модель пристосується, а сервіс 6.5, CI і правила дозволів — ні.
9. Репозиторій курсу, п'ятеро авторів, усі мають отримати той самий сервер Lectern. Який scope і про що пам'ятати?
Так. Project scope — єдиний, що ділиться через git. Інтерактивна сесія питає дозволу, а неінтерактивна — ні.
User і local записуються в ~/.claude.json конкретної людини, і до команди нічого не дійде. MCP local scope не має стосунку до settings.local.json.
10. Сервер вантажить 12 лекцій. save_quiz для лекції A приймає питання з цитатою з лекції B. Чому?
Так. У CLI лекція одна, і припущення не було видно. scoped() звужує сесію перед save_quiz і check_quiz, а тест це закріплює.
Нормалізація торкається лише лапок, тире й переносів, речення з різних лекцій не зливаються. Кеш tools/list зберігає визначення, а не аргументи. Причина в any(... for t in self.lectures.values()).
11. Агента уроку 2.5 переводять з in-process сервера на зовнішній lectern mcp через stdio. Що в agent_sdk.run перестане працювати?
Так. Об'єкт Session агента більше ніхто не викликає, тож saved лишиться None, і run() кине «no valid quiz», хоча файл записано.
Імена залежать від ключа в mcp_servers, а не від транспорту, тож mcp__lectern__* не змінилися. Синхронізації об'єктів між процесами MCP не має: є лише результати й файли.

isErrorПомилка виконання інструмента в результаті, яку модель читає й виправляє; на відміну від JSON-RPC помилки протоколу.
Client(server)Client(server) у тесті: справжній протокол без порту й підпроцесу.
entry pointКоманда, якою клієнт запускає сервер: lectern mcp з [project.scripts] і опційної залежності [mcp].

версії схемСхеми інструментів, промптів і ресурсів як контракт: знімок, класифікація ламких змін, версія, депрекація.
